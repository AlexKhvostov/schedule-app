## Подтверждённые замечания

Приоритет P1 — требуется исправить в первую очередь; P2 — заметная ошибка согласованности. Замечания подтверждены исполнением актуальных TypeScript-функций в изолированном Node/VM-сценарии с подменой React hooks и сетевых ответов. Это контролируемая проверка логики, не живая проверка Supabase. Проверочный сценарий исполнялся через stdin без добавления тестов в приложение.

### 1. P1: замена чужих меток не атомарна

Место: [useScheduleMutations.ts](../../apps/web/src/v2/schedule/useScheduleMutations.ts#L184), строки 184–193; [серверная функция удаления](../../supabase/migrations/20260922160000_mark_edit_act_as.sql#L175).

`confirmOverwrite` сначала вызывает `removeForeignSlots`, затем отдельную `applyOwnSlots` через `writeDiffs`. Первый запрос уже завершает свою транзакцию. Если второй запрос отклонён (например, игрок отключил лимит в другом окне или сеть пропала), чужая смена удалена, новая не поставлена. Воспроизведение: успешное удаление → ошибка `schedule-player-limit-not-selected` при постановке; конечный серверный слот пуст. Уведомление ботом также не вызывается, поскольку обработчик выходит по ошибке.

Рекомендация: одна защищённая транзакционная RPC для всего подтверждённого действия с проверкой ожидаемых владельцев. Уже существующую `replace_foreign_slots` сначала сверить с текущими правами и смешанными диапазонами, не подключать вслепую.

### 2. P1: ошибка загрузки нового месяца показывает данные старого

Место: [useScheduleMonth.ts](../../apps/web/src/v2/schedule/useScheduleMonth.ts#L112), строки 112–123.

Хранилище индексировано только `variant:limit`. При переходе месяца предыдущие данные сохраняются; обновляются только успешно загруженные виды. Даже при ошибке ставится `readyStamp` нового месяца, снимающий блокировку редактирования. Воспроизведение: октябрь успешно загружен, ноябрь вернул ошибку; `gridLoading=false`, под ноябрём остаётся октябрьская сетка с 31 днём и прежними метками. При сбое одного вида проблема касается только этого вида. Действие по старой метке использует уже даты нового месяца.

Рекомендация: связывать снимок с месяцем и готовностью каждого вида; старый снимок сохранять только при обновлении того же месяца, а незагруженный новый месяц держать закрытым для правок с возможностью повтора.

### 3. P1: запоздалый откат записи перезаписывает другой месяц

Место: [useScheduleMutations.ts](../../apps/web/src/v2/schedule/useScheduleMutations.ts#L120), строки 120–133.

Обработчик ошибки без проверки месяца или версии восстанавливает целиком `prevGrid`. Воспроизведение: начать запись октября, перейти на успешно загруженный ноябрь, вернуть ошибку октябрьского запроса; ноябрь заменяется октябрьской сеткой. Аналогичный откат способен стереть из экрана более позднюю успешную правку того же месяца. Успешное подтверждение чужого диапазона на строке 215 также записывает старый снимок без проверки актуального месяца.

Рекомендация: привязать запись к месяцу и версии; откатывать только затронутые клетки, если их версия не изменилась, и согласовывать результат со свежим серверным снимком.

### 4. P1: метки без букв не сохраняются и не удаляются

Место: [schedulePresentation.ts](../../apps/web/src/v2/schedulePresentation.ts#L24), строки 24–29; вызов на [useScheduleMutations.ts](../../apps/web/src/v2/schedule/useScheduleMutations.ts#L90), строки 90–93.

Буквенная метка по принятому правилу необязательна. `seatDiffs` сравнивает только `t`, а пустой слот и игрок без букв дают одинаковую пустую строку. Воспроизведение: пустая клетка → объект игрока с `t: ''`; результат `seatDiffs=[]`. Экран локально меняется, но запрос записи не вызывается; после загрузки результат исчезает. Обратное снятие также даёт пустой diff. В Demo сетка сохраняется до проверки diff, поэтому обычные Demo E2E это скрывают.

Рекомендация: определять изменение по наличию владельца и `memberId`, отдельно учитывать сохраняемые данные клетки; добавить тест пустой буквенной метки в обоих направлениях.

### 5. P2: realtime игнорирует чужую запись за текущего игрока

Место: [useScheduleMonth.ts](../../apps/web/src/v2/schedule/useScheduleMonth.ts#L177), строки 177–180.

Любое событие с `memberId === actingRef.current` обновляет только занятость и сразу выходит. Это не доказывает, что запись сделало текущее окно. Если тот же пользователь поставил метку из второй сессии либо администратор поставил её за него, основная сетка и календарь в первом окне не обновятся до иного события или перезагрузки. Воспроизведение: передать событие собственной метки; количество вызовов загрузки месяца не меняется. Локальная занятость также имеет приоритет над remote для уже загруженных пар, поэтому `refreshBusy` не исправляет отображение.

Рекомендация: исключать только доказанно локальные подтверждения операций либо согласовывать все события после завершения текущих записей. Проверить двухсессионным Working-сценарием.
