## Принятые правила

- UUID карточки — постоянная сущность участника. Discord ID и ID дистанции — разные внешние идентификаторы. Смена Discord ID вне объёма.
- Факты импорта сохраняют ID дистанции, исходный ник и числа. Владелец определяется при чтении через member_distance_ids.
- Первое значение списка ID в карточке — основное. Ник карточки обновляет основной ID. Дополнительные ID участвуют в дистанции и приоритетах.
- Последний загруженный CSV считается актуальным по нику независимо от месяца, включая повтор чисел и нулевые строки.
- Добавление/снятие ID сразу меняет связь со всей историей, не удаляя факты. Другому участнику тот же ID назначить нельзя, пока он занят.
- Роль RedParty берётся от Discord текущей карточки. Внутренняя legacy-роль member больше не определяет состав контроля дистанций и доступность добавления записи администратором.
- Старый справочник и сохранённые ранее member_id/Discord ID остаются исторической информацией. Источник начальных назначений — текущие карточки.

## Проверенные причины и результат

Прежний импорт закреплял Discord/участника через отдельный справочник. Ручной ID карточки мог измениться позже, а прежняя связь записи не пересчитывалась. Для ID211/283 справочник расходился с текущими карточками; для363 запись была импортирована до назначения карточки. Дополнительно основной список контроля требовал старую внутреннюю роль member/admin: обычная активная карточка могла попасть только как историческая строка, без кнопки добавления.

Внутренняя member — прежняя техническая роль, которую выдаёт set_discord_access при разрешении участника (а также вместе с admin). Создание современной карточки и роль RedParty не обязаны выдавать эту роль. Для исправления не требуется массово менять роли: контроль использует текущие карточки, а RedParty проверяет отдельно.

Импорт до появления карточки остаётся допустимым: данные не теряются, неизвестный ID виден без фильтра RedParty. После назначения связь появляется. Подбор владельца по никам исключён; оба ника могут меняться.
