## Что подтверждено локальным кодом

1. [currentPriorityPeriod](../../apps/web/src/schedule/priorities.ts) выбирает февраль/май/август/ноябрь по переданной дате. [V2Schedule](../../apps/web/src/v2/V2Schedule.tsx) передаёт первый день открытого месяца расписания (строка 143), а не сегодняшнюю дату. Поэтому ноябрьское расписание использует ноябрьский расчёт даже при предварительном статусе. Октябрьское выбирает августовский.
2. [LivePriorities](../../apps/web/src/v2/LivePriorities.tsx) выбирает период по сегодняшней дате при открытии и генерирует 16 вариантов вокруг неё (включая следующий период). Выпадающий список — просмотр; отдельного реестра утверждённых расчётов и разрешения на применение нет.
3. Для 50–100 очки = старшие 50 × 0,5 + старшие 100 × 1 + младшие 50 × 1 + младшие 100 × 2. Берутся шесть предшествующих месяцев Winamax, все части, только выбранный вид. Август 2026: февраль–апрель ×0,5 и май–июль ×1; ноябрь 2026: май–июль ×0,5 и август–октябрь ×1. Дополнительно вес лимита100 равен2.
4. [Серверный кэш](../../supabase/migrations/20261104145020_priority_matrix_cache.sql) хранит период × вид × группу, создаётся при чтении и пересчитывается после изменений исходных данных; кнопка обновления принудительно пересчитывает выбранную пару/период. Это не неизменяемый архив утверждённых версий. Core и исключения берутся из текущих карточек/настроек, без привязки к кварталу.
5. Предварительность: до8-го числа начала периода ИЛИ меньше20 логических записей последнего исходного месяца выбранного вида с50/100. Это не20 уникальных игроков и не проверка полноты по всем людям. В очереди флаг используется только для пояснения; блокировки применения нет. После8-го числа даже статус «рассчитан» не гарантирует полноту.
6. [rankPriorities](../../apps/web/src/schedule/priorities.ts): таблица50–100 по очкам, затем ник/ID, Core справочный. [orderRosterRows](../../apps/web/src/schedule/roster.ts): активная очередь Core по возрастанию → очки по убыванию → ник/ID; исключённые внизу без номера. Старый grid_priority участвует во вспомогательной первичной сборке строк, но итоговая активная очередь его не использует. Номер очереди — последовательный номер, а не буквально номер Core.
7. В250 дистанционных очков нет: отдельный Core выбранного вида, затем ник/ID. Все четыре Core независимы. Фильтры страницы Приоритеты не меняют общий состав/правила расписания. Состав активной очереди и часы определяются фильтрами расписания, доступом и выбранными лимитами; исторические строки отделены.
8. [load_month_roster](../../supabase/migrations/20261104164056_compact_month_roster.sql) получает от клиента период и отдаёт ID/Core/очки/исключение из того же кэша. [data/roster](../../apps/web/src/data/roster.ts) проверяет точное совпадение запрошенного/полученного периода; при добавлении активного расчёта этот контракт нужно изменить, а не просто вернуть август вместо ноября под прежним полем.
9. [useRosterSource](../../apps/web/src/v2/schedule/useRosterSource.ts) обновляет открытое видимое окно раз в30секунд и по focus/сигналам. BroadcastChannel работает между вкладками браузера, не гарантирует немедленного межпользовательского обновления.
10. [OptFieldGrid](../../apps/web/src/v2/optField/OptFieldGrid.tsx) отображает метки по существующим дню/получасу/уровню. Рейтинг не переставляет координаты занятости. Автоматическая блокировка хода очереди ещё не реализована; это отдельная функция.

## Принятое уточнение Алексея — 5 ноября 2026,13:09 Минск

Источник: прямое сообщение в этом чате после исследования.

- Администратор выбирает, какой существующий расчёт используется для упорядочения участников расписания и списка «Игроки месяца».
- Выбор расчёта и обновление его данных независимы. Существующий кэш, автоматическое обновление после изменения дистанций и остальные правила расчёта сохраняются. Валидное чтение не должно заново рассчитывать очки.
- Администратор сам оценивает полноту данных перед переключением. Новый период или статус готовности не переключает источник очереди автоматически.
- Отдельные утверждённые версии, замораживание очков и история переключений не нужны. Предыдущая рекомендация агента о снимках/версиях/назначениях исторических месяцев заменена этим решением и исключена из объёма.
- Начальный желаемый период из первого сообщения — предыдущий квартальный, то есть август2026 по существующему календарю. Данные не переключались.
- Календарь остаётся квартальным: февраль/май/август/ноябрь. Алексей прямо подтвердил: имел в виду август, сентябрь назвал по ошибке.
- Уточнение13:14: При каждом входе в раздел «Приоритеты», повторном входе после ухода из него и обновлении страницы по умолчанию открывается активный расчёт, используемый для сортировки расписания. Самый новый календарный расчёт и ранее вручную просмотренный период не подменяют этот выбор. Пользователь может временно выбрать другой период для просмотра; общий активный расчёт от этого не меняется. Следующий вход или обновление снова открывает актуальный серверный выбор.

## Уточнённое предложение реализации

1. Хранить общий серверный выбор действующего периода. Сохранять его отдельной административной RPC с проверкой прав; не делать выбор личной настройкой браузера.
2. На странице Приоритеты оставить просмотр любого периода и предложить отдельное действие «Использовать для сортировки». Показывать выбранный для использования период независимо от просматриваемого. Место управления пока предложено агентом, а не отдельно утверждено пользователем.
3. Очередь получает выбранный сервером расчёт, вместо автоматического вычисления периода из месяца расписания. Формула, Core → очки → ник, исключения и состав сохраняются. В250 остаётся Core/ник.
4. Скорректировать load_month_roster и клиентский контракт: запрошенный месяц расписания и период используемого расчёта различать; при переключении обновлять ревизию и очередь. Сохранить компактный ответ, условное чтение и переиспользование готового кэша.
5. Просмотр периода и пересчёт не должны менять серверный выбор. Переключение не перемещает метки, не меняет часы и права записи. Ошибка загрузки не должна молча включать другой расчёт.
6. Кнопка управления только администратору; проверка на сервере обязательна. Нынешнее canManage/is_staff не копировать без проверки соответствия административному праву.
7. Новая отдельная история/привязки по месяцам не добавляются. Общий выбранный расчёт служит источником очереди; автоматического восстановления исторических очередей не обещать.

Окончательный охват переключения видов (общее для Nitro/Regular либо отдельно) ещё не был явно уточнён; исходное предложение — общий период, независимые очки видов. Это не основание реализовывать дополнительную историю или версии.

## Проверки для будущей реализации

- При активном августовском и уже рассчитанном ноябрьском периоде новый вход открывает август; ручной просмотр ноября допустим, но перезагрузка и повторный вход возвращают к активному. После переключения администратором на ноябрь новый вход открывает ноябрь.

- При открытом ноябре выбранный августовский расчёт определяет очередь до явного переключения.
- Изменение дистанций обновляет соответствующий кэш и действующую очередь без повторного одобрения; неизменённые исходные данные не вызывают повторного расчёта при каждом чтении.
- Наступление нового периода, просмотр отчёта и кнопка пересчёта не меняют выбранный источник сортировки.
- Core остаётся первым, виды не смешиваются,250 остаётся Core/ник, исключения и допуски прежние.
- Выбор общий между пользователями; права проверяются сервером; кэш клиента не удерживает старую очередь после переключения.
- Координаты меток и часы не изменяются.
