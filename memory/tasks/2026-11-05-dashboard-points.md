## Уточнение пользователя и проверка действующего API — 18:42

Алексей предложил перейти к реальным данным и прямо поручил проверить доступность endpoints. Адрес найден в README/памяти winamaxScraper: `dashboard.redparty.ru`, front controller `/api/index.php?__route=...`. Не использовались пароль БД или admin/cron-секреты.

- HTTPS root и OPTIONS: TLSV1_UNRECOGNIZED_NAME, соединение не установлено. Проверка сертификата не отключалась. HTTP root:200. OPTIONS PHP:204; CORS origin `*`, разрешён только Content-Type, Authorization не разрешён.
- HTTP GET /api/regs без сессии:200 JSON,209записей (151ours/58theirs). Проверка добавления/удаления не выполнялась.
- HTTP GET /api/points/heatmap, limit50, top1: за2026-11-05 и2026-11-04 ноль строк. За2026-11-05 downtimeHours0–16, хотя raw /api/points содержит точки.
- HTTP GET /api/points за2026-11-05, limit50, top1:200 JSON,1серия/51точка; временной диапазон выбранной серии07:30:52–13:36:55 UTC. Это не утверждение о последнем сборе всей базы.
- Карта2026-10-15/50: есть436игроков. Сквозная проверка с реальным ответом через новый TypeScript loadPoints (Top10):10строккарты,10серий,426точек,missing0,ошибок0; выравнивание по240слотов. Вывод: endpoints доступны по HTTP; чтение отчётов/регов публичное, защита на PHP отсутствует для проверенных операций. Серверная почасовая таблица за проверенные свежие даты пуста при наличии сырья — причина/cron ещё не проверены. Не подключать браузерный React к открытому HTTP API: сначала TLS, серверный допуск и CORS, восстановление агрегатов. Действующие серверы не перенастраивались, POST/PUT/DELETE/cron/пересчёт не вызывались. Старый PHP при обычных GET сам выполняет ensure таблиц/индексов; до/после схема не снималась, поэтому отсутствие внутренних побочных действий PHP не утверждаем.
