## Единственная реализация и порядок новой работы

Рабочее приложение — apps/web, серверные миграции и функции — supabase. CI запускает web-проверки из apps/web. В imports/конфигурации сборки не обнаружено зависимости от sandbox. Sandbox содержит 110 отслеживаемых исторических файлов; он не удалялся и не переносился. Исторические SQL-миграции являются последовательностью схемы, а не лишними версиями, и должны оставаться.

Рабочее уточнение по поручению Алексея: начинать из актуального main в основной папке. Не создавать/выбирать другие ветки и worktrees автоматически. При специальном прямом поручении можно использовать отдельную ветку. Не переносить архивные файлы целиком поверх main. Это правило процесса, а не технический запрет Git: новая ветка всё ещё может быть создана вручную.

## Предложение для отдельного разрешения

1. Повторно сверить origin/main и preview: после аудита они могут измениться.
2. Сохранить `41a685d094a776475043c7b775df8b3865126125` архивным Git-тегом `archive/preview-schedule-ui-2026-11-05` и опубликовать только этот тег. Тег — неподвижная метка истории, не дополнительная ветка разработки. Все коммиты уже доступны из main, метка сохраняет удобное имя старого состояния.
3. Удалить серверную `preview/schedule-ui` и локальную `codex/locked-slot-appearance`; main и его историю не переписывать. Без force-слияний, без нового выпуска приложения.
4. Сохранить существующий архив папок и sandbox. Отдельно решить судьбу старого preview-сайта; его отключение/удаление в Vercel не считать автоматически разрешённым удалением ветки.
5. После действий проверить серверный список веток, единственный локальный main и текущий Production.

Удаление и push требуют разрешения согласно правилам пользователя. Сейчас выполнены только аудит и безопасное уточнение документации. Следующий шаг — решение Алексея по пунктам 2–3; слияние кода не требуется.
