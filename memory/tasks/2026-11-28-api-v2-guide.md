## Результат

- Новые ключи из панели передаются для зашифрованного хранения в Supabase Vault; SHA-256 остаётся способом авторизации внешнего API. Сам ключ и отпечаток не попадают в список подключений.
- Root получает секрет по явному нажатию отдельной командой `reveal`. Проверяется актуальная роль; просроченные и отозванные ключи не выдаются. Прямой доступ браузерных ролей к Vault закрыт. Повтор create не дублирует секрет.
- После создания можно открыть или скопировать инструкцию с токеном. При повторном открытии подстановка включается явно. Видимые примеры и копируемый текст используют один токен. Ошибки и подтверждение копирования показаны рядом с действием.
- После закрытия окна рабочий токен очищается из React-состояния; localStorage/sessionStorage для него не используются. Demo хранит только учебные ключи в памяти модуля до перезагрузки.
- Старые ключи с единственным SHA-256 восстановить невозможно. В инструкции есть поле для временной вставки своей сохранённой копии; на сервер эта вставка не сохраняется. Если копия утеряна, понадобится новый ключ.
- Исправлено устаревшее описание приоритета: после Core/баллов используется общая позиция RedParty `club_order`, затем имя/ID. Пример ответа и универсальная инструкция согласованы с миграцией24ноября.

## Следующий шаг

Перед публикацией проверить настоящие Vault/reset/security contracts/database lint в CI или тестовом Supabase. После согласования выпуска сначала применить20261128152414, затем опубликовать клиент. Не заменять и не отзывать существующие ключи автоматически. При ручном переносе Vault в новый проект требуется правильный root key по официальной документации; секреты в git не записывать.

Навыки: session-memory — план и передача; ui-ux-pro-max — компактность, доступность и постепенное раскрытие справки (поиск не дал релевантного правила disclosure, применены общие практики); supabase — документированный Vault и серверная граница прав.
