# Предложение: синхронизация External API v2

12 ноября 2026, Europe/Minsk. Статус: исследование выполнено, предложение ожидает согласования. Код, схема базы, Edge Function и действующий API не менялись.

Цель: обновлять данные внешнего клиента каждые три минуты, передавая только необходимые изменения. Алексей также предложил отделить сведения о людях от слотов расписания.

## Текущее поведение

[Описание API](../../supabase/functions/external-api/README.md), [реализация снимков](../../supabase/migrations/20261103165923_external_api_snapshot_pages.sql).

Каждый новый запрос с date/days создаёт неизменяемый снимок на 15 минут. Сервер собирает весь выбранный диапазон, формирует JSON, записывает страницы по 1000 меток. Клиент загружает страницы последовательно. Имя владельца, Discord ID и оформление его метки повторяются в каждом слоте.

Существующий cursor продолжает страницы одного снимка. Он не получает изменения после предыдущей выгрузки. Постоянного кеша месяца нет.

[Версии расписания](../../supabase/migrations/20261107113020_event_driven_schedule.sql) уже существуют: отдельная версия для date + kind_id и общие версии config/directory. Они меняются в одной транзакции с данными. Версия участка сохраняется после удаления последней метки. Это подходящая основа для внешней синхронизации без нового журнала всех действий.

Незавершённое сравнение RAM/swap после настройки shared_buffers остаётся в [отчёте теста](2026-11-12-buffers-trial.md). Архитектурное предложение его не заменяет.

## Рекомендуемый вариант

Новый endpoint `/v2/schedule/sync`. Один запрос раз в 180 секунд. В ответе два логических раздела:

- **people**: стабильный person_id, имя, разрешённый Discord ID, оформление метки;
- **schedule**: даты, линии, получасовые слоты и ссылка person_id вместо повторения сведений о человеке.

Разделение данных не требует двух обязательных HTTP-запросов. Один ответ обеспечивает согласованность, одну авторизацию и меньше сетевых обращений. Самостоятельные endpoints людей и приоритетов можно добавить позже, если появится независимый потребитель. Приоритеты в эту работу не входят.

Справочник по умолчанию содержит только участников, связанных с выбранным диапазоном. Выдача всех членов клуба по прежнему праву schedule:read расширила бы доступ к данным и не подразумевается этим предложением.

person_id должен быть стабильным идентификатором внешнего контракта, а не ником или auth_user_id. При реализации проверить существующие идентификаторы и переиспользовать подходящий; отдельную таблицу ID не создавать без необходимости.

### Начальная загрузка

Первый запрос задаёт date/days/variant/limit и возвращает полный выбранный диапазон вместе со справочником людей. Полнота означает только этот диапазон и фильтры. Правила Europe/Madrid, получасов, DST и tables сохраняются.

Данные и версии фиксируются в одном согласованном SQL-срезе. После завершения всех страниц клиент получает sync_cursor и сохраняет его вместе с данными. Отдельное значение full не требуется: отсутствие курсора и наличие диапазона уже означает начальную загрузку.

### Следующие запросы

Клиент отправляет sync_cursor и прежний API key. Сервер проверяет ключ и сравнивает версии. Параметры диапазона, фильтры и версия формата уже связаны с курсором; изменить их через этот запрос нельзя.

Если изменений нет:

```json
{"mode":"unchanged","sync_cursor":"тот-же-курсор"}
```

Для этого ответа не нужно заново читать все метки, собирать JSON месяца и записывать snapshot_pages. Небольшая работа остаётся: авторизация, квота и чтение версий. Новый курсор и новая запись состояния при каждом пустом опросе не нужны.

Если изменения есть, ответ содержит обновления справочника и замену затронутых участков. Условный пример, не окончательный OpenAPI:

```json
{
  "mode": "delta",
  "people": {
    "upsert": [{"id":"p1","name":"Discord nick","mark":{"text":"A","background":"#123456","foreground":"#ffffff"}}],
    "remove": []
  },
  "schedule": {
    "replace": [{
      "date":"2026-11-12",
      "section_id":"nitro-50",
      "lines":[{"id":"line-1","slots":[{"start":"18:00","end":"18:30","person_id":"p1","tables":null}]}]
    }]
  },
  "has_more": false,
  "sync_cursor": "opaque-checkpoint-2"
}
```

## Почему заменять участки, а не отдельные поля

Участок — дата и вид расписания, например 12 ноября / Nitro 50. Клиент целиком заменяет только указанные участки. Остальной месяц сохраняется.

Это соответствует существующей механике сайта. Если за три минуты одну клетку несколько раз изменили, внешнему клиенту нужен результат, а не история действий. Перенос между участками обновляет оба участка.

Удаление последней метки возвращает тот же участок с `lines: []`. Это явная команда очистить старые данные. Отсутствие участка в ответе означает, что он не изменился. Эти ситуации нельзя смешивать.

Формат не является минимально возможной передачей отдельных полей, но проще в реализации, повторении запросов и восстановлении после ошибок. Для редких изменений расписания это разумный компромисс.

## Как обновлять людей

Смена имени или оформления метки должна возвращать одну обновлённую запись people, без повторной передачи слотов этого человека. Клиент обновит справочник, а отображение всех связанных слотов изменится автоматически.

Можно использовать существующую directory revision как сигнал проверки. При её изменении сервер читает разрешённую проекцию небольшого справочника и сравнивает её хеши с предыдущим состоянием. Служебный updated_at и изменение невыдаваемых полей не должны менять результат. Ложное срабатывание общей версии приведёт к проверке справочника, а не к выгрузке месяца.

Если новый слот принадлежит человеку, которого клиент ещё не знает, его запись people обязательно включается в тот же пакет. Нельзя удалить человека из справочника, пока на него ссылаются оставшиеся слоты. Правило показа старых меток заблокированного участника сохраняется.

Редкое изменение структурных настроек, несовместимое с прежними фильтрами или форматом, может потребовать полного обновления. Такие случаи должны иметь явный ответ resync_required, а не незаметно повреждать клиентский кеш.

## Что хранит сервер

В закрытой схеме — компактные контрольные состояния: клиент и поток синхронизации, диапазон, фильтры, версии участков, версии справочника и настроек, хеши публичных сведений людей, необходимые связи участников с участками. Полные копии месяца для каждого курсора не нужны.

Курсор — случайный непрозрачный идентификатор такого состояния. Он не является API key. Сервер проверяет срок, владельца и право чтения при каждом запросе. Данные не должны зависеть от памяти конкретного экземпляра Edge Function.

Хранение ограничивается сроком неактивности и квотами на потоки, состояния и байты. Предлагаемый начальный срок — 24 часа неактивности. Активный клиент не должен выполнять полную загрузку ежедневно только из-за возраста курсора. Продление срока можно объединять, не создавая новую запись каждые три минуты.

Старое состояние нельзя удалять сразу после выдачи нового: ответ может потеряться, и клиент повторит запрос со старым курсором. Неактивные состояния и временные страницы очищаются по явно заданному сроку. Конкретные квоты фиксируются в OpenAPI и миграции перед реализацией.

## Гарантии корректности

- Версии, люди и содержимое участков берутся из одного MVCC-среза базы. Сначала прочитать данные, потом более новую версию и выдать курсор нельзя: так можно пропустить правку навсегда.
- Нельзя использовать только updated_at или max(sequence_id) как границу изменений: порядок времени или выдачи ID не гарантирует порядок завершения параллельных транзакций.
- При пагинации пакет неизменяемый. page_cursor продолжает пакет, sync_cursor обозначает завершённое состояние. Финальный sync_cursor выдаётся на последней странице.
- Клиент сначала получает все страницы во временное хранилище, затем одной локальной транзакцией применяет people, заменяет участки и сохраняет новый курсор. Частичный пакет не заменяет рабочий кеш.
- Повтор безопасен: люди заменяются по ID, участки заменяются целиком. Повторная доставка не создаёт дубликатов.
- Изменения, завершившиеся после выбранного среза, попадут в следующую синхронизацию.
- Устаревшее или утраченное состояние: HTTP 410 / resync_required, затем новая полная загрузка. Отозванный ключ: 401/403; это не причина бесконечно повторять full.
- На один поток нужен один незавершённый цикл. Ошибки повторяются с задержкой, с соблюдением Retry-After. Офлайн не сдвигает курсор.

Внешнему клиенту нельзя открывать внутреннюю таблицу sync_versions или authenticated-only RPC. Нужна отдельная внешняя RPC с действующими проверками ключа, права и квоты, переиспользующая внутренние механизмы чтения.

## Ожидаемый эффект и цена

Три минуты — 480 циклов в сутки. Сейчас это потенциально 480 полных снимков плюс страницы. Предложение заменяет их начальной загрузкой, маленькими проверками и выдачей изменившихся людей и участков.

Сократятся ответы, обработка JSON и запись временных страниц. Точный выигрыш в байтах, SQL-времени и IO нужно измерять на одинаковых данных. HTTP-сжатие уже уменьшает повторяющийся текст, поэтому нельзя обещать процент экономии только по размеру несжатого JSON. Инкрементальная выдача дополнительно убирает саму работу построения полного ответа.

Цена решения: серверные контрольные состояния и новый контракт; клиенту понадобятся локальный кеш, связи по ID и атомарное применение пакетов. Для опроса раз в три минуты это обосновано. Увеличивать частоту запросов, вводить отдельную очередь событий или обязательный WebSocket для бота не требуется.

## Порядок будущих изменений

1. Согласовать OpenAPI v2, идентификаторы, состав people, правила replace/empty, сроки и квоты курсоров.
2. Добавить закрытые структуры контрольных состояний и безопасную RPC. Существующий v1 оставить рабочим.
3. Добавить новый маршрут и сериализатор Edge Function. Измерять full/delta/unchanged, байты, число изменённых участков и людей, задержки и ошибки без секретов и персональных payload.
4. Обновить клиент бота: полная загрузка, затем запрос каждые 180 секунд, сохранение данных с курсором, восстановление по 410. Без изменения клиента экономии не будет.
5. Проверить пустой месяц, добавление, удаление последней метки, перенос, смену имени/цвета, нового владельца, смену фильтров и месяца, параллельные записи, правки во время пагинации, повтор после потери ответа, истечение, отзыв ключа, большие пакеты и отсутствие данных несвязанных участников.
6. Сравнить результат с полной выгрузкой на одном срезе тестовой базы, затем согласованно переключить потребителя. Написать разработчику бота только по отдельному поручению Алексея.

Для раздельных SQL-метрик API и сайта использовать новую границу статистики после рестарта 12 ноября в 20:53:23. Время выполнения SQL не выдавать за долю CPU или RAM.

## Проверенные практики

- [Google Calendar incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync): начальная загрузка, sync token, удаления, итоговый курсор после всех страниц, восстановление при 410.
- [Microsoft Graph delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview): получение изменений по непрозрачному состоянию, разделение продолжения страниц и завершённого результата.
- [JSON:API compound documents](https://jsonapi.org/format/#document-compound-documents): отдельные связанные ресурсы со ссылками по ID. Предложенный ответ не объявляется реализацией стандарта JSON:API.

Следующий шаг — согласование. Технические документы действующего API намеренно не переписаны: они продолжают описывать опубликованный v1.

## Уточнение после обсуждения отдельных слотов

Предложение выше с заменой участков было первым вариантом для минимального изменения существующей серверной механики. После вопроса Алексея уточнён рекомендуемый внешний контракт: **v2 передаёт новые состояния отдельных адресов слотов**, а не обязательную замену целого участка. Это предложение, реализация ещё не поручена.

Причина первоначального выбора: текущая sync_versions знает дату и kind_id изменившегося участка, но не полный список изменённых адресов. Замена участка обходится без дополнительного учёта удалений и отдельных клеток. Это компромисс сложности сервера и объёма ответа, а не требование корректности.

В схеме occupancy уже есть уникальный адрес `(kind_id, slot_date, half, level)`. Во внешнем контракте ему соответствуют дата, стабильная линия и получас. ID записи occupancy для этой цели хуже: при удалении и повторном заполнении ячейки он может измениться. У пустой ячейки строки occupancy вообще нет.

Уточнённый delta: `slots.upsert` содержит адрес и полное новое состояние (person_id, tables и прочие поля слота); `slots.clear` содержит очищенные адреса. Альтернатива — один changes[] с state:null для очистки, но не смешивать два обозначения в одном контракте. Отсутствие адреса в delta означает «не менялся». Отправляется последнее состояние адреса, не последовательность всех операций.

Внутри сервера сохранить существующие версии участков и добавить компактный учёт последнего изменения адреса: адрес, версия его участка, факт удаления. При необходимости актуальное непустое содержимое читается из occupancy, без дублирования всей бизнес-записи. Для одного адреса достаточно последнего изменения; бесконечный журнал каждой правки не требуется. Изменение адреса/очистка и версия фиксируются в одной транзакции. Сравнение с вектором версий курсора и один MVCC-срез предотвращают пропуски параллельных commit. Удалённые адреса сохраняются до границы поддерживаемых курсоров; более старый курсор получает410 и full. Обслуживание и квоты такого учёта входят в оценку реализации.

Существующий occupancy_events — полезный источник для аудита, но его нельзя автоматически назначить протоколом синхронизации: сначала проверить покрытие всех UPDATE/перемещений/каскадных удалений и порядок фиксации. Время события или max ID сами по себе не являются безопасным watermark.

People остаётся отдельным разделом того же ответа, обновляется по ID. Пагинация, атомарное сохранение данных+курсора, авторизация, диапазон и восстановление сохраняются. Цена уточнения: немного больше серверной логики/данных при каждой правке; выгода — минимальная выдача отдельных клеток при регулярном опросе. Для текущей редкой записи и регулярного чтения это обоснованный вариант, хотя точный выигрыш должен измеряться.

Версия выбирается маршрутом `/v2/...`, а не секретным содержимым ключа. v1 и его ключи остаются рабочими. Для тестовой/новой интеграции рекомендуется отдельный ключ с независимым отзывом; сам новый ключ не создаёт поддержку v2, сначала требуется реализация и публикация нового контракта. Ключи/права в этом обсуждении не создавались и не изменялись.

## Оценка предложения о постоянно готовом серверном ответе

Алексей предложил отдельный промежуточный сервис: держать готовый месяц и изменения, обновлять его при записи, выдавать full/delta без обращения к основной базе каждые три минуты. Это известный read-model/materialized-view подход; не плохая идея сама по себе.

Оценка для текущей нагрузки: отдельный постоянно работающий сервис и внешнее хранилище сейчас не рекомендуются. Нет доказательства, что дешёвая индексная проверка версий раз в180секунд является узким местом. Наблюдавшаяся тяжёлая работа — создание полного снимка, JSON и запись страниц; v2 delta устраняет её при отсутствии изменений. При нескольких потребителях, частом full или подтверждённом дорогом чтении общая проекция может стать оправданной.

Риски отдельного слоя: новая точка отказа, согласованность при потере подписки, восстановление после перезапуска, контроль отзыва ключа, дополнительная стоимость/RAM, перенос исходящего трафика между Supabase и сервисом, а не исчезновение трафика. Память Edge Function не годится как единственное надёжное хранилище: изоляты имеют раздельную память и ограниченный срок жизни. Обновление проекции только из Broadcast без надёжного восстановления может пропустить данные. Транзакционный учёт изменений в базе всё равно нужен.

Рекомендуемая последовательность остаётся: v2 с отдельными людьми, состояниями изменённых адресов и курсором; небольшая проверка версий/изменений в той же базе, без построения полного месяца. Подготовленную full-выдачу кешировать по версии и фильтрам только если измерения покажут повторные одинаковые full-запросы: один раз собрать, переиспользовать, при изменении пометить устаревшей и пересобрать по потребности. Не вводить постоянный процесс только ради первоначальной выгрузки, которая после delta будет редкой. Такой кеш не заменяет авторизацию и durable delta. Это предложение, не согласованная реализация.

## Согласовано Алексеем: full без курсора, delta последних состояний

12.11.2026. Прямое подтверждение пользователя: первый запрос получает весь месяц; дальше клиент обновляется с курсором; сервер агрегирует изменения так, чтобы передавать только последнее состояние слота. People остаётся отдельным разделом. Это заменяет первоначальную рекомендацию обязательной передачи целых участков во внешнем контракте.

Под «агрегацией логов» понимается отдельный компактный учёт последнего изменения адреса клетки для API, не удаление или изменение существующего аудита occupancy_events. Каждый адрес содержит последнюю версию и признак очистки; актуальное непустое состояние можно читать из occupancy. По запросу с курсором выбираются адреса новее согласованной границы и возвращаются их последние состояния. Не удалять запись после выдачи одному клиенту: у остальных могут быть старые курсоры. Маркеры очистки и минимальная поддерживаемая граница хранятся согласованно; утратившие покрытие курсоры получают410/resync_required. Нельзя просто дедуплицировать журнал и продолжать по максимальному ID без учёта порядка commit.

Без курсора требуется полный явно выбранный месяц. Действительный курсор фиксирует этот диапазон/фильтры и клиента. Новый месяц/фильтры — новый full. Данные и новый курсор клиент сохраняет атомарно. Новый курсор выдаётся после всех страниц согласованного пакета. Реализация, деплой и создание ключей этим подтверждением ещё не выполнены; следующий этап — конкретная спецификация и реализация по поручению пользователя.
