### Основание финального предложения

Прямое уточнение Алексея: 90–95% времени — пассивный просмотр плановых смен покеристов, иногда сутки; заполнение обычно последовательное, пересечения возможны. Это продуктовый сценарий, не измеренная серверная статистика. Постоянная подписка нужна независимо от активности мыши.

Повторная проверка кода подтвердила отдельные Postgres Changes-подписки нескольких загрузчиков на schedule_settings и таймеры оформления; персональные параметры вида в prefs уже локальные. Общие настройки предлагается читать одним разрешённым пакетом, держать в памяти аккаунта и обновлять по Broadcast; права/закрытый профиль не смешивать с публичным оформлением. Сетка, конфигурация, справочник и приоритеты получают отдельные версии/события через единый слой загрузки; контроль одним запросом раз в5минут, только нужные разделы. Нормальные события обрабатываются сразу; версии изменяются транзакционно, снимок согласован с версией.

Сохраняем ручную галку редактирования и транзакционный apply_schedule_edit; проверяем конфликт всех типов записи и неопределённый ответ/повтор перед снятием 60-секундного срока и обязательности WebSocket. Не нужны блокировка всей таблицы или новый сервер синхронизации. Прежнее предложение сохранять расширенный Онлайн заменено прямым уточнением Алексея ниже.

### Прямое уточнение Алексея 13:53 — убрать необязательную нагрузку

- Онлайн: достаточно ников пользователей, подключённых к сервису/обновлениям. Историю активности, недавно ушедших, время и вид последних правок убрать из этого интерфейса; не читать логи ради обогащения списка. Это разрешение упростить функциональность, не удалять накопленные таблицы или аудит.
- Предложенный механизм — стандартный Supabase Presence на существующем клиенте Realtime, по возможности в общем авторизованном канале. Клиент один раз публикует минимальное состояние из уже загруженного профиля; sync/join/leave обновляют локальный список без периодических SQL ping/list. Пользователь с несколькими соединениями отображается один раз; исчезает после закрытия последнего соединения и обнаружения разрыва сервером. Список означает подключение, а не внимание человека или фактическую игру. Presence не используется как источник прав доступа. Если сама вкладка потеряла связь, её список больше не выдаётся за текущий.
- Настройки: Алексей допускает обновление только после reload для малозначимого оформления, если это заметно упрощает систему. Предпочтительный вариант остаётся начальная загрузка + событие существующего канала + одно чтение изменившегося пакета; самостоятельные периодические запросы настроек убрать. Правила/права сервер всегда проверяет при записи независимо от кеша оформления.
- Индикатор: показывать состояние подписки из SDK (подключено/подключаемся/связь потеряна), без отдельного SQL-запроса проверки. Название «Обновления подключены» точнее абсолютного «Актуально». Известный сбой чтения и восстановление данных после reconnect отражаются событиями уже выполняемых операций; зелёный сокет сам по себе не доказывает завершённую сверку данных. Отдельные частые опросы ради цвета не нужны.
- Общая редкая страховка данных раз в5минут остаётся предложением предыдущего этапа; она не нужна для Presence/индикатора и не дублируется отдельными таймерами настроек. Обычные изменения приходят по Broadcast.
