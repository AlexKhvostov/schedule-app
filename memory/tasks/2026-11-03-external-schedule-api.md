## Цель и критерий готовности

Подытожить требования Алексея к выдаче расписания внешнему боту по отдельному ключу, проверить текущую модель данных и предложить архитектуру, параметры запроса и JSON. Готовность: рекомендации сопоставлены с кодом, пограничные случаи описаны, подтверждённые требования отделены от предложений.

| Подзадача | Статус | Критерий завершения | Результат / препятствие |
|---|---|---|---|
| Проверка текущего хранения, времени, линий и владельцев | Готово | Прочитаны тематические документы, актуальные миграции и чтение расписания | Источники приведены ниже; облачная схема не проверялась |
| Контракт и архитектура | Готово | Запрос, JSON, ключи, фильтры, границы дат и источник данных определены как предложение | Проект ниже; предложения ещё не утверждены |
| Сверка и передача | Готово | Проверены примеры и ссылки, сохранён итог и нерешённые вопросы | Node: JSON, 3 дня, число слотов, строковый Discord ID, Madrid/UTC и локальные ссылки прошли |

## Подтверждено пользователем

- Потребитель — внешний бот; отдельный ключ, без входа через Discord.
- Обязательны начальная дата и количество дней, включая начальный день: 3 = сегодня, завтра, послезавтра.
- Необязательные фильтры: лимит и вид турнира; отсутствие фильтра означает все значения.
- Ответ JSON содержит установленные метки, дни, линии, время и данные владельца, включая Discord ID и ники.
- Код API нужно отделить в собственный каталог. Предварительная месячная таблица обсуждается как вариант, а не требование.

## Границы

Только исследование и проектирование. Код приложения, схема, ключи, доступы и облачные настройки не меняются. Существующие незавершённые изменения сохранены.

## Что подтверждено локальным кодом

- [Базовая схема](../../supabase/migrations/20260919100000_mvp_spine.sql): `occupancy` хранит владельца, `kind_id`, календарную дату, `half` 0–47 и `level` 0–5. У линии нет отдельной сохранённой сущности с названием; подпись строится из вида, лимита и номера.
- [Текущая месячная RPC](../../supabase/migrations/20260924190000_load_month_schedule.sql): собирает метки и текущие ники соединением таблиц, проверяет пользовательские права. Её нельзя просто открыть боту или снять проверку Discord-прав.
- [Клиент чтения](../../apps/web/src/data/slots.ts) и [архитектура](../../docs/code-architecture.md): Nitro и Regular читаются отдельно, сохранённой полной месячной сетки нет.
- [Часовой пояс](../../apps/web/src/schedule/cet.ts): Europe/Madrid, сетка всегда 48 получасов; точный UTC-момент в записи отсутствует.
- [Справочник игроков](../../supabase/migrations/20261001090000_schedule_directory_profile_name.sql): Discord ID связан через `identities`; профильное имя отдельно от Discord; игровой ник — последний по истории. Справочник фильтрует активных игроков, поэтому не годится в качестве исходного набора для всех уже стоящих меток.
- [Модель данных](../../docs/database.md): метка и ники текущие, столы в `occupancy.tables` — снимок постановки. Скрытие/объединение ячеек на экране не меняет хранимые записи.
- [Лимиты и подписи](../../apps/web/src/schedule/capacity.ts): лимиты — строковые ID, в том числе `0.25`, `0.50`; подписи N для Nitro, E для Regular, максимум шесть уровней.
- [Конфигурация API базы](../../supabase/config.toml) содержит `max_rows = 1000`: обычная табличная выдача может обрезать большой диапазон. Новый контракт должен гарантировать полноту отдельно.

## Предлагаемый контракт v1

Один GET-метод. Один день — `days=1`; отдельный метод для одного дня не требуется. Бот опрашивает сервер, push-уведомления сюда не входят.

Предлагаемый прямой адрес: `https://<project-ref>.supabase.co/functions/v1/schedule-api/v1/schedule`.
Пример запроса (относительный путь после домена):

```http
GET /functions/v1/schedule-api/v1/schedule?date=2026-11-03&days=3&limit=50&variant=nitro
X-API-Key: <индивидуальный ключ бота>
```

| Параметр | Правило |
|---|---|
| `date` | Обязателен, настоящая дата `YYYY-MM-DD`, календарь Europe/Madrid. Бот сам определяет «сегодня» в этом поясе; относительное `today` в v1 не нужно |
| `days` | Обязателен, целое 1–31; 31 — предлагаемое ограничение, не требование пользователя |
| `limit` | Необязателен, точный строковый ID игрового лимита; отсутствие означает все лимиты. Это не число возвращаемых строк |
| `variant` | Необязателен, `nitro` или `regular`; отсутствие означает оба вида |

Диапазон `[date, date + days)`, последняя включённая дата `date + days - 1`. Переход месяца, года и високосный февраль поддерживаются. Неверные/пустые значения и неизвестные или повторяющиеся параметры → 400; никаких незаметных значений по умолчанию. Валидные фильтры сочетаются через И. Известная комбинация без записей → 200 с пустыми днями; неизвестный лимит/вид → 400. Не задавать произвольные фильтры SQL: новые поля добавлять явно в контракт.

Для v1 рум фиксирован Winamax и явно возвращается в данных. Фильтры по владельцу, нескольким лимитам и другим румам можно добавить по реальной потребности бота.

Группировка: `days[] → lines[] → slots[]`. Линия определяется `(kind_id, level)`; ID стабилен, отображаемое имя не используется как ключ. `number = level + 1`. В ответе все запрошенные дни, включая пустые; линии только с установленными метками. Полная сетка свободных мест — отдельная будущая возможность, так как требует правил вместимости, а пользователь запросил стоящие метки.

Каждая метка — отдельный получас, даже если на экране несколько объединены. `half` остаётся точной координатой сетки. Конец интервала не включён; у получаса 47 конец — 00:00 следующей даты. Сортировка: дата, Nitro/Regular, порядок лимита из справочника, номер линии, half, ID записи.

### Время и перевод часов

Календарь Europe/Madrid — предлагаемый канон API, совпадающий с текущим приложением, не фиксированное UTC+1. Существующая модель `date + half` не различает два одинаковых получаса при осеннем переводе часов и допускает несуществующие весенние часы. Это ограничение модели, а не повод молча выбрать UTC.

Предложение v1: координаты сетки и локальные границы возвращать всегда; UTC-границы — только когда обе определяются однозначно и интервал сохраняет 30 минут. В иных случаях обе UTC-границы null, `time_resolution = ambiguous | nonexistent | transition`. Ничего не удалять из ответа и не переносить на соседний час. Боту запрещено планировать точное срабатывание по null. Если нужны гарантированные уведомления именно в этот час, до такого запуска отдельно согласовать правило первого/второго повторения либо расширить хранение UTC/fold. Это ещё не принятое продуктовое решение.

## Предлагаемая архитектура

`Внешний бот → HTTPS + ключ → schedule-api (Edge Function) → закрытая RPC чтения → существующие таблицы → JSON`.

Отдельная Supabase Edge Function подходит к существующему расположению интеграций и не связывает бот с публикациями интерфейса Next.js. Альтернатива — Next route `/api/v1/schedule`; она удобна для адреса redparty.ru, но связана с деплоем сайта. Два обработчика параллельно не нужны. Доменный proxy можно добавить позднее, сохранив одну реализацию.

Предлагаемое размещение (каталоги кода сейчас не создаются):

```text
supabase/functions/schedule-api/
  index.ts        # HTTP, метод, ошибки, обязательная проверка ключа
  auth.ts         # проверка индивидуальных ключей и прав интеграции
  query.ts        # дата, дни, фильтры
  repository.ts   # вызов одной закрытой RPC
  response.ts     # стабильный JSON
  contract.ts     # типы v1
  README.md       # подключение и примеры для разработчика бота
supabase/migrations/<timestamp>_external_schedule_api.sql
supabase/tests/external_schedule_api.sql
```

Миграции остаются в стандартном каталоге Supabase, а не перемещаются рядом с HTTP-кодом. SQL и HTTP проверяют ключ/права согласованно; существующие пользовательские RPC и Discord-вход не ослабляются. Чтение возвращает согласованный срез одной SQL-командой с ограниченным диапазоном, без циклов загрузки каждого владельца и без зависимости от React.

На старте не создавать сохранённую месячную таблицу. Диапазон может пересекать месяцы, метки и ники меняются; новая копия потребует инвалидации по всем таким изменениям. Уже есть индекс `(kind_id, slot_date)`; планы чтения без фильтра проверить на реалистичном объёме, индекс по дате добавлять по результату. Кеш вводить только после измерений, с явной свежестью, изоляцией прав и инвалидацией; первоначально `Cache-Control: no-store`.

Полнота: закрытая RPC возвращает один JSON-агрегат, а не табличный набор, обрезаемый `max_rows`; сортировка детерминирована. Проверить ответы >1000 меток и максимальный допустимый диапазон на размер/таймаут. Не отдавать частичный ответ как успешный: если платформа не вмещает всё, явно отказать `response_too_large` с предложением меньшего days. Пагинация только как явно согласованное расширение; для v1 не вводить молчаливый предел числа меток.

## Доступ и эксплуатация — предложения

- Индивидуальный случайный ключ на интеграцию, право только `schedule:read`, вся сетка текущего клуба. Нельзя использовать ключ проекта Supabase/service_role в качестве ключа внешнего бота.
- Ключ передаётся только HTTPS-заголовком `X-API-Key`, не query-параметром. В защищённом реестре — ID/префикс, SHA-256 высокоэнтропийного секрета, права, срок, отзыв; сырой ключ показывается при выпуске один раз. Показ/выдача ключей и изменение доступа — отдельный этап, сейчас не выполняются.
- Реестр ключей в закрытой схеме без Data API; доступ из браузера исключён. В RPC явно отозвать EXECUTE у PUBLIC/anon/authenticated, разрешить только внутреннему серверу; не полагаться лишь на сокрытие URL. Серверный привилегированный секрет остаётся в среде функции. Если необходим SECURITY DEFINER — минимальная функция, закреплённый search_path и явные grants, никаких динамических произвольных SQL от клиента.
- Для этой функции с собственным ключом нужен отдельный `verify_jwt = false` и обязательная собственная проверка ДО чтения расписания. Это не настройка для других функций. Отсутствующий, неверный, истёкший или отозванный ключ всегда получает 401.
- Ограничение частоты по интеграции в общем серверном хранилище, а не в памяти одного serverless-процесса; предварительный предел 60 запросов/мин, окончательно выбрать по частоте опроса. Отдельно ограничить неуспешные попытки. 429 с Retry-After, таймауты, ограничение размера ответа.
- Ошибки: 400 validation_error, 401 invalid_api_key, 403 insufficient_scope, 405 method_not_allowed, 429 rate_limited, 503 schedule_unavailable. Пустой день только при успешном чтении; сбой базы не маскируется под пустое расписание. Точный HTTP-код response_too_large согласовать в окончательной OpenAPI-схеме.
- Журнал: request_id, ID интеграции, диапазон, число записей, время и итоговый статус. Не писать ключи и полные персональные ответы. Раздельные ключи Working и будущего Production.
- Интеграция не обращается к Discord при каждом запросе: ники берутся из существующего локального снимка; их свежесть зависит от синхронизации Discord. `generated_at` — время сборки ответа, а не доказательство свежего обращения в Discord.

Технические источники проверены 03.11.2026: [защита Edge Functions](https://supabase.com/docs/guides/functions/auth), [платформенная проверка заголовков](https://supabase.com/docs/guides/functions/auth-headers), [ключи Supabase и их полномочия](https://supabase.com/docs/guides/getting-started/api-keys), [changelog](https://supabase.com/changelog). Markdown-индекс changelog не прочитался web-инструментом из-за Content-Type; проверена HTML-версия. Сторонних SDK не добавлено.

## Приёмка будущей реализации

1. date + days: 1/3/31, границы месяцев/лет, високосный февраль; даты и числа с ошибками отклоняются.
2. Все четыре сочетания отсутствия/наличия фильтров; Nitro/Regular и одинаковые лимиты не смешиваются; дробный лимит сохраняет точный ID.
3. Пустые дни и несколько линий; соответствие каждой строки occupancy ровно одной метке, включая скрытые UI-часами и отключённые ныне лимиты.
4. Discord ID без округления, отсутствующие ники null, владелец отдельно от автора постановки; текущие имена без ложной историчности.
5. Получасы, полночь, переходы DST, текущая метка/цвет и сохранённые столы. Одинаковый ответ при одинаковых данных независимо от настроек браузера.
6. Нет ключа/неверный/отозванный/истёкший ключ, чужие права, запрещённые прямые RPC; отсутствие секретов в логах.
7. Ответ >1000 записей, максимальный диапазон, одновременное редактирование, ошибка базы и ограничение частоты. Полнота либо явная ошибка, никогда скрытая обрезка.
8. Интеграционный тест внешнего GET с тестовым ключом, SQL security contracts, Supabase reset/lint; все обязательные проверки репозитория при реализации. UI E2E для нового экрана только если такой экран войдёт в объём.

## Итог и следующий шаг

Проверка примера выполнена через Node/Intl; первая попытка через Python не завершилась из-за отсутствия tzdata, пакеты не устанавливались. Проверки приложения/БД не запускались: код и схема не изменены, работающий endpoint не создан. Проверенные данные об устройстве приложения — локальный код и миграции на 03.11.2026, не повторная сверка опубликованной схемы.

Требования Алексея записаны; конкретная платформа, названия параметров, границы 31 день/60 запросов, поведение DST и поля JSON — предложения агента, не утверждённая реализация. Следующее действие — уточнить контракт по обратной связи Алексея; затем отдельным поручением реализовать API и выпуск ключа. Практически важны нужный боту пояс, необходимость точных уведомлений во время DST и ожидаемая частота опроса. Для проектирования принят пояс текущего расписания.

Рабочие docs/current-state.md и docs/decisions.md не меняются: ни реализованное состояние, ни утверждённая архитектура этим исследованием не изменены. Проект предложения сохранён здесь, ссылка добавляется в индекс документации и память.
