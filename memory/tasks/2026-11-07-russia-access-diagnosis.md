## Как проверить исправление на Билайне в 18:33 Europe/Minsk

Vercel показывает `Valid Configuration` и `Production` для обоих адресов. Обе DNS-службы Hostland возвращают для `redparty.ru` IP `216.198.79.1`. Сейчас `www.redparty.ru` указывает на Hostland и не проходит проверку HTTPS из текущей сети. `dashboard.redparty.ru` также указывает на Hostland и отвечает по HTTPS. Для теста альтернативного размещения подойдёт отдельная DNS-запись, например `check.redparty.ru`. Менять запись `@` следует только после успешного теста и с возвратом на `216.198.79.1` при сбое.

С текущего подключения полный CSS (320 814 байт без сжатия) и JavaScript (179 638 байт) скачались на обоих адресах через IP `216.198.79.1` и `216.198.79.195`. Это проверка доступности двух направлений для сравнительного теста. Публичная DNS-запись может использовать только значение, рекомендованное Vercel для конкретного домена. [Инструкция Vercel](https://vercel.com/docs/domains/set-up-custom-domain).

Когда сбой повторится, участник может открыть Windows PowerShell на подключении Билайна, вставить весь блок и отправить четыре строки результата. Запрос скачивает открытый файл оформления, обходит выбор адреса через DNS только в рамках команды, проверяет сертификат и выводит код HTTP, объём полученных данных и код завершения curl. Путь файла соответствует выпуску на момент замера. Если все четыре запроса дают 404, нужно обновить путь из актуальной главной страницы.

```powershell
$asset = '/_next/static/css/e31287a714e503ed.css'
$siteNames = 'redparty.ru', 'schedule-app-omega-five.vercel.app'
$edgeAddresses = '216.198.79.1', '216.198.79.195'
foreach ($siteName in $siteNames) {
    foreach ($edgeAddress in $edgeAddresses) {
        $result = curl.exe --silent --show-error --fail --max-time 12 --resolve "${siteName}:443:${edgeAddress}" --output NUL --write-out 'HTTP %{http_code}, %{size_download} bytes, %{time_total} s' "https://${siteName}${asset}"
        $exitCode = $LASTEXITCODE
        "$siteName via ${edgeAddress}: $result, curl exit $exitCode"
    }
}
```

| Что покажет проверка | Следующее действие |
| --- | --- |
| `redparty.ru` стабильно загружает файл через второй IP и зависает через первый | Попросить Vercel подтвердить поддерживаемый IP для основного домена. При получении адреса проверить его на Билайне, затем заменить только A-запись `@` в Hostland и перепроверить полный вход и расписание. |
| При одинаковом IP основной адрес зависает, резервный загружает файл | Сохранить время и результат для Vercel Community. Попросить проверить доставку статики по имени домена. Если нужен управляемый обход, испытать отдельное размещение веб-приложения на тестовом поддомене и проверить полную работу из сети участника. |
| Четыре загрузки проходят, браузер продолжает висеть | Записать вкладку «Сеть» при обновлении проблемной страницы. Сохранить первый зависший запрос, его статус, `x-vercel-id`, если ответ успел прийти, и время. |

Проверка пилота перед переносом корневого адреса включает HTTPS, открытие страницы в новой сессии, вход через Discord с возвратом на тестовый адрес и загрузку расписания на Билайне. Для тестового адреса понадобится разрешить точный `/auth/callback` в Supabase. Отдельное размещение приложения можно проверить с текущим сервисом входа и данными. ## 7 ноября 2026, 19:15 Europe/Minsk — оценка сложности входа

По вопросу Алексея проверен текущий код, без изменения авторизации. В loadLiveEntry посетитель без сохранённой сессии выходит из проверки после getSession, без getUser/профиля/Discord. При восстановлении Discord-сессии типовой путь: getUser → два параллельных запроса слепка/настроек → member → identity → member_access_context → Discord-имя из БД. Это до 7 сетевых запросов в 6 последовательных этапах, не считая возможного обновления токена и последующей загрузки расписания. Прямой Discord API вызывается только после нового OAuth-входа; обычное восстановление читает Supabase. App ждёт завершения этой цепочки до выхода из boot; общий дедлайн 15 с, далее показ недоступности и повторы. Секунды реальной загрузки в этой проверке не измерялись: выявлена структура возможной задержки, а не её измеренный вклад.

В layout глобально импортированы весь Font Awesome и четыре семейства шрифтов; V2Login/V2Shell уже отложены через React.lazy. Поэтому предложение — облегчить критические CSS/шрифты и самостоятельный стартовый экран, объединить чтение профиля/прав серверной функцией и/или распараллелить независимые чтения с сохранением проверок доступа. Это предложение, не реализованное изменение. Оптимизация входа не исправляет подтверждённую остановку CSS на Билайне. Подготовленный assetPrefix остаётся непубликованным вариантом изменения доставки. Использованы Supabase (проверка схемы Auth) и session-memory (сохранение вывода).
