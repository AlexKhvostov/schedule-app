# RedParty External API

Локальная реализация от 3 ноября 2026. В облако не опубликована. Общая точка входа внешних
интеграций; расписание — первый ресурс. Формальный контракт: [openapi.json](openapi.json). Готовая
инструкция для стороннего разработчика: [BOT-CONNECTION.md](BOT-CONNECTION.md); она не содержит
ключей.

```text
external-api/
  index.ts                 запуск Supabase Edge Function
  app.ts                   маршруты, HTTP, ошибки, безопасный журнал
  core/                    общие ключи, ошибки, доступ к RPC
  v1/schedule/             параметры, типы, время, JSON расписания
  tests/                   unit- и HTTP-контракты без сети
  integration/             тесты настоящего локального HTTP
  tools/                   генерация ключа, подготовка тестовых данных
```

Новый ресурс добавляется своим модулем `v1/<resource>` и явным маршрутом в `app.ts`, со своим правом
в закрытом реестре ключей. Нельзя добавлять endpoint произвольного чтения таблиц. Общий API не
зависит от React; доменная база расписания остаётся прежней.

## Запрос

```http
GET /functions/v1/external-api/v1/schedule?date=2026-11-03&days=3&limit=50&variant=nitro
X-API-Key: rp_<64 шестнадцатеричных символа>
```

- `date`: обязательная настоящая дата YYYY-MM-DD в Europe/Madrid. Поддерживаются четырёхзначные годы
  1000–9999, исключительная граница диапазона также должна помещаться в 9999 год.
- `days`: обязательное целое 1–31. Начальный день включён: 3 ноября +3 дня = 3–5 ноября. Переход
  месяца/года поддержан.
- `limit`: точный строковый ID лимита, включая `0.25` и `0.50`. Отсутствует — все лимиты.
- `variant`: `nitro` или `regular`. Отсутствует — оба вида.
- Неизвестные/повторяющиеся параметры, пустые фильтры и несуществующие значения — 400. Фильтры
  пересекаются, рум v1 — Winamax. Клиент самостоятельно вычисляет «сегодня» в Europe/Madrid.

Ответ: `days[] → lines[] → slots[]`. Все даты присутствуют, пустые дни содержат `lines: []`. Пустые
линии/ячейки не возвращаются. Линия содержит ID `kind_id:level`, имя `N50 · 1`/`E50 · 1`, номер с1,
вид, лимит, рум и валюту. Получас остаётся отдельной записью даже при визуальном объединении на
сайте. `half` от0 до47 соответствует сохранённой ячейке; конец интервала не включён.

Владелец — участник из occupancy, а не автор постановки. ID Discord — строка. Буквы/цвета/ники
текущие и для прошлых дат; `game_nick` берётся из последней записи истории Winamax. Discord-поля
берутся из существующего снимка, без запроса к Discord на каждый GET. Отсутствующие сведения — null.
`tables` — снимок постановки при включённой клубной функции, иначе null. Контакты, платёжные данные,
auth IDs и секреты не выдаются. Заблокированный участник или отключённый лимит не скрывают уже
сохранённую метку.

`generated_at` обозначает создание снимка БД, не свежесть Discord-синхронизации. Нет постоянного
кеша месяца; HTTP `Cache-Control: no-store`.

## Страницы и единый снимок

Первый запрос с date/days создаёт неизменный снимок на15 минут: состав записей, метки, ники и
настройка столов фиксируются одним SQL `INSERT/SELECT`. Снимок хранится в закрытой схеме и разбит
по1000 меток; последний пакет может быть меньше. Пустая выгрузка — одна страница с0 меток.

Ответ содержит `pagination`: `snapshot_id`, `expires_at`, `page_size=1000`, `page_number`,
`total_pages`, `total_slots`, текущий `cursor`, `has_more`, `next_cursor`. `slots_count` относится
только к текущей странице. Прежнее неопубликованное поле `complete` удалено: окончание цепочки
определяется `has_more=false` и `next_cursor=null`.

Продолжение: GET на тот же endpoint с **единственным** query-параметром `cursor=<next_cursor>` и
прежним `X-API-Key`. Параметры даты/фильтров повторять нельзя — сервер берёт их из снимка. Каждый
ответ сохраняет исходные `generated_at`, параметры и срок. ID cursor — непрозрачное случайное
значение; подменять/вычислять его клиенту не нужно. Cursor не заменяет ключ: каждый вызов проверяет
срок/отзыв/право/квоту, а снимок привязан к конкретному клиенту. Другой ключ не прочитает страницы.

Каждая страница по-прежнему содержит все даты диапазона. Накапливайте `days` по дате, `lines` поID,
`slots` поID; пустая линия/день означает отсутствие записей только на этой странице. Один день и
линия могут продолжаться дальше. Повтор того же cursor возвращает ту же страницу до истечения срока.
Новый запрос с date/days создаёт свежий снимок. При410 отбросьте частичный результат и начните
заново; страницы разных снимков смешивать нельзя.

`external_api_private.snapshots` хранит параметры/срок/объём, `snapshot_pages` — зафиксированные
данные и курсоры. Cron удаляет истёкшие снимки вместе со страницами каждые5 минут; проверка времени
запрещает чтение сразу после истечения, независимо от очистки. Это временный артефакт выгрузки, а не
второй источник расписания. Удаление/постановка меток и смена ников во время загрузки не меняют уже
созданный снимок.

## Время и ограничения

Канонический пояс — Europe/Madrid, шаг30 минут. `start_local`/`end_local` — границы ячейки местного
календаря; `start_at`/`end_at` — UTC. При неоднозначном/несуществующем местном времени или интервале
перехода DST обе UTC-границы равны null, а `time_resolution` — `ambiguous`, `nonexistent` или
`transition`. Для обычного получаса — `exact`. Клиент не должен планировать точное уведомление по
null; исходная модель не хранит первое/второе повторение часа.

Ограничение10000 меток прежнего прототипа заменено пагинацией. Защитные пределы:250000 меток/128 MiB
сырого JSON на снимок;4 MiB на сохранённую страницу и5 MiB на итоговый HTTP-ответ. При превышении
—422 `response_too_large`, без частичного снимка/обрезанной успешной выдачи. Обычно страница1000
меток значительно меньше. `max_rows=1000` PostgREST не обрезает данные: RPC возвращает один
JSON-объект страницы.

У одного ключа может быть не более30 одновременно живых снимков и256 MiB их суммарных данных.
Превышение даёт429 `snapshot_limit` с `Retry-After`; уже созданные страницы доступны по-прежнему с
учётом обычной квоты запросов. Эти пределы ограничивают накопление забытых выгрузок; TTL не
продлевается чтением. Для регулярно опрашиваемого бота запрашивайте нужный диапазон, а не
новый31-дневный снимок для каждой страницы.

По умолчанию ключу разрешено60 запросов за календарную минуту; общая квота хранится атомарно в БД и
работает между экземплярами функции. Неизвестные/отозванные/просроченные корректно сформированные
ключи имеют общий лимит300 попыток/мин; он не блокирует действующие ключи. Пустой/неправильный по
форме ключ отсекается до БД; это не полноценная защита от сетевого DDoS. 429 содержит `Retry-After`.

Ошибки:400 `validation_error` (поле в `field`),401 `invalid_api_key`,403 `insufficient_scope`,404
`not_found`,405 `method_not_allowed`,410 `snapshot_unavailable`,422 `response_too_large`,429
`rate_limited`/`snapshot_limit`,503 `schedule_unavailable`. Текст ошибок — стабильные машинные коды,
бот получает их без локализации. Все ошибки включают `request_id`; внутренние SQL/секреты не
раскрываются.

## Локальный запуск

Нужны Docker, Supabase CLI и для тестов Deno2.9.6. PowerShell7 открывайте в корне репозитория.
Команды ниже обращаются только к локальному Supabase. `db reset` в существующей среде удаляет её
локальные данные: для проверки используйте новую временную копию `supabase/` с отдельным
`project_id` и свободными портами, как описано в
[отчёте реализации](../../../memory/tasks/2026-11-03-external-api-implementation.md).

1. В подготовленной локальной копии запустите `supabase start`. Новая база применит миграции и seed,
   включая `20261103160348_external_api.sql`, `20261103165923_external_api_snapshot_pages.sql` и
   `20261103173923_external_api_root_admin.sql`.
2. Выполните `supabase functions serve external-api`. Параметр `verify_jwt=false` задан только для
   этой функции в config.toml; собственный ключ проверяется приложением и RPC. Не отключайте
   проверку JWT глобально для других функций.
3. В отдельном терминале перейдите в `supabase/functions/external-api` и выполните `deno task key`.
   Команда работает офлайн, показывает случайный ключ и его SHA-256. Ключ сохраните у бота, в БД
   нужен только SHA-256. Не публикуйте вывод в git/логах.
4. Подключившись к локальной БД как postgres, создайте интеграцию (подставьте SHA-256, а не сырой
   ключ):

```sql
insert into external_api_private.clients(name,key_hash,scopes,expires_at)
values ('local-bot','<SHA-256>',array['schedule:read'],now()+interval '30 days');
```

5. В PowerShell запросите расписание; сначала сохраните ключ в переменную окружения `RP_API_KEY`
   безопасным для вашей среды способом:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:54321/functions/v1/external-api/v1/schedule?date=2026-11-03&days=3' -Headers @{ 'X-API-Key' = $env:RP_API_KEY }
```

Если получен пустой список — в новой базе ещё нет меток. Не подменяйте её облачной базой для
наполнения тестов. Для тестового набора используйте процедуру ниже.

Для отзыва локального ключа:

```sql
update external_api_private.clients set revoked_at=now() where id='<ID интеграции>';
```

Для замены выпустите новый ключ/строку и отзовите старый. Эти SQL-команды — запасной способ для
локальной проверки без Discord-входа. Основное управление владельцем доступно в Root → API через
защищённую RPC; внешние боты не могут управлять ключами. В облаке эти действия требуют отдельного
поручения. Сервер использует `SUPABASE_SERVICE_ROLE_KEY`, предоставленный локальным runtime; для
отдельного серверного секрета поддерживается `EXTERNAL_API_SERVER_KEY`. Внешнему боту эти
привилегированные ключи не передаются.

## Ключ для внешнего разработчика: действия владельца

Ключ не нужно придумывать человеку. `deno task key` использует криптографический генератор случайных
чисел:32 случайных байта, представленных строкой `rp_…`. Утилита показывает два значения: `key` —
сам секрет, который нужен боту; `sha256` — отпечаток для регистрации в нашей закрытой таблице. По
отпечатку восстановить исходный случайный ключ практически невозможно; передавать разработчику
только sha256 бесполезно.

Порядок выдачи при отдельном поручении на подключение:

1. Назвать интеграцию, например `tournament-helper-bot`, и среду. Для каждого бота/среды — свой
   ключ, чтобы отзывать независимо.
2. Открыть меню Админ → Root → API (`#root-api`), нажать «Создать ключ». Заполнить название, контакт
   разработчика, примечание, срок (30/90/365 дней или без срока) и квоту1–600 запросов/мин (по
   умолчанию60). Право фиксировано: `schedule:read`. Браузер создаёт256-битный секрет через Web
   Crypto, RPC получает только SHA-256. Ключ показывается только после успешной регистрации и только
   один раз. При сетевой ошибке повтор использует тот же ID/хеш, без дубликата. Офлайн-утилита
   остаётся дополнительным способом для разработчика.
3. Сам ключ сохранить владельцу в менеджере паролей, вместе с названием бота, разработчиком, средой,
   ID записи и сроком. В исходном коде/Markdown/общих таблицах его не хранить. В БД сохранять только
   sha256.
4. Передать разработчику [инструкцию](BOT-CONNECTION.md), окончательный URL и срок доступа. Сам ключ
   передать отдельно лично через согласованный защищённый канал, предпочтительно средствами
   безопасной передачи секрета; не в общем чате, публичной задаче или репозитории.
5. Разработчик сохраняет секрет в настройках сервера/Secrets хостинга бота (`RP_API_KEY`) и
   отправляет в `X-API-Key` каждого запроса. Это даёт доступ к расписанию, включая разрешённые имена
   и Discord ID; передавать такой ключ следует только доверенному получателю.
6. При утечке/смене разработчика отозвать старый ключ. При потере ключа выпустить новый: извлечь его
   из сохранённого отпечатка нельзя. Замена ключа требует начать новые снимки.

Разработчику **не нужны** доступ к Supabase Dashboard, пароль базы, service-role/secret key проекта,
Discord-токен или аккаунт владельца. URL не является секретом; одного URL недостаточно. Пока API не
опубликован, доступ внешнему боту в интернете не открыт и реальный ключ ему не выдан.

## Экран Root → API

Экран находится в `apps/web/src/v2/api`, запросы — в `src/data/externalApi.ts`. В root-меню он
отдельный от настроек Discord/Telegram. Карточки показывают бота, контакт, заметку, статус,
создание/срок с часовым поясом и квоту. Изменение квоты/метаданных существующей записи пока не
добавлено: при необходимости создайте замену, затем отзовите прежний ключ. Отзыв требует
подтверждения и действует на следующие запросы, включая страницы старого снимка.

Кнопка «Инструкция владельцу» открывает порядок выдачи/хранения/замены. В карточке подключения
«Инструкция для подключения» показывает фактический URL выбранного сервера, имя, срок, квоту, формат
запроса, пагинацию и ошибки. Её можно скопировать. Только в окне выдачи доступно копирование
инструкции вместе с ключом; впоследствии вместо ключа используется `<API_KEY>`. Секреты не пишутся в
localStorage/sessionStorage. При утрате ключа после закрытия нужно отозвать запись и создать новую.

В Demo записи живут только в памяти до перезагрузки, запросов к Supabase нет, ключи учебные. При
недоступной миграции в Live экран показывает ошибку, а не подменяет данные Demo. Экран не публикует
API; для работы в выбранной реальной среде нужны все три миграции и Edge Function. Публикация сайта
сама по себе не применяет миграции.

## Проверки

Из каталога API:

```powershell
deno task check
deno task lint
deno task fmt:check
deno task test
```

Из корня: SQL-контракты `supabase/tests/external_api.sql` и
`supabase/tests/external_api_pagination.sql`, `supabase/tests/external_api_root_admin.sql`
выполняются `psql` с `ON_ERROR_STOP=1` после чистых миграций+seed. Он включает fixtures через
относительный `\ir`, весь набор откатывается. Общие security contracts и database lint остаются
обязательными; lint должен включать `public,external_api_private`.

Для настоящих HTTP-тестов используйте отдельную свежую локальную базу, в которой fixture ещё не
записан. Из каталога API выполните в PowerShell7 (при необходимости задайте полный `-PsqlPath`):

```powershell
./tools/prepare-local-tests.ps1 -DatabaseUrl 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
deno test --env-file=.env.integration --allow-net=127.0.0.1,localhost --allow-env=EXTERNAL_API_TEST_URL,EXTERNAL_API_TEST_KEY,EXTERNAL_API_TEST_LIMITED_KEY integration/
```

Подготовка создаёт1106 синтетических меток и случайные тестовые ключи, записывает их только в
игнорируемый `.env.integration`. Существующие fixtures не перезаписываются. При других портах
передайте `-ApiUrl` и соответствующий DatabaseUrl. Для нового отдельного тестового файла можно
передать `-EnvFile .env.pagination`; существующий файл не перезаписывается. HTTP-тесты отвергают
облачные адреса; повтор теста квоты требует следующей календарной минуты. Переменные можно передать
без env-файла и выполнить `deno task test:integration`.

CI проверяет Deno typecheck/lint/format/tests и SQL-контракт. Полный локальный HTTP-тест выполнялся
отдельно; автоматического деплоя API нет.
