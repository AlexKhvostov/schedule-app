# RedParty API v2 — инструкция владельцу бота

Универсальный HTTP API для любого языка и сервера. Google Sheets, Google-аккаунт и Supabase SDK не
нужны. API только читает расписание. Старый `/v1/schedule` продолжает работать.

## 1. Что получить от владельца RedParty

- Персональный ключ интеграции `rp_…` с правом `schedule:read`. Передаётся отдельно от этой
  инструкции.
- Разрешённую частоту запросов для ключа. Обычная синхронизация — раз в180секунд.
- Месяц и нужные фильтры. Новый месяц — новый полный набор и отдельный курсор.

Адрес рабочей среды:

```text
https://wvfllegshaqonqqpbtle.supabase.co/functions/v1/external-api/v2/schedule
```

Ключ передавать только заголовком `X-API-Key`. Заголовки `apikey`, `Authorization: Bearer`, Supabase
publishable/service_role ключи и Discord-вход для этого API не нужны. Сохраните ключ в
секретах/переменных окружения сервера бота. Не помещайте его в URL, исходники, клиентский
JavaScript, сообщения Discord или журналы. Если существующий ключ имеет `schedule:read`, его можно
использовать с v2; новую интеграцию лучше выделить отдельным ключом.

## 2. Первый запрос: полный месяц

```http
GET /functions/v1/external-api/v2/schedule?date=2026-11-01&days=30
X-API-Key: <ваш ключ>
Accept: application/json
```

`date` — дата начала `YYYY-MM-DD`, `days` — от1до31. Для месяца задайте первое число и его
фактическую длину: ноябрь30, декабрь31. Необязательные фильтры:

| Параметр  | Значение                                                      |
| --------- | ------------------------------------------------------------- |
| `variant` | `nitro` или `regular`; без параметра оба вида                 |
| `limit`   | Один лимит, например `50` или `100`; без параметра все лимиты |

Чтобы получить Nitro50 и100 одним набором, запросите `variant=nitro` без `limit` и отберите нужные
линии у себя. Список лимитов через запятую не поддерживается. Если запрашиваете50и100 отдельно, у
каждого запроса должны быть собственные локальные данные и курсор.

Пример curl в shell с заранее заданным секретом `REDPARTY_API_KEY`:

```bash
curl --fail-with-body --get \
  'https://wvfllegshaqonqqpbtle.supabase.co/functions/v1/external-api/v2/schedule' \
  --header "X-API-Key: $REDPARTY_API_KEY" \
  --data-urlencode 'date=2026-11-01' --data-urlencode 'days=30' \
  --data-urlencode 'variant=nitro'
```

Для реального клиента задайте HTTP timeout30секунд и проверяйте HTTP status до разбора данных.

## 3. Ответ и страницы

Сокращённый пример полного ответа (ID синтетические):

```json
{
  "api_version": "2",
  "mode": "full",
  "batch_id": "aaaaaaaa-0000-4000-8000-000000000001",
  "page": 1,
  "query": { "date": "2026-11-01", "days": 30, "variant": "nitro", "limit": null },
  "timezone": "Europe/Madrid",
  "slot_minutes": 30,
  "lines": [
    {
      "id": "bbbbbbbb-0000-4000-8000-000000000001:0",
      "number": 1,
      "variant": "nitro",
      "limit": "50"
    }
  ],
  "items": [
    {
      "type": "person",
      "id": "cccccccc-0000-4000-8000-000000000001",
      "state": {
        "name": "Example",
        "discord_id": "123456789012345678",
        "mark": { "text": "EX", "background": "#76a5af", "foreground": "#1a2118" },
        "priority": {
          "order": 1,
          "core": 2,
          "score": 1250.5,
          "excluded": false,
          "period_start": "2026-11-01",
          "variant": "nitro",
          "limit_group": "50-100"
        }
      }
    },
    {
      "type": "cell",
      "date": "2026-11-01",
      "line_id": "bbbbbbbb-0000-4000-8000-000000000001:0",
      "half": 20,
      "state": { "person_id": "cccccccc-0000-4000-8000-000000000001", "tables": null }
    }
  ],
  "has_more": false,
  "next_page": null,
  "cursor": "dddddddd-0000-4000-8000-000000000001"
}
```

В одной странице максимум1000записей `items` (людей и клеток вместе). Если `has_more=true`,
`cursor=null`, а `next_page` содержит токен следующей страницы. Немедленно продолжите:

```http
GET /functions/v1/external-api/v2/schedule?page=<next_page>
X-API-Key: <тот же ключ>
```

Передавайте **только** `page`, без `date/days/variant/limit/cursor`. Соберите все страницы одного
`batch_id`; их режим должен совпадать. Пакет неизменен15минут, даже если расписание уже поменялось.
Повтор страницы безопасен. На последней странице будет новый `cursor`, который означает границу
всего применённого пакета. Страничный `next_page` не является курсором синхронизации.

## 4. Что сохранять в боте

На каждый набор (ключ + месяц/диапазон + фильтры):

| Данные                                  | Ключ локального хранения |
| --------------------------------------- | ------------------------ |
| Люди: имя, Discord ID, метка, приоритет | `person.id`              |
| Линии: вид, лимит, номер                | `line.id`                |
| Занятые клетки: человек, столы          | `(date, line_id, half)`  |
| Финальный курсор синхронизации          | Один на этот набор       |

`discord_id` храните **строкой**:18–19значные ID теряют точность в обычном JavaScript Number.
`person.id` — внутренний стабильный ID RedParty, он отличается от Discord ID.

`half` от0до47:0=00:00–00:30,20=10:00–10:30,47=23:30–24:00. Это клетки местного расписания
Europe/Madrid. Не считайте их UTC и не прибавляйте постоянно 2часа круглый год: разница с Минском
меняется при летнем времени. Переходы часов не создают новые номера `half`. `line_id` непрозрачен —
используйте `lines`, не разбирайте UUID/суффиксы сами. `tables:null` означает отключённый учёт
столов, а не свободный слот.

В `full` замените **целиком** локальные данные именно этого набора, в том числе удалите прежние
занятые клетки, которых больше нет. Не стирайте другие месяцы/наборы.

## 5. Далее — обновление раз в три минуты

```http
GET /functions/v1/external-api/v2/schedule?cursor=<сохранённый cursor>
X-API-Key: <тот же ключ>
```

Передавайте только `cursor`, остальные параметры уже связаны с ним на сервере.

При `mode=delta` примените `items` как замены последних состояний:

- `person` с непустым `state` — заменить запись человека целиком.
- `person` со `state:null` — удалить запись справочника после применения клеток пакета.
- `cell` с непустым `state` — заменить владельца/столы по точному адресу клетки.
- `cell` со `state:null` — очистить этот адрес (удалить занятость).
- Отсутствие записи в дельте означает «без изменений», а не удаление.

Один адрес приходит в последнем состоянии: промежуточные перестановки не воспроизводите. Дельта тоже
может иметь страницы — сначала соберите их все. Изменение имени/метки/приоритета приходит отдельной
записью `person`, без повторной передачи его клеток.

Если ничего не менялось:

```json
{
  "api_version": "2",
  "mode": "unchanged",
  "cursor": "dddddddd-0000-4000-8000-000000000001",
  "has_more": false,
  "next_page": null,
  "items": []
}
```

При `unchanged` расписание не перестраивайте и полный месяц не запрашивайте. Сохраните возвращённый
курсор и время успешной проверки. Курсор действует24часа без использования; успешные запросы
продлевают его срок. У сервера может быть новый курсор даже при пустом наборе изменений.

## 6. Порядок игроков: рассчитанный приоритет Nitro50–100 с Core

Сервер берёт **активный расчёт клуба**, выбранный администратором RedParty. Месяц расчёта находится
в `person.state.priority.period_start` и может отличаться от месяца запрошенного расписания. Не
рассчитывайте рейтинг самостоятельно и не используйте порядок Discord ID.

- Сначала игроки с положительным Core Nitro50–100, по возрастанию номера.
- Затем остальные — по убыванию рассчитанных баллов `score`.
- При равенстве — имя без учёта регистра, затем стабильный ID.
- Исключённые из приоритета (`excluded=true`) остаются в конце; их существующие слоты не исчезают.

`priority.order` — готовый порядок среди людей **этого ответа/локального набора**, начиная с1. Это
не номер Core и не глобальное место среди всех участников клуба. Справочник содержит только
владельцев слотов выбранного диапазона, а не весь список клуба. Nitro50–100 используется как единая
база сортировки, даже если в запрос попали Regular или старшие лимиты. Core других групп не
подмешивается. `core=0` означает отсутствие Core.

В полном пакете люди идут в порядке `priority.order`, затем клетки. После дельт поддерживайте
словарь людей по ID и **сортируйте сохранённый список по `priority.order`**, а не по порядку прихода
последней дельты: она содержит только изменившихся людей. При изменении расчёта, Core или активного
периода сервер сам присылает новые приоритеты и места; клетки при этом не повторяются. Старый уже
начатый пакет переходного выпуска может не иметь `priority`: завершите его и запросите дельту по
финальному курсору, она добавит приоритеты. Не заменяйте их догадками.

## 7. Надёжный цикл клиента

```text
каждые180секунд, без параллельного запуска для одного набора:
    прочитать сохранённый cursor
    запросить cursor, а если его ещё нет — date/days/фильтры
    собрать все страницы; проверить batch_id, mode и финальный cursor
    начать локальную транзакцию:
        full: заменить людей/линии/клетки этого набора
        delta: применить состояния клеток и людей; удалить person tombstones последними
        unchanged: не менять данные
        сохранить финальный cursor и время успешной проверки
    зафиксировать транзакцию
    сформировать представление бота из локальных данных,
        отсортировав людей по priority.order
```

Курсор сохраняется **вместе с успешно применёнными данными**, не раньше. При сбое остаётся старый
курсор; повтор применяет те же состояния и безопасен. Если хранилище не имеет транзакций, сначала
записывайте временный набор, затем переключайте активную версию данных и курсор вместе. Не храните
курсор только в RAM: после перезапуска бота он должен сохраниться. Не запускайте full каждые3минуты
и не заводите отдельный курсор на каждый опрос.

После перехода на новый месяц выполните новый full. Старый набор можно продолжать обновлять
отдельным курсором, если он ещё нужен. Смена ключа или фильтров требует нового полного набора.

## 8. Ошибки и восстановление

Ошибки имеют JSON вида `{"error":{"code":"..."},"request_id":"..."}`; поле `field` может уточнять
неверный параметр. HTTP status — основной признак, `request_id` полезен для поддержки.

| HTTP                              | Действие бота                                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------------------------- |
| 400 `validation_error`            | Исправить параметры; не повторять тот же запрос бесконечно                                         |
| 401 `invalid_api_key`             | Остановить опрос, проверить/заменить ключ с владельцем                                             |
| 403 `insufficient_scope`          | Остановить опрос, запросить право `schedule:read`                                                  |
| 410 `resync_required`             | Забыть токен, один раз загрузить исходный полный диапазон; заменить данные после успешной загрузки |
| 422 `response_too_large`          | Уменьшить диапазон/фильтр; для каждого нового набора отдельный курсор                              |
| 429                               | Соблюсти заголовок `Retry-After` в секундах; курсор/данные сохранить; без немедленных повторов     |
| 5xx, timeout, сеть, неверный JSON | Сохранить прежние данные/курсор, повторить с нарастающей задержкой и случайным разбросом           |

Рекомендуемые задержки при временном отказе:30,60,120,180, затем максимум900секунд, с небольшим
случайным разбросом. После успеха вернуться к180секундам. Одновременно выполняется только одна
цепочка данного набора. Страницы одного пакета получать сразу, не ждать3минуты между страницами.
Лимит частоты общий для всех запросов данного ключа, включая страницы и обе версии API. Не
маскируйте401/403/5xx постоянным запросом полного месяца.

При низкой квоте первый полный набор может загружаться несколько минут. Все страницы должны быть
получены за15минут жизни пакета. Если это невозможно с текущим лимитом, уменьшите диапазон или
согласуйте с владельцем больший лимит; не пытайтесь обходить429 параллельными запросами.

## 9. Переход с v1 и проверка перед запуском

V2 — другой формат. Недостаточно заменить `/v1/` на `/v2/` в старом парсере. V1 возвращает прежний
экспорт, v2 — `items` с людьми/клетками и `lines`. Включите новый обработчик отдельно, выполните
первый full и сравните локальное расписание со старым ботом. После проверки переключите основной
цикл на курсор и отключите прежний полный опрос. Старый API не отключается; при откате его можно
вернуть.

Критерии приёмки клиента:

1. Полный месяц загружается со всеми страницами и сохраняется после перезапуска.
2. Следующий опрос даёт `unchanged` или корректную дельту, без второго полного месяца.
3. Изменение владельца, очистка клетки и изменение метки отражаются в боте.
4. Изменение Core/расчёта переставляет людей без повторной загрузки клеток.
5. Ошибка записи не продвигает курсор; повтор не создаёт дубликатов. 6. 410 вызывает один resync,429
   — ожидание,401/403 — остановку и сообщение оператору.
6. Discord ID не теряет цифры, время слотов соответствует Europe/Madrid.

Проверки записи/очистки выполняйте в согласованной тестовой среде, а не меняйте рабочие смены ради
проверки бота. В технических журналах достаточно HTTP status, request_id, mode, количества записей и
байт. Ключи, содержимое расписания и персональные записи в журналы не выводить.
