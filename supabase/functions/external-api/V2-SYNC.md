# API v2: синхронизация расписания

Подготовленная реализация. Перед использованием в Working нужны миграция, обновление Edge Function и
приёмка выпуска. V1 продолжает работать.

## Запросы

Тот же заголовок `X-API-Key`, право `schedule:read`. Для нового потребителя рекомендуется отдельное
подключение в Root → API: его ключ можно отозвать независимо. Версию выбирает URL, а не формат
ключа.

```http
GET /functions/v1/external-api/v2/schedule?date=2026-11-01&days=30
GET /functions/v1/external-api/v2/schedule?cursor=<sync-cursor>
GET /functions/v1/external-api/v2/schedule?page=<next_page>
```

Первый запрос: `date` и `days` (1–31), необязательные `limit` и `variant` — как в v1. Для целого
месяца передайте первое число и фактическое число дней месяца. `cursor` или `page` передаются
**отдельно**, без других параметров. Курсор привязан к ключу и исходному диапазону/фильтрам. Для
другого месяца нужен новый полный запрос.

## Формат данных

`mode`: `full`, `delta` или `unchanged`. `full` заменяет локальные данные выбранного диапазона
целиком. `delta` применяет перечисленные изменения. Отсутствующая клетка в дельте означает «без
изменения», `state: null` — очистить адрес.

`items` — нормализованные записи двух видов:

```json
[
  {
    "type": "person",
    "id": "aaaaaaaa-0000-4000-8000-000000000001",
    "state": {
      "name": "Example",
      "discord_id": "123456789012345678",
      "mark": { "text": "EX", "background": "#76a5af", "foreground": "#1a2118" }
    }
  },
  {
    "type": "cell",
    "date": "2026-11-01",
    "line_id": "bbbbbbbb-0000-4000-8000-000000000001:0",
    "half": 20,
    "state": { "person_id": "aaaaaaaa-0000-4000-8000-000000000001", "tables": null }
  }
]
```

Адрес клетки — `(date, line_id, half)`. `half` от0до47: 0=00:00–00:30,
20=10:00–10:30,47=23:30–24:00. Это местные клетки расписания Europe/Madrid, а не UTC-интервалы: при
переходе часов не следует самостоятельно назначать им единственный UTC-момент. `line_id` непрозрачен
для клиента; полный ответ даёт `lines` с `id`, номером линии, `variant` и `limit`. Нумерация линий
начинается с1. `tables:null` означает отключённый учёт столов, а не свободную клетку.

Имена и метки передаются один раз в справочнике людей. В клетках остаётся `person_id`. Смена
имени/метки даёт только `person`; удаление последнего слота человека в диапазоне также даёт `person`
со `state:null`. Удалённая запись справочника удаляется после применения всех клеток пакета.
Справочник содержит только владельцев слотов диапазона, не весь клуб. Идентификатор человека не
является идентификатором учётной записи Auth.

## Страницы и надёжное сохранение

В странице не более1000 записей (людей **и** клеток вместе), до4MiB внутреннего JSON. Пакет
ограничен250000записями/32MiB. Ответы `full`/`delta` содержат `batch_id`, `page`, `has_more`,
`next_page`, `expires_at`, `cursor`, а также исходный `query`, `timezone`, `slot_minutes`,
`generated_at`. `lines` заполнен только в `full`.

При `has_more:true` поле `cursor` равно null: продолжайте через `page=next_page`. Новый курсор
появляется **только на последней странице**. Все страницы одного пакета неизменны15минут. Повтор
исходного курсора в этот срок повторяет тот же пакет; повтор страницы тоже безопасен. Изменения,
пришедшие во время выдачи, будут в следующем пакете.

Клиент должен собрать страницы во временный набор, проверить их `batch_id`, применить изменения и
сохранить новый курсор **одной локальной транзакцией**. При сбое используйте прежний сохранённый
курсор. Не сохраняйте промежуточный `page` как курсор синхронизации. Не запускайте несколько
независимых цепочек синхронизации для одного локального набора одновременно.

Нет изменений — короткий ответ, например:

```json
{
  "api_version": "2",
  "mode": "unchanged",
  "cursor": "cccccccc-0000-4000-8000-000000000001",
  "has_more": false,
  "next_page": null,
  "items": []
}
```

Курсор живёт24часа без использования; успешный тихий опрос продлевает его срок. Если служебная
версия поменялась без видимых изменений, `unchanged` может дать новый курсор — его тоже нужно
сохранить. Опрос раз в3минуты достаточен.

## Ошибки

- `410 resync_required`: истёк/неизвестен/чужой курсор или страница, изменена конфигурация
  расписания либо очищены старые маркеры изменений. Удалите локальный курсор и заново загрузите
  диапазон полностью. Не смешивайте новый full со старым незавершённым пакетом.
- `401`/`403`: проблема ключа/права, не выполнять бесконечный полный опрос.
- `429`: выдержать `Retry-After`; квота ключа общая дляv1/v2 и всех страниц.
- `422 response_too_large`: сузить диапазон/фильтры и создать отдельные цепочки.
- `503`: ограниченные повторы с задержкой; сохранить старые данные и курсор.

## Устройство и ограничения

Это не чтение аудита. В закрытой `cell_changes` хранится одна версия адреса, при чтении берётся его
**последнее состояние** из occupancy. Запись маркера, изменение слота и увеличение версии участка
выполняются одной транзакцией. Курсор хранит вектор версий; счётчик sequence/maxID здесь не
используется. `read_sync` — STABLE, поэтому версии, состояния и люди читаются из одного
согласованного снимка PostgreSQL.

Основание для выбора STABLE:
[правила снимков PostgreSQL](https://www.postgresql.org/docs/15/xfunc-volatility.html).

Тихий опрос читает версии, без occupancy и сборки JSON месяца. При изменениях читаются затронутые
адреса; справочник владельцев диапазона сверяется по хешам. То есть API всё ещё обращается к БД, но
избегает повторной полной выгрузки. Итоговое сокращение трафика зависит от количества изменений и
перехода клиентов наv2; работающие v1-клиенты продолжают получать прежние полные ответы.

Первая полная выгрузка не обязана быть меньшеv1: адрес каждой клетки и служебная информация тоже
занимают место. На синтетическом наборе1106клеток все страницыv1 заняли200310байт JSON, fullv2 —
215477байт, unchangedv2 —131байт. Это локальная проверка формата, не расход или прогноз рабочих
квот. Основная экономия — последующие короткие опросы и дельты.

На ключ допускается600 живых контрольных точек, до64MiB их служебных данных и до64MiB пакетов.
Маркеры старше30дней удаляются часовым заданием с обязательной сменой эпохи: старый курсор
получает410, а не теряет изменения молча. Работа расписания/Broadcast сохраняется, отдельного
постоянно работающего сервера нет.
