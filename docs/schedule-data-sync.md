# Данные, подключение и обновление расписания

Документ новой реализации в ветке `codex/realtime-schedule`. Основной сайт до отдельного выпуска использует прежний клиент. Точные результаты проверок, SHA и адрес Preview находятся в [отчёте реализации](../memory/tasks/2026-11-07-realtime-preview.md). История диагностики — в [исследовании](schedule-reliability-review.md).

## 1. Назначение и границы

RedParty — график плановых смен покеристов. По уточнению Алексея от7ноября2026 примерно90–95% времени пользователи смотрят расписание, иногда сутки без действий. Заполнение обычно последовательное, но одновременные правки возможны. Отсутствие действий мышью не означает, что наблюдателю больше не нужны обновления.

Приоритеты архитектуры:

1. Открытое расписание получает чужие изменения через постоянную подписку.
2. Неизменные данные не перечитываются короткими независимыми таймерами.
3. Изменение одной клетки не вызывает повторной загрузки всего месяца и оформления.
4. Успешность записи и права определяет сервер, а не состояние индикатора.
5. Пропуски при разрыве/сне исправляются восстановлением данных.
6. Дополнительная периодическая страховка управляется администратором, а не требует нового выпуска кода.

Доставка данных не означает определение фактической игры человека. Онлайн показывает подключение клиента к сервису, а не внимание пользователя или его участие в покерной смене.

## 2. Компоненты и ответственность

| Компонент | Ответственность |
|---|---|
| PostgreSQL в Supabase | Единственный источник расписания, профилей, правил и прав; атомарные записи, версии изменений |
| Supabase Auth | Сессия пользователя и обновление токена |
| Supabase Realtime | Закрытый канал Broadcast и Presence по WebSocket |
| API / RPC | Чтение согласованных данных и транзакционная запись с серверными проверками |
| `src/data` | Один клиент Supabase, общий канал, загрузка/кеш конфигурации, преобразование ответов |
| `ScheduleSync` / состояние месяца | Очередь уведомлений, загрузка участков, восстановление, защита от поздних ответов |
| React-компоненты | Отображение уже полученных данных и пользовательские действия |

Браузер подключается к API и Realtime, а не получает прямой PostgreSQL-доступ. Секретный service-role ключ в браузере не используется. Подписка не заменяет авторизацию запросов.

## 3. Начальная загрузка

После подтверждения сессии создаётся общий контекст текущего аккаунта. Потребители сетки, конфигурации и списка Онлайн переиспользуют один Supabase-клиент и общий канал. Несколько компонентов не создают собственные одинаковые подписки.

Подписка начинается до чтения расписания. Затем клиент получает:

- согласованный снимок выбранного месяца с метками, отображаемыми владельцами и версиями;
- общий пакет конфигурации: разрешённые клиенту правила, оформление, мёртвые интервалы и ёмкости.

Уведомления, полученные во время загрузки, не теряются: после принятия снимка выполняются необходимые дополнительные чтения. Старый ответ другого месяца/аккаунта не может заменить текущий экран. Первоначально неполное расписание не показывается как готовое.

После первого подтверждения подписки и каждого восстановления кеш конфигурации инвалидируется: это закрывает промежуток между HTTP-чтением и входом в канал. Кеш конфигурации существует в памяти вкладки и привязан к аккаунту. При одновременных запросах несколько потребителей ожидают одну загрузку. Выход и смена аккаунта очищают данные и подписки прежнего пользователя.

## 4. Изменение расписания

Операция проходит последовательность:

1. Клиент отправляет транзакционную команду записи.
2. Сервер проверяет права, правила и конфликт клетки, сохраняет данные и обновляет версию в той же транзакции.
3. После фиксации подписчики получают короткое Broadcast-уведомление о затронутом участке.
4. Клиент объединяет близкие уведомления и читает актуальные данные нужных участков.
5. Ответ применяется к подтверждённой основе месяца; неизменённые участки сохраняются.

Участок — дата и вид расписания (`kind_id`, включающий вариант/лимит). События текущей операции группируются; протяжка по48клеткам не должна порождать48одинаковых чтений.

Для сетки и общего пакета конфигурации выполняется по одному запросу каждого типа одновременно; начальные snapshot и config могут читаться параллельно. Новые уведомления во время чтения остаются в очереди. Удаление последней метки означает пустой участок и должно очистить прежнее содержимое.

Клиент не строит собственную полную репликацию PostgreSQL. Broadcast передаёт сигнал об изменении; разрешённые данные выдаёт существующий API.

## 5. Конфигурация и производные разделы

| Данные | Когда читаются |
|---|---|
| Общие настройки и оформление | При необходимости первого показа, затем после события конфигурации |
| Ёмкости и мёртвое время | В пакете конфигурации, после соответствующих изменений |
| Отображаемые сведения участников | Вместе со снимком и после события справочника |
| Список игроков и приоритеты | Когда раздел открыт, после событий зависимостей/восстановления |
| Личные фильтры и параметры вида | Из существующего локального хранилища браузера |
| Часы, текущий получас и затемнение прошедшего времени | Вычисляются локально; для движения часов SQL-запрос не нужен |

Нет независимого минутного опроса палитры, оформления закрытых клеток и цветов нагрузки. Конфигурация загружается общим разрешённым пакетом. Изменение профиля/прав/роли/дистанций, влияющее на производный раздел, должно инвалидировать соответствующие данные. Переход календарного дня также учитывается там, где расчёт зависит от даты без изменения строки БД.

Справочник ролей также кешируется по аккаунту и сбрасывается по directory/access и подтверждению соединения. Заявки приоритетов и их авторы читаются только при открытии окна заявок; постоянно обновляемый счётчик на кнопке убран. Локальный минутный таймер производных списков обнаруживает смену календарной даты Europe/Minsk; сам по себе он не делает SQL-запросов.

Оформление из кеша не является источником прав. Сервер всегда использует текущие ограничения при записи. Косметическая ошибка не даёт права сохранить стандартное значение поверх неизвестной клубной настройки.

## 6. Версии и страховочная проверка

Версии — небольшие метаданные изменений, а не копия расписания. Для сетки сохраняются версии участков; для конфигурации, справочника, приоритетов и контекста доступа — соответствующие версии разделов.

Версия меняется в той же транзакции, что и данные. Снимок возвращает данные и версии одного согласованного среза. Версия участка сохраняется и после удаления последней клетки. Параллельные транзакции не должны теряться из-за порядка фиксации; `max(sequence_id)` не используется как доказательство отсутствия пропущенных изменений.

В админских настройках расписания есть отдельный блок:

- включить/выключить страховочную проверку;
- интервал в целых минутах от1до60;
- исходно выключена, сохранённый интервал5минут;
- краткое объяснение назначения и дополнительной нагрузки.

Когда страховка включена, один запрос проверяет версии нужных разделов. Совпавшие данные не перечитываются. Различающиеся участки/разделы обновляются. Скрытые вкладки не выполняют регулярные контрольные запросы.

**Выключение страховки выключает только периодическую сверку.** Начальная загрузка, Broadcast, восстановление после reconnect/сна, подготовка редактирования и ручное обновление продолжают работать. Переключатель не является командой отключить сетевое подключение или серверную защиту.

При выключенной страховке тихо потерянное последнее уведомление может остаться незамеченным до следующего события того же участка, возврата, reconnect или ручного обновления. Это осознанный режим для проверки событийной работы. При включённых5минутах такой пропуск обнаруживается не позже следующей успешной сверки; неисправная сеть не позволяет обещать фиксированную задержку.

Пример текста блока: «Расписание получает изменения автоматически через постоянное соединение с Supabase. Страховочная проверка дополнительно сверяет данные через заданный интервал. Обычно она не требуется; включайте её при пропусках обновлений или для проверки нестабильного подключения. Частые проверки увеличивают нагрузку».

## 7. Соединение, индикатор и восстановление

Индикатор основан на событиях SDK, без SQL-опроса ради цвета:

| Состояние | Цвет / надпись |
|---|---|
| Подписка подтверждена | Зелёный / «онлайн» |
| Устанавливается соединение | Жёлтый / «connect» |
| Соединение потеряно | Красный / «оффлайн» |

Наведение, фокус с клавиатуры и доступное действие на сенсорном экране показывают пояснение состояния и время последнего успешно принятого обновления данных, если оно известно. Полученное уведомление без успешного чтения не обновляет это время. Процент прогресса без измеряемого объёма работы не показывается. Карточка разделяет заметный заголовок состояния, короткое пояснение, дату/время последнего принятого снимка и ручное действие. Цвет небольшого маркера внутри карточки всегда относится к соединению, даже если сама карточка предупреждает об ошибке чтения. Анимация сопровождает только выполняющийся запрос; переходы и размер адаптированы для светлой/тёмной темы и узкого экрана.

Зелёный цвет описывает соединение. Известная ошибка чтения или незавершённая сверка указывается отдельно в подробностях/состоянии загрузки. Подключение сокета не является доказательством выполнения любой SQL-команды.

Heartbeat и обновление токена выполняет штатный SDK. Это служебный обмен, а не чтение месяца. Не добавляется собственный таймер, который каждые10секунд разрушает подписку и отменяет медленное чтение.

При сбое последнее расписание остаётся видно с честным состоянием подключения. Повторы ограничены одним запросом, имеют увеличивающуюся задержку. Восстановление соединения и возврат после сна запускают согласование версий и изменившихся данных. При потере WebSocket также выполняется одна HTTP-сверка: если API доступен, запись после неё разрешена. Ручная кнопка обновления снимает задержку повторной попытки, но не обрывает уже выполняющийся запрос. Возвращение видимости не должно создавать несколько одинаковых чтений через независимые обработчики focus/visibility/online.

## 8. Запись и конкуренция

Галка редактирования сохраняется как защита от случайного нажатия. При входе в редактирование выполняется одна сверка. Состояние канала и возраст полного снимка сами по себе не заменяют серверный контракт.

- Права участника, допустимость вида/лимита, ёмкость, срок клетки и ожидаемое состояние проверяет сервер.
- Операция диапазона атомарна: либо все её изменения подтверждены, либо операция возвращает конфликт.
- Конкурирующие записи одной клетки не должны молча затирать друг друга.
- Подтверждение замены чужой метки относится к показанному владельцу; иной новый владелец вызывает конфликт.
- Поздний снимок, начатый до локального жеста, не стирает незавершённую операцию.
- При неизвестном результате записи клиент сначала выясняет состояние; автоматическое повторение должно быть защищено от повторного выполнения.

Убирается искусственный срок60секунд после полного чтения. При работающем HTTP отсутствие WebSocket не является самостоятельным запретом записи после сверки. При неизвестном состоянии, ошибке доступа или неподтверждённой операции новая запись не выдаётся за успешную.

## 9. Онлайн через Presence

Вместо регулярных `ping_member_presence` и `list_member_presence` новый клиент использует Presence общего Realtime-подключения. Клиент публикует минимальные сведения из уже загруженного профиля. События `sync/join/leave` обновляют локальный список.

В компактном списке отображаются аватар, имя из анкеты и публичный ник Discord; одинаковые имя и ник не повторяются. Поле `nick` остаётся обязательным для совместимости прежних клиентов, `profile_name` и `avatar_url` — необязательные. Winamax, история игры и активности не передаются. Имя берётся из уже существующего чтения анкеты в V2Shell, ник и аватар — из текущей сессии; отдельных запросов для списка нет. Строки ограничены по длине, аватар допускает только HTTP(S) URL без встроенных учётных данных. Несколько вкладок одного участника объединяются. Разрыв обнаруживается сервером с задержкой; после потери собственной связи старый список не обозначается как текущий.

Вспомогательные подписки пресетов столов и клубных настроек административной панели пока остаются отдельными каналами на том же соединении SDK. Они не выполняют периодических SQL-проверок.

Не загружаются история активности, недавно ушедшие, время/вид последних правок. Журнал действий сохраняется отдельно и не опрашивается для списка Онлайн. Старые таблицы и функции остаются для совместимости, данные не удаляются.

Доступ к каналу проверяется при входе/переавторизации, поэтому серверный отзыв прав не означает мгновенное закрытие уже существующего сокета. Событие access запускает перепроверку пользователя, а каждый новый API-запрос отдельно проверяет права. Уведомления не содержат содержимого профилей, расписания или заявок.

Presence — информационный интерфейс. Его клиентские сведения не используются для прав доступа, авторства транзакций или подтверждения реальной игры. Закрытый канал проверяет членство; право отправлять Presence не даёт право подделывать Broadcast-события.

## 10. Безопасность и совместимость

Новая схема добавляет RPC, метаданные и поля настроек; прежний клиент и прежние RPC остаются работоспособны. Исторические миграции не переписываются. Отзыв доступа, выход и смена аккаунта очищают приватное состояние на клиенте; серверная защита действует независимо от клиентских уведомлений.

Preview и основной сайт сейчас используют один Working-проект Supabase. Изолированы клиентские ветки, а не реальные данные. Поэтому:

- тестовые записи и нагрузочные испытания выполняются только локально;
- в Working применяется только проверенное совместимое дополнение схемы;
- проверка опубликованного Preview проводится чтением;
- старый основной клиент продолжает свою прежнюю схему до отдельного выпуска main;
- новая настройка страховки влияет на новый клиент; старый клиент её не использует.

Откат Preview к прежнему клиенту не требует удаления добавочных колонок/версий или сброса базы. Публикация main требует отдельного поручения Алексея.

## 11. Проверка результата

Обязательны unit/typecheck/lint/build/bundle, Demo и synthetic Live E2E, чистая локальная пересборка БД, SQL security contracts и database lint. Реальная локальная пара сессий проверяет постановку, удаление, замену, протяжку, изменения справочника/конфигурации, Presence и восстановление.

Проверяется отсутствие регулярных чтений при выключенной страховке, включение/изменение интервала без выпуска кода, обнаружение пропуска при включённой страховке, отсутствие гонок при смене месяца/аккаунта и скрытой вкладке. Цель нормальной доставки — p95≤2секунды на исправном стенде; это критерий, а не гарантия при отказе сервиса.

Длительная устойчивость проверяется наблюдением после тестового выпуска. Короткая успешная проверка или Ready в Vercel не доказывает сутки безотказности. Результаты и ещё не проведённые проверки перечисляются в отчёте, без выдуманных процентов готовности.

| `ScheduleSync` / `ScheduleMonthState` | `v2/schedule`: очередь чтения/записи, отбрасывание позднего ответа, применение только прочитанных ревизий |
| Индикатор / Онлайн / страховка | `v2/schedule/ScheduleSyncStatus.tsx`, `v2/OnlineMenu.tsx`, `v2/ScheduleSyncSettingsEditor.tsx` |

RPC-параметры на проводе имеют префикс `p_`. Версии передаются десятичными строками, чтобы bigint не терял точность в JavaScript. В `schedule_private.sync_versions` один ключ увеличивается один раз на транзакцию. Повторный импорт Discord, меняющий только служебные отметки времени/синхронизации, не будит подписчиков. Косметическая смена ника/метки не порождает access и не заставляет всех перечитывать авторизацию.

Операция v2 получает UUID один раз на жест и ожидаемое содержимое каждой клетки (владелец/столы либо пустота). Сервер блокирует затронутые клетки, проверяет ожидание, вызывает существующий атомарный контракт и сохраняет закрытую квитанцию `edit_receipts`: автор, UUID, хеш команды, результат, время. Повтор той же команды возвращает её результат; иной payload с тем же UUID даёт конфликт. Квитанции не содержат полной копии расписания; автоматическое удаление в этом выпуске не добавлено.

Чтение ограничено15секундами; запись —20секундами. Истечение ожидания записи не означает отмену транзакции. Клиент сохраняет исходную команду и UUID в памяти, запрещает новые правки и предлагает «Проверить сохранение». Повтор безопасно получает квитанцию либо завершает исходную операцию. Определённый серверный конфликт/откат требует свежего снимка и нового решения пользователя. После закрытия или перезагрузки вкладки незавершённая команда из памяти не воспроизводится: пользователь проверяет итоговую метку. Старые атомарные helpers/основной клиент продолжают использовать v1.

Фоновые повторные чтения после ошибок:5,10,20…до120секунд плюс небольшой случайный сдвиг, только один запрос одновременно. Это восстановление после ошибки, а не постоянный опрос здорового сервиса. Отдельный ручной пересчёт приоритетов остаётся пользовательской операцией и может совпасть с событийным чтением панели; он не запускается по таймеру.
