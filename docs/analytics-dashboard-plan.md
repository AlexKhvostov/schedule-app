# План переноса Dashboard на React

Дата: 5 ноября 2026. Статус: **четыре компактных экрана Points/Profile/Speed/Density с фильтрами реализованы локально в Demo; рабочее PHP-подключение впереди**.

Принято Алексеем: новый интерфейс на React; PHP-расчёты, MySQL и сборщик пока сохраняются. Последующее подтверждение «давай так и сделаем»: React обращается по HTTPS к защищённому PHP API, PHP — к прежней MySQL. Сначала переиспользуем текущие операции; оптимизации выполняем по измерениям. Dashboard — самостоятельный раздел приложения с модульными меню, фильтрами, показателями и графиками. Сначала составляется план по экранам. Порядок этапов и конкретное устройство блоков ниже — предложение реализации, а не отметка о готовой функции.

Основания: [разбор исходного проекта](analytics-dashboard.md), [копия-референс](../modules/analytics/README.md), [план-отчёт задачи](../memory/tasks/2026-11-05-dashboard-react-plan.md). Исходники Vue в `modules/analytics/upstream` сохраняются как проверяемый референс, в React-сборку не импортируются.

## 1. Граница с расписанием

Общее приложение предоставляет вход пользователя, тему, язык и верхнюю навигацию. Dashboard получает этот контекст через небольшой публичный интерфейс. Его фильтры, данные, запросы и состояние принадлежат только аналитике.

```text
Приложение: вход · язык · тема · верхняя шапка
    ├─ Расписание → существующие компоненты, расчёты и Supabase
    ├─ Приоритеты → существующие компоненты и Supabase
    └─ Dashboard → собственная оболочка React
         ├─ Меню аналитики
         ├─ Заголовок текущего экрана и состояние данных
         ├─ Фильтры текущего экрана
         └─ Экран-композиция
              ├─ Показатели
              ├─ График / тепловая карта
              ├─ Таблица / детализация
              └─ Служебные панели
                       ↓
            собственный слой запросов → защищённый PHP API → MySQL
```

Разрешённые точки изменения существующего приложения: навигация `V2Shell`, распознавание раздела `shellNavigation`, RU/EN-словарь, адаптивная компоновка общей шапки под третью кнопку и тесты перехода. При будущем подключении — проверка доступа на PHP API и настройка разрешённого источника запросов в политике сайта. Не переписываем `App`, вход, провайдеры и маршрутизацию всего сайта ради Dashboard.

Запрещённые зависимости: импорт `src/schedule`, компонентов сетки, приоритетов, ёмкости, смен или их хранилищ в аналитику. Даже похожую таблицу «день × час» не строим на компоненте редактирования смен: у неё другая модель данных. Повторно используем только подходящие общие UI-примитивы: кнопки, диалоги, подсказки и тему.

Данные аналитики не записываются в Supabase расписания. Соединение с MySQL остаётся только у PHP. Секреты PHP/базы не попадают в браузер, `NEXT_PUBLIC_*`, Git и референс.

## 2. Шапка, меню и компоновка

| Уровень | Состав | Правило |
|---|---|---|
| Общая шапка сайта | Расписание · Приоритеты · **Dashboard**, существующие аккаунт/тема/язык | Добавляется одна кнопка; текущий порядок и поведение остальных разделов сохраняются |
| Локальное меню Dashboard | Очки за день · Профиль игрока · Скорость · Плотность; отдельно Реги. Home/Players/Yearly и админка отложены по уточнению Алексея 5 ноября | Меню не дублирует общую навигацию, не загружает данные всех экранов |
| Заголовок экрана | Название, краткий смысл, зона времени ES/Madrid, состояние и обновление данных | Не повторяет весь набор фильтров и не называет локальное время загрузки временем сбора |
| Панель фильтров | Только применимые к экрану поля, «Применить», «Сбросить», краткое описание применённого набора | Период и аудитория не прячутся в настройках графика |
| Поле блоков | Карточки показателей, графиков и таблиц | Каждая карточка имеет свой заголовок, настройки отображения и состояние загрузки/ошибки |

На широком экране: общая шапка сверху, компактное локальное меню слева; справа заголовок, фильтры и сетка блоков. На телефоне локальное меню превращается в компактный переключатель раздела, фильтры сворачиваются с видимой сводкой, блоки идут одной колонкой. Тепловая карта и широкая таблица прокручиваются **внутри своего блока**, не растягивая всю страницу.

У Dashboard один основной вертикальный контейнер прокрутки, без вложенного `100vh` из старого приложения. Липкие элементы учитывают высоту общей шапки. Диалоги имеют отдельные шапку, прокручиваемое содержимое и действия, возвращают фокус в вызвавший элемент. Подсказки доступны по клавиатуре и касанию. Цвет дополняет числовую подпись/легенду, не заменяет её. Обе темы и RU/EN входят в каждый этап.

Первый экран — **«Очки за день»**, как в текущей аналитике. Home не делаем стартовым только из-за названия: в исходном меню он помечен «В разработке».

## 3. Самостоятельные модули и их договорённости

| Модуль | Ответственность | Чего внутри нет |
|---|---|---|
| `DashboardShell` | Компоновка, локальный маршрут, подключение нужного экрана | Формул, SQL и общих фильтров расписания |
| `DashboardNavigation` | Пункты меню, активный экран, доступность | Запросов отчётов, проверок прав только по локальному флагу |
| `DashboardHeader` | Заголовок, пояснение, часовой пояс, статус | Владения фильтрами и расчёта показателей |
| `DashboardFilterBar` | Сборка отдельных фильтров из описания экрана | Большого набора `if` для каждого графика и вызовов PHP |
| `PeriodFilter` / `LimitFilter` / `AudienceFilter` / `PlayerFilter` | Каждое поле, доступность, валидация, события изменения | Самовольного запуска всех запросов приложения |
| `AnalyticsPanel` / `MetricCard` | Рамка блока, заголовок, действия, единый вид статусов и единиц | Предметных вычислений и сетевых запросов |
| `charts` | Тонкая обёртка выбранной библиотеки: линии, столбцы, легенда, масштаб | Знания PHP-ответов, пользователя и сессии |
| `heatmaps` | Общие ячейки, подписи, легенда, подсказки и оси; отдельные сборки «игрок × час» и «день × час» | Копирования расписания и универсального компонента с десятками несвязанных режимов |
| `widgets` | Законченные блоки: карта очков, график очков, показатели профиля, рейтинг скорости и т. п. | Прямых импортов соседних страниц и чтения общего глобального store |
| `pages` | Сборка блоков, согласование связанных выборок, переходы | Детальной отрисовки всех ячеек/линий и низкоуровневого fetch |
| `model` | Чистые преобразования и сохранённые клиентские расчёты | React, DOM, времени «сейчас» без явного аргумента, побочных запросов |
| `data/analytics` | HTTP, типы ответов, проверка формы, адаптеры PHP, отмена запросов | JSX, оформления и вычисления серверных показателей заново |

Блок получает данные, параметры отображения и обработчики событий: например, `onPlayerSelect`, `onCellSelect`, `onRetry`. Он не меняет соседний график напрямую. Страница обрабатывает событие и передаёт новый согласованный контекст нужным блокам. Специальный hook экрана запрашивает данные через `src/data/analytics`; простой график получает уже подготовленные серии.

Настройки библиотеки графиков остаются внутри адаптера. Внедрение другого движка графиков не должно требовать переписывать PHP-клиент или страницы. Для первого линейного графика реализован небольшой SVG-адаптер `charts/LinePlot` без новой зависимости: продолжение значения через пропуски (уточнено6ноября), стабильные цвета, диапазон времени, легенда и текстовый инспектор. Это не выбор универсального движка для остальных экранов. При необходимости сторонней библиотеки проверяются смешанные линии/столбцы, пропуски, масштабирование, доступность, лицензия и размер загрузки. Отдельная библиотека управления состоянием пока не нужна: начать с локального React-состояния/hooks; добавлять зависимость только по выявленной потребности.

## 4. Предлагаемая структура файлов

Это целевая структура. Созданы `analytics/index.ts`, `Dashboard.tsx`, `shell`, `ui`, `filters`, `contracts`, `model`, `state`, `charts/LinePlot`, `widgets/points`, `pages/PointsPage`, CSS Modules и локальные словари `analytics/locales`; `data/analytics` содержит адаптер PHP и отдельный синтетический источник. Остальные каталоги создаются при переносе соответствующей функции.

```text
apps/web/src/
  analytics/
    index.ts                       небольшой публичный интерфейс раздела
    Dashboard.tsx                  вход в модуль
    shell/                         компоновка, меню, заголовок, локальные переходы
    locales/ru.json, en.json        лениво загружаемое пространство i18next analytics
    filters/                       панель и отдельные поля
    contracts/                     чистые типы данных, фильтров и событий
    model/                         время ES, серии, показатели, форматирование
    state/                         состояние фильтров и жизненный цикл запросов
    ui/                            AnalyticsPanel, MetricCard, состояния блоков
    charts/                        адаптер графиков
    heatmaps/                      общие элементы двух типов тепловых карт
    widgets/
      points/                      карта, линии, выбор Top/сортировки
      profile/                     показатели, скорость по часам, заметка
      speed/                       рейтинг и сравнение по часам
      density/                     карта, сумма по часам, детализация
      overview/                    показатели дня и блок лимита
      players/                     таблица игроков
      yearly/                      годовой календарь и легенда
    features/regs/                 общая панель «свои/чужие»
    features/admin/                административные операции, отдельно от чтения
    pages/                         композиции экранов
    fixtures/                      только синтетические тестовые данные
  data/analytics/                   клиент, адаптеры, API-операции
  locales/ru.json, en.json          только общая навигация, включая кнопку Dashboard

modules/analytics/upstream/         неизменяемый референс Vue/PHP, вне сборки сайта
```

Типы `contracts` не импортируют React и доступны слою данных без втягивания интерфейса. Серверная проверка выполняется в PHP: новый Node/Next.js-посредник и прямое подключение Next.js к MySQL не входят в выбранную схему. Проверенная копия upstream остаётся референсом; размещение поддерживаемой версии PHP-кода определяется перед её доработкой. Не создаём второй клиент аналитики внутри `widgets` и второго экземпляра сессии Supabase. CSS Modules и существующие переменные темы ограничивают стили Dashboard; глобальный `styles.css` исходной Vue-аналитики не переносится. Ориентир проекта — до 400–500 строк на компонент, но деление идёт по ответственности, а не механически по строкам.

Для первого подключения предлагается существующая схема hash-навигации: `#dashboard/points`, `#dashboard/profile`, `#dashboard/speed` и т. д. `#dashboard` открывает «Очки за день»; внешняя оболочка распознаёт только пространство Dashboard. При необходимости красивого `/dashboard` это отдельное небольшое решение, а не повод менять маршрутизацию расписания. Название «страница Dashboard» здесь означает самостоятельный раздел интерфейса, не новый развёрнутый сайт.

## 5. Фильтры и состояние

### Принадлежность

Три уровня: контекст приложения (аккаунт/тема/язык), состояние текущего экрана (применённая выборка), локальное состояние блока (масштаб, видимость линий, открытая подсказка). Не используем один большой объект, подписка на который перерисовывает весь Dashboard при движении мыши над графиком.

У каждого экрана свои `draft` и `applied`: редактирование фильтров не запускает тяжёлые запросы, пока не нажато «Применить». Поиск вариантов ников — отдельный ограниченный запрос с задержкой и отменой предыдущего. После применения весь связанный набор блоков получает одну неизменяемую выборку. Повторное применение без изменений не создаёт лишние запросы; «Обновить» явно повторяет запрос с текущими параметрами.

Для переходов из таблицы/календаря передаётся явный контекст, а не несколько последовательных изменений глобальных фильтров. Возврат сохраняет просмотренный период. На первом открытии дневного экрана — текущий день Madrid, далее пользовательский период не сбрасывается молча. Запоминание визуальных настроек ограничено аккаунтом и разделом; ответы API и заметки не сохраняются в localStorage. Ники/выборки по умолчанию остаются в памяти вкладки; постоянные ссылки на игрока требуют отдельного решения о журналировании URL.

### Матрица применимости

| Экран | Период | Лимит | Игроки / аудитория | Настройки внутри экрана |
|---|---|---|---|---|
| Очки за день | Один день ES | Один | Список ников и сегмент | Общие Top N и сортировка для карты **и** линий; масштаб/видимость линий локальны |
| Профиль | Месяц ES | Один | Один обязательный игрок; без сегмента | Локальные подсказки, заметка отдельно от выбора месяца |
| Скорость | Месяц ES | Один | Список и сегмент | Top N относится к рейтингу и сравнительному графику |
| Плотность | Месяц ES | Один | Список и сегмент | Детализация одного часа дня либо часа за весь месяц |
| Обзор дня (Home) | Один день ES | Четыре отдельных фиксированных блока | Список и сегмент | Выбранный в общем фильтре лимит не должен создавать ложное ожидание фильтрации Home |
| Игроки | Интервал дат ES | Несколько | Список и сегмент | Локальный поиск в уже загруженном списке и Top N |
| Активность за год | Окно около года | Несколько | Список и сегмент | Переход в обзор выбранного дня с сохранением даты |
| Администрирование | Свои параметры операции | По операции | Нет общей панели фильтров | Собственные диапазоны, подтверждение и ход операции |

Контракты запросов сохраняют `16-25` как самостоятельный код, а не число или диапазон для разворачивания. Месяц передаётся как месяц, а день — как календарная дата ES; не подставляем условное 28-е число в API, который принимает `month`. Точные необходимые legacy-параметры закрепляются в адаптере и тесте запроса.

### Загрузка и согласованность

Состояния блока: требуется выбор → первая загрузка → данные / пусто / ошибка / нет доступа. Повторное обновление тех же параметров может сохранять прежние значения с явной отметкой обновления; при изменении выборки прежние цифры нельзя показывать как результат нового фильтра. «Нет данных», ноль, отсутствие сбора и будущий час — разные состояния.

Запрос имеет ключ `пользователь + экран + применённые параметры + ресурс`. Поздний ответ другой выборки игнорируется; используется AbortController и проверка актуального запроса. При выходе или смене аккаунта очищаются данные и открытые приватные панели. На ошибку авторизации нет бесконечных повторов; временная ошибка одного графика не снимает меню и остальные независимые блоки. Блоки одного ответа используют один hook/запрос, а не запрашивают один и тот же PHP endpoint каждый отдельно.

## 6. Перенос по экранам

| Очередь | Референс → новый экран | Отдельные блоки | Существующий API | Проверка готовности |
|---|---|---|---|---|
| 1 | `PointsView` → Очки за день | `PointsControls`, `PlayerHourHeatmap`, `PointsTimeline`, общая легенда/подсказки, действие «В реги» позже | GET `/api/points/heatmap`, затем `/api/points` по тому же набору игроков | Карта и линии совпадают по дню/лимиту/никам/Top; пропуски и простой различимы; быстрые смены фильтров не смешивают ответы |
| 2 | `ProfileHubView` + `PlayerView` → Профиль игрока | `PlayerIdentity`, `PlayerMetrics`, `PlayerMonthHeatmap`, `PlayerHourlySpeed`, `PlayerNote` | GET `/api/heatmap?player=…&month=…&limit=…`; GET/PUT `/api/players/:name/note` | До выбора игрока нет запроса его данных; совпадают KPI и почасовая скорость; переход из списка открывает нужного игрока; заметки подключаются только с правом записи |
| 3 | `SpeedView` → Скорость | `SpeedTopControls`, `SpeedRanking`, `HourlySpeedComparison`, действия регов | GET `/api/speed`; общий справочник регов | Max/Avg и лучший час совпадают; Top меняет согласованно рейтинг и сравнение; пропущенный час не становится нулём |
| 4 | `HeatmapView` → Плотность | `DensitySummary`, `DensityMonthHeatmap`, `DensityHourTotals`, `DensityCellDetails` | GET `/api/heatmap?mode=density`; GET `/api/heatmap/cell` с `day` **либо** `month` | Суммы/выборка совпадают; детализация различает день и месяц; закрытие окна/смена фильтра отменяет устаревший ответ |
| 5 | `HomeView` → Обзор дня | `DayMetrics`, четыре `LimitVolumePanel` со столбцами и средними линиями | GET `/api/home` | Четыре лимита считаются отдельно; итог/пик совпадают; подписи средних соответствуют API; долгий запрос имеет понятное состояние и повтор |
| 6 | `PlayersView` → Игроки | `PlayersToolbar`, `PlayersTable`, `PlayerLink`, `RegBadge` | GET `/api/players`, общий `/api/regs` | Период/лимиты/сегмент соблюдаются; локальный поиск/Top не меняют серверные фильтры; профиль открывается с нужным контекстом |
| 7 | `YearlyView` → Активность за год | `YearActivityCalendar`, `ActivityLegend`, `DayDetails`, действие открытия дня | GET `/api/yearly` | Количество записей не названо очками; downtime различим; клик по дню не сбрасывает дату на сегодняшнюю; недели/месяцы доступны на телефоне |
| Отдельно | `RegsDrawer` → Свои/чужие | `RegsDrawer`, `RegList`, `RegActions`, `BulkRegEditor`, `RegCounts` | GET/POST/PUT/DELETE `/api/regs`, POST `/api/regs/bulk` | Единый список между экранами; read-only доступ отдельно от редактирования; подтверждённые записи обновляют зависимые выборки, ошибка сохраняет черновик |
| Последним | `AdminView` → Администрирование аналитики | `AggregateCatalog`, `CoverageCalendar`, `AggregateDetails`, `RowsPreview`, `RebuildControls`, `JobProgress`, `RunScheduleSettings` | Разрешённые `/api/admin/*`; cron отдельно | Только определённые права; не выдаём пароль/cron-секрет браузеру; просмотры не запускают пересчёт; тяжёлая операция имеет явную цель и контролируемый повтор |

Первый экран **«Очки за день» реализован локально на синтетическом источнике**, остальные экраны остаются запланированными. Действующий PHP-ответ исторического дня проверен через тот же TypeScript-адаптер в памяти, но рабочий HTTP API к браузерному интерфейсу не подключён. После согласованной первой итерации оболочка уже открывает 8 разделов, включая «Реги», с явным уведомлением об отсутствии данных. Администрирование не включено до определения прав. Дальнейший перенос ведётся законченными вертикальными частями: данные → модель → блок → экран → проверка.

У «Очков за день» последовательность запросов важна: из карты получается набор игроков для линий. Пустой либо ошибочный ответ карты не должен незаметно запускать более широкую выборку линий. Это поведение нового интерфейса нужно явно проверить, а не механически переносить старый fallback.

`PlayerView.vue` — только переход к `ProfileHubView`, а не отдельный полноценный экран. `/api/players/:name`, `/history` и `/hour-heatmap` присутствуют в PHP, но текущий профиль использует `/api/heatmap`; не подключаем неиспользуемые маршруты лишь потому, что они существуют.

## 7. Что сохраняем в расчётах

PHP-алгоритмы, таблицы и процесс сбора не меняются. Но в Vue уже есть клиентские вычисления: KPI профиля, средняя скорость по часу суток, выравнивание графика по шестиминутным интервалам, обработка пропусков/простоя, сортировка/ограничение отображения. Их переносим в чистые TypeScript-функции **без изменения формулы**, проверяя на одинаковом входе старый и новый результат.

Сохраняем: сутки Madrid; UTC-моменты; MAX/carry только в пределах своего дня и лимита; точный смысл `null`/нуля/отсутствия сбора; различие прироста между часами и скорости внутри часа. Среднее профиля не заменяем формулой рейтинга скорости: у них в исходнике разные правила отбора. Переходы летнего времени проверяются отдельно; не «исправляем» 24-часовую модель PHP незаметно при переносе UI.

Обнаруженное расхождение референса: Home подписывает среднее как «~60 дней», но `handle_home` возвращает `avgDaysBack=30`. В новом интерфейсе подпись должна брать фактическое окно из ответа, а не воспроизводить устаревший текст. Это исправление представления, а не смена формулы.

Для проверок используем синтетические ответы: обычный день; нули; пропуски; downtime; только один игрок; несколько лимитов; переход месяца/года; DST; большие выборки. Позднее на отдельно разрешённом тестовом контуре сверяем фактические ответы старого и нового интерфейса. Реальные ники/заметки/ответы не сохраняем в Git.

## 9. Что требует решения до соответствующего этапа

Выбранная схема: **React → HTTPS PHP API → MySQL**. React остаётся в существующем приложении на Vercel, серверная проверка доступа добавляется непосредственно в PHP. Новый Node.js-сервер/прокси и прямой доступ приложения к MySQL не планируются. По исходному README PHP API рассчитан на Hostland; фактические HTTPS, версия PHP, сетевой доступ к Supabase и ограничения аккаунта проверяются перед подключением. Выбор архитектуры не означает, что доступ на сервере уже настроен.

Согласованный подход к API: сначала переиспользовать действующие операции и форматы, добавить общую проверку доступа **до обращения к базе**, затем измерить время и размер ответа каждого экрана. При подтверждённом узком месте оптимизировать соответствующий endpoint, SQL/агрегат или кэш с сохранением смысла результата. Число UI-компонентов не определяет число endpoints: несколько связанных блоков могут использовать один ответ. Новые оптимизированные операции не должны ломать работающий старый Dashboard; при несовместимом формате нужен отдельный контракт/версия. PHP проверяет подлинность пользовательской сессии и серверные права; CORS не заменяет эту проверку. Браузер передаёт токен по HTTPS в заголовке, не в URL. Учётные данные MySQL остаются только на сервере. Сейчас это план, никаких изменений PHP/БД не выполнено.

- **До реальных данных:** где работает PHP, как закрывается прямой доступ и прежний публичный адрес. Пользовательская сессия проверяется сервером, а не кнопкой. Формулы и MySQL сохраняются, но серверную обвязку доступа потребуется дополнить. Существующий `db()` выполняет DDL даже при чтении; изоляция доступа не даёт оснований считать его read-only.
- **До записи:** кто читает, кто меняет реги/заметки и кто запускает пересчёты. Предложение: чтение активным участникам клуба, запись и администрирование отдельными правами. Это пока не утверждённая матрица ролей.
- **До запуска тяжёлых отчётов:** ограничения времени PHP/веб-сервера и клиента. В исходнике Home допускает до 180 секунд, Speed — до 60. Эти установки не доказывают фактические лимиты хостинга; нужны фактические измерения и отдельное эксплуатационное решение без изменения формул.
- **До выбора графического движка:** функциональность и лицензия, размер отдельного пакета, поведение на телефоне. Его замена ограничивается `charts`, не всей аналитикой.

На этапе планирования эти пункты не блокируют описание модулей и перенос на синтетических данных. Они блокируют соответствующие реальные возможности, поэтому не должны скрываться за уже работающим меню.

## 10. Реги: обязательная проверка при переносе

По прямому поручению Алексея 5 ноября 2026 недочёты референса не воспроизводятся автоматически. Статический разбор выявил:

- `PointsView.addReg` добавляет только в `theirs`, без обработки ошибки и состояния сохранения в точке действия; панель открывается только после успеха.
- `PlayersView` вызывает `regs.upsert` напрямую для своих/чужих, без обработки ошибки на экране.
- `RegsDrawer.move` и кнопки удаления не обрабатывают отклонённый запрос и не блокируют повторный клик. Массовое добавление, напротив, имеет `busy`/`catch`.
- `stores/regs.load` поглощает ошибку перечитывания списка. После успешной записи `upsert`/`remove`/`bulkUpsert` могут завершиться успешно при устаревшем списке. Нужно различать «запись выполнена, обновить список не удалось» и «запись не выполнена», не повторять запись автоматически.
- В `SpeedView` есть локальные обработчики ошибок и занятости. Их поведение нужно сохранить и проверить вместе с обновлением общего списка.

Это подтверждённые свойства кода; причина замеченной пользователем ошибки в работающем сервисе пока не воспроизведена. Референс и рабочий PHP не менялись. В первой итерации показаны только области «Свои реги» и «Чужие реги» без фиктивных кнопок сохранения.

Приёмка функции: одиночное добавление в обе группы из «Очков», «Скорости», «Игроков» и общего списка; массовый ввод с разделителями/пустыми строками/дублями; перенос туда и обратно; удаление; согласованное обновление всех экранов и фильтров. Проверяются отказ/истечение доступа, ошибка сети, двойной клик, неуспешное перечитывание после записи и сохранение черновика. Исходное правило bulk — существующие ники пропускаются без смены группы — сохраняется и явно объясняется пользователю; это не ошибка само по себе. Реальная запись включается только после серверных проверок прав этапа F.


## 11. Реализованная логика Points и проверенный API — 5 ноября 2026

Панель собирается из `DayFilter`, `LimitFilter`, `AudienceFilter`, `PlayersFilter` по явному набору `pointsFilterFields`; лишних месячных/диапазонных/мультилимитных полей нет. Ники пересекаются с сегментом, поддержаны все7сегментов PHP. Редактирование меняет draft; «Применить» меняет оба блока, «Обновить» повторяет applied и сохраняет draft, «Сбросить» возвращает текущий день Madrid/50€/всех/Top10/сортировку по очкам. Top/sort применяются сразу к applied обоих блоков. Повтор без изменений не запускает запрос. Поля можно свернуть, оставив видимыми действия и сводку выборки.

Внутри Dashboard применённые значения и черновик сохраняются при переходах между вкладками; выход из модуля/перезагрузка/смена аккаунта сбрасывают их. Ответы/ники не пишутся в localStorage. При будущей необходимости сохранять возврат из расписания это отдельное расширение жизненного цикла, а не глобальный store сейчас.

`loadPoints` сначала получает карту и проверяет день/лимит/формат. Пустая/ошибочная карта не запускает график. Для графика передаются строго имена карты и `topN=all, segment=all`, затем проверяются имена/лимит ответа и сохраняется порядок карты. Отсутствующие серии явно отмечаются. Ошибка графика оставляет корректную карту с отдельным повтором. AbortController и монотонная ревизия исключают устаревшие ответы, включая A→B→A. При новом запросе прежние цифры скрываются.

Модель сохраняет шестиминутные MAX-бакеты, carry после первого снимка, null до первого появления и в будущем, исходное окно скорости около30мин. Нулевые очки не превращаются в отсутствие данных. Известные часы downtime разрывают линии; stale_yesterday_tail не показывается как актуальное значение карты. Сохраняется исходная модель24часов по настенным часам ES: повторный осенний час объединяется по MAX. Это ограничение совместимости, не утверждение о полноте DST-модели.

Действующий endpoint — `http://dashboard.redparty.ru/api/index.php?__route=...`. На18:40Minsk: HTTP200JSON для points/heatmap/regs; HTTPS не устанавливает TLS (unrecognized name). Preflight204 разрешает origin `*`, но только заголовок Content-Type. Проверенные GET отчётов/регов не требуют входа. Карта за4–5ноября/50 пуста; исходные точки за5ноября есть. Исторический день15октября/50 успешно прошёл новый адаптер (Top10,10серий,426точек), без сохранения raw-ответов.

Следующий приоритет после указания Алексея: HTTPS, проверка сессии/прав в PHP и CORS для разрешённых источников, диагностика заполнения analytics_player_hour/analytics_scrape_hour. Затем подключить рабочий Points к защищённому источнику. До этого Demo не подменяет реальные показатели. Админские действия, cron, пересчёт и запись регов не запускались. Для Top=all перед реальным включением измерить размер ответа/URL с никами и время исполнения; при необходимости согласовать ограничение или пакетный контракт без скрытого усечения.

## 12. Компактные четыре экрана — 5 ноября 2026

Последующее прямое поручение Алексея уточняет текущий объём: переносить только Points/Profile/Speed/Density, сохранить компактность MaxWin V2 и испанские часы слева сверху. Home/Players/Yearly и админка в текущем меню отсутствуют; предыдущие описания этих экранов — справочный план отложенных функций. Списки регов остаются важной отдельной функцией, без имитации добавления/удаления.

Локально реализованы:

- Общая оболочка: боковая панель 182 px, отдельный `SpainClock` (Europe/Madrid с DST), компактные заголовки и сворачиваемые фильтры. Таблицы имеют собственную прокрутку, содержимое не растягивается на много экранов; на телефоне таблицы также прокручиваются по горизонтали.
- Points: карта и линии стали компактнее, имя в карте открывает профиль с тем же месяцем и лимитом.
- Profile: только месяц/один лимит/один игрок, KPI max points/max speed/avg speed, карта дня×часа, линия средней скорости по часам. Без выбора игрока нет запроса. Заметки отложены вместе с операциями записи.
- Speed: месяц/лимит/аудитория/ники и Top. Таблица с max/avg, лучшим замером и принадлежностью к регам; столбцы выбранного Top и линия всей выборки. Top не меняет контекст неприменённых фильтров. Кнопок записи регов пока нет.
- Density: месяц/лимит/аудитория/ники, карта суммы прироста, суммы по часам. Ячейка и итог часа открывают отдельную детализацию, сначала 10 игроков и явное раскрытие остальных; из неё можно открыть профиль. Запрос детали задаёт либо день, либо месяц.

Модули `monthly` разделены на контракты, модель, reducer, hooks, filters, widgets и слой `src/data/analytics`. Состояние каждого экрана находится в Dashboard и сохраняется между внутренними вкладками; перезагрузка начинает новый просмотр. Старые/отменённые запросы не могут подменить актуальные данные. Неизвестный профиль/пустое пересечение не расширяют аудиторию. На этапе5ноября HTTP-транспорт не был включён (заменено§14); синтетический источник загружается только в явно включённом Demo.

Сохранены разные определения: Profile считает среднее по всем наблюдаемым часам с ненулевым по типу значением скорости, включая числовой ноль, исключая empty/serverDown. PHP-рейтинг Speed считает только speed>0 при diff_seconds>1200. Density использует серверный междучасовой прирост, без пересчёта его из отображаемой скорости.
