## Root-журнал (локальная миграция, 7 ноября 2026)

[Миграция root_logs](../supabase/migrations/20261106225025_root_logs.sql) добавляет две RPC с пустым search_path, явной проверкой auth.uid()/is_root(), без EXECUTE для PUBLIC/anon:

- `root_logs(source, person, role, from, to, action, limit, before_at, before_id)` читает существующие occupancy_events или member_distance_id_audit. Максимум 200 записей, keyset-переход по `(at,id)` без OFFSET. Даты включительны в Europe/Minsk, UUID и bigint курсоры сравниваются в родных типах. Поиск подстроки по текущим именам/Discord/ID, `%` не является шаблоном. Автор и участник фильтруются независимо. LEFT JOIN сохраняет события удалённых карточек; старые FK occupancy_events уже могли стать NULL — восстановить автора по ним нельзя. Email/телефон/прочие частные поля не возвращаются.
- `root_logs_cleanup(months, cutoff, confirm)` принимает только 2/3 месяца. Предпросмотр возвращает границу и количество. Подтверждение требует ту же допустимую границу, не старее 15 минут, и удаляет только occupancy_events с `at < cutoff`, до 5000 строк, с SKIP LOCKED. Возвращает удалённое/оставшееся количество. История ID, факты дистанций и само расписание не затрагиваются. Операция транзакционная; при неоднозначном сетевом результате пользователь заново получает подсчёт.

У occupancy_events узкий индекс по at заменён `(at DESC,id DESC)`, совместимым с автоматической очисткой; у member_distance_id_audit добавлен такой же индекс. Существующие actor/member индексы сохраняются. Прежний cron `occupancy-events-prune` и функция хранения 2 месяца не меняются. [SQL-контракт](../supabase/tests/root_logs.sql) проверяет права, даты, курсоры одинакового времени, поиск, удалённые карточки, строгую границу и размер порции очистки.

Доработка5 ноября2026, миграция применена к Working перед тестовым выпуском: миграция [20261105102935](../supabase/migrations/20261105102935_active_priority_selection.sql) добавляет закрытую RLS-таблицу priority_settings(id=true, active_period=2026-08-01, revision=0). set_active_priority(date,bigint) — admin.people/root и auth.uid, проверка даты и ожидаемого счётчика под FOR UPDATE; load_priority_view(date,text,text,boolean) — прежние права чтения, null выбирает активный период и возвращает activePeriod/activeRevision/canActivate; load_active_month_roster(text,text,text[],text,text) — schedule, период определяется сервером. ## Компактное чтение и события расписания (Working/preview, 4 ноября 2026)

[Миграция](../supabase/migrations/20261104125706_compact_schedule_sync.sql) добавляет `load_schedule_snapshot(year, month, targets = null, directory_only = false) → jsonb`. Доступ — только авторизованным с `schedule` или `schedule.manage`; SECURITY DEFINER использует пустой search_path и явные схемы. `targets` — до 500 пар `{date, kind_id}` внутри выбранного месяца Winamax Nitro/Regular. `null` означает весь месяц, `[]` — пустой набор. При `directory_only` слоты не передаются, справочник включает владельцев выбранного набора.

Один SQL-срез возвращает `version:1`, период, каталог `kinds`, компактные `slots`, уникальных `members` и `slot_count`. Шесть полей слота: `kind_id, day, half, level, member_id, tables`; текущие буквы, цвета, Discord/Winamax-имена, аватар и приоритеты находятся в справочнике. Табличный max_rows не применяется к скалярному JSON. Защитные пределы — 100000 слотов и 16 MiB JSON: превышение явно завершает запрос ошибкой, без молчаливого усечения. Материализованного серверного кэша нет. `load_month_schedule` сохранена для старого опубликованного клиента.

Закрытая схема `schedule_private` содержит trigger-функции без клиентского EXECUTE. INSERT/UPDATE/DELETE `occupancy` отправляет через `realtime.send` private Broadcast `schedule:changes / slots` с `{date, kind_id}`; смена координат сообщает оба участка. Транзакция записи включает уведомление, откат не публикует изменение. В новой миграции семантические row-триггеры профилей/ников отправляют `directory`, без персональных данных; изменения только технических timestamps не публикуются. Одно событие на ключ/транзакцию; доступ инвалидируется отдельно от косметики. Политика `realtime.messages` разрешает только получение пользователям расписания, отправка клиентом не разрешена. Основные данные в любом случае перечитываются через защищённую RPC.

[SQL-контракт](../supabase/tests/compact_schedule.sql) проверяет более 1000 слотов, справочник без дублей, чтение/очистку участка, уведомление удаления, смену метки, недопустимый период, отсутствие права, anon и запрет подделки событий. Отдельный браузерный тест использует два настоящих локальных Auth-сеанса и Realtime. 4 ноября 2026 миграция установлена в Working, чтение/права и неизменность всех occupancy проверены; порядок выпуска — [operations.md](operations.md).

## Две склейки Discord — это нормально


### Дистанции

Экспорт «Контроль дистанций» строится в браузере из того же отфильтрованного списка, что таблица: выбранные месяц, рум, роль, анкета, ID, наличие дистанции, поиск и виды турниров. Одна строка CSV — отдельный Nitro/Regular/part с исходным ID дистанции и снимком игрового ника; текущие Discord ID/имя берутся из связанной карточки. Карточки без выбранных записей экспортируются нулевой строкой. Сворачивание подробностей не исключает записи. Итоги в отдельные строки CSV не добавляются, чтобы не удваивать суммы при обработке. UTF-8 BOM, разделитель `;`, длинные ID сохраняются текстом. Локальное уточнение 6 ноября: имя скачивания дополнено UTC-временем, чтобы различать файлы одного месяца. Выбор отображаемых лимитов скрывает только столбцы; суммы, CSV и редактор сохраняют все лимиты. Видимость колонок, месяц/рум, поиск, сортировка и остальные фильтры хранятся в localStorage отдельно по пользователю и среде; между браузерами не синхронизируются. [Проверка экспорта](../memory/tasks/2026-11-06-distance-csv-layout.md).

Одна логическая запись — участник, рум, отчётный месяц, Nitro/Regular и part. Значения лимитов лежат отдельно и ссылаются на запись.

- Рум лежит в строке (сейчас Winamax). Второй рум — то же поле, другое значение.
- На строке три идентификатора снимком: `member_id`, `discord_id`, `distance_ext_id`. Если Discord или ID дистанции потом сменятся, старые срезы остаются, новые копятся на карточку.
- `part` по умолчанию `1`. Досыл — `2`, `3`… Отдельные признаки primary/correction и пользовательские ярлыки больше не применяются.
- `comment` — необязательный комментарий к конкретному part.
- `game_nick` — игровой ник из выгрузки в момент записи. Снимок, не живая связь с `player_nicks`. Нужен, чтобы админ сортировал контроль без CSV.
- Повтор с тем же ключом (рум + месяц + вид + формат + part + ID дистанции) **не создаёт вторую запись**. Чтобы дослать турниры отдельной записью, используется следующий part.
- Нет строки — на экране ноль. Год и «всего» не храним, складываем.
- Импорт: Root → «Импорт дистанции», CSV, выбранный рум (Winamax по умолчанию), месяц, part и комментарий, кнопка «Записать» (`save_distance_dump`, SQL `is_root()`). RPC создаёт одну `distance_batches`, логические `distance_entries` и ненулевые `distance_values`; изменившийся ник попадает в `player_nicks`. Админский `admin_distance_book` возвращает активных играющих участников вместе с записями выбранного периода. Ручное создание и изменение выполняют транзакционные `create_manual_distance_entry` и `update_manual_distance_entry` с проверкой `is_staff()`.
- Применённая к Working 12 октября миграция `20261012020000_distance_filter_metadata.sql` дополняет этот read-model `people_filters_version=1`, актуальными `present`/`roles` и `has_active_profile` для каждого участника и каждого среза, включая историю без активной карточки. Текущая identity ищется по сохранённому member_id, а при его отсутствии — по Discord ID; `profile_member_id` позволяет объединить такую историю с текущей играющей карточкой только при чтении. Исторические member_id/Discord ID/ID дистанции остаются неизменными. Активная анкета означает активный `members` и существующий `profiles`, без требования заполнить каждое поле. Права `admin.people`, закрытый anon и существующие границы записей сохраняются. Working обновлён после полного CI; старый ответ без версии не превращается в ложное «все не RedParty», клиент показывает ошибку загрузки.
- «Статус ID» по-прежнему относится к отображаемому ID: при отсутствии ID текущей карточки используется ID из выбранной истории. Это не отдельный поиск незаполненных карточек; изменение этой семантики не принято.
- Та же версия read-model передаёт текущие `avatar_url`/`discord_nick` и для исторических строк без активной карточки, используя уже найденные `discord_members`/`identities`. Снимок игрового ника остаётся отдельным полем, в данных дистанции ничего не переписывается. `distance_filter_metadata.sql` проверяет также сохранение фото и текущего ника; миграция применена к Working 12 октября, фото/ник включены до первого применения.
- Исторический импорт: Root разбирает широкий CSV с четырьмя строками шапки, выбирает рум и Nitro/Regular и передаёт факты в `save_historical_distance_dump`. Запись транзакционная. Владение определяется текущими назначениями ID при чтении; исторические member_id/Discord не назначают владельца. Строка без корректного ID дистанции до RPC не доходит. Числовые дубли пропускаются, кроме разрешённой перезаписи ручных правок, описанной ниже.

Применено к Working 7 ноября 2026 и опубликовано в клиенте 112ec13: [миграция нулевой дистанции и политики импорта](../supabase/migrations/20261107130531_allow_zero_distance_update.sql).

- Существующую запись разрешено обнулить через `update_manual_distance_entry`: сохраняются запись, ID, происхождение и комментарий, положительных `distance_values` не остаётся. Итоги и рейтинг учитывают 0; фильтр наличия записи продолжает считать её существующей. Новая ручная запись требует положительного значения. RPC принимает непустой массив корректных значений, включая все нули; null, пустой массив и неверные числа не означают команду очистки.
- Ручной редактор устанавливает `distance_entries.manual_override=true`. Миграция отмечает прежние ручные записи и записи с `updated_at > created_at`, сохраняя времена аудита.
- Оба импорта имеют `p_overwrite_manual boolean` и общий компонент `DistanceImportPolicy`. По умолчанию OFF: вся защищённая запись пропускается, включая отсутствующие лимиты. ON: заменяются только явно переданные лимиты, 0 удаляет соответствующий `distance_values`; комментарии и прочие лимиты сохраняются. Защита остаётся true. Старые сигнатуры RPC вызывают новые с false; права root не изменены. Новый файл сбрасывает переключатель.
- В обоих форматах CSV пустое количество не передаётся, явный 0 передаётся. Нулевой импорт не создаёт новую пустую запись. Обычные записи без ручной правки сохраняют добавление отсутствующих лимитов. Обновление метаданных Winamax отделено от защиты количества турниров.
- Редактор и импорт блокируют логическую запись `FOR UPDATE` перед изменением. `inserted` в ответе импорта считает фактически записанные/изменённые значения, включая разрешённое обнуление; неизменённые и защищённые значения входят в `skipped`. Проверки: [distance_zero_update.sql](../supabase/tests/distance_zero_update.sql).

Формат пока всегда `mtt` (экспрессо). Когда появится кэш — тот же стол, другое значение.

## Ключи, которые нельзя ломать

- **Человек** — `members.id`. Discord можно перепривязать в `identities`, человек тот же.
- **Один вход — один участник:** `members.auth_user_id` уникален.
- **Один Discord ID на провайдера:** `identities (provider, provider_uid)` уникален.
- **Метка**, если задана, уникальна в группе (`lower(mark_tag)`). Профиль может быть пустым, но новая `occupancy` требует непустые буквы метки целевого участника.
- **Пресеты столов** уникальны внутри участника и занимают позиции 1–5 без повторов значения; публичная RPC требует непустой набор.
- **ID в дистанциях**, если задан, уникален (`distance_ext_id`, только цифры). Пустой — норма. Пишет SQL `is_staff()` (admin/root), в кабинете нет.
- **Вид** уникален как набор рум + лимит + формат + вариант.
- **На уровне одна метка:** `occupancy (kind_id, slot_date, half, level)` уникален. Один человек может стоять на нескольких уровнях и видах **в тот же получас**. Часы считаем по уникальной паре дата+получас. Месяц сетки ищется по `(kind_id, slot_date)`. Слоты человека за месяц — индекс `(member_id, slot_date)`.
- **Лимит** — текст, не число: иначе `'0.25'` не ключ.
- **Один человек — один рум:** `players (member_id, room_id)` уникален.
- **Лимит на игроке** — набор `player_id + variant_id + limit_id`. Nitro 50 и Regular 50 — две строки.

## Что держит SQL сам

- Ставить слот может только `active`.
- На закрытый уровень поставить нельзя (триггер смотрит `hours_of`).
- Если на час заданы и число месяца, и день недели — берётся **минимум**.
- `save_schedule_filter_limits` проверяет `schedule.manage`, известность каждого ID в справочнике и наличие соответствующего `schedule_kind`; нормализует порядок по `limits.sort` и меняет оба вида в одной транзакции. Ошибка оставляет прежние массивы без изменений.
- `save_member_table_presets` проверяет владельца или `admin.people`, валидирует весь набор до записи и заменяет его атомарно. Прямые записи клиента в `member_table_presets` запрещены.
- Живое обновление нового клиента: единый private Broadcast `app:changes`, координаты участка → `load_schedule_snapshot_v2` после объединения100мс. Повторные чтения/версии и optional safety описаны в [едином документе](schedule-data-sync.md); полные30-секундные и принудительные10-секундные циклы исключены. Старый `schedule:changes`/v1 RPC сохранён для основного клиента. Журнал `occupancy_events` не опрашивается для Онлайн.
- `apply_schedule_edit` связывает защищённые `remove_foreign_slots` и `apply_own_slots` внутри одной серверной транзакции. Ожидаемые владельцы чужих слотов проверяются под `FOR UPDATE`; конфликт, истёкшее время, недопустимый набор, неполное выполнение, запрет записи или ошибка вставки отменяют весь диапазон и его события. Прямой доступ к функции закрыт для anon; серверные права постановки/снятия не ослаблены.
- Постановка и снятие пишут строку в `occupancy_events` (триггер). Сетка этот журнал не читает. Строки старше 2 месяцев удаляет ночной cron. Снятие чужой через `remove_foreign_slots` и замена через `replace_foreign_slots` тоже пишут журнал.
- Если чужую метку сняли (клик или замена), Edge Function `notify-mark-removed` пишет в клубный Discord-канал: какая метка, слот, кто снял — и в личку обоим. Галка в Root. Канал человека в кабинете и в карточке участника: Discord / Telegram / почта.

Права на строки: RLS, читает вошедший; писать слот — себе, либо SQL `is_staff()` (admin/root) за активного чужого `member_id`; `placed_by` ставит триггер (кто вошёл). Снять **чужую** метку с поля можно только функцией `remove_foreign_slots`, заменить — `replace_foreign_slots`, и только если соответствующая галка клуба включена — не общей политикой DELETE. Журнал читает admin/root, плюс человек видит события про свою метку или свои нажатия. Клиент в журнал не пишет. Ёмкость и роли — admin/root. Клубный статус `staff` этих прав **не** даёт.

## Назначения ID дистанции — модель от 6 ноября 2026

Миграция 20261106163724_member_distance_links добавляет member_distance_ids (ID → members.id, основной ID), member_distance_id_audit и distance_id_nicks (последний принятый ник по руму и ID). members.distance_ext_id сохраняется как совместимая проекция основного ID. Триггер поддерживает старые вставки/изменения этого поля в той же транзакции; новый клиент использует save_member_distance_ids с ожидаемым списком для защиты от устаревшего редактирования.

admin_people_snapshot отдаёт distance_ids. admin_distance_book и priority_source определяют владельца только по текущим назначениям. Исторические member_id/discord_id в distance_entries сохраняются как происхождение и не восстанавливают удалённую связь. create_club_card/self_create_profile/set_discord_access больше не копируют ID из старого справочника. Ручной part требует назначенный ID либо атомарно задаёт первый ID карточке без назначений.

save_distance_dump сохраняет факты без привязки к текущему человеку. remember_distance_nick обновляет метаданные при повторе и нулевой строке; refresh_member_distance_nick синхронизирует ник основного ID с player_nicks, сохраняя историю и provenance distance_ext_id. После изменения связей пересчитывается кэш текущих приоритетов. SQL-контракт member_distance_links.sql проверяет поздние назначения, несколько ID, смену основного, отвязку/перенос, повтор/нулевой импорт, права и отсутствие потери сумм.
