# Архитектура кода

## Общий административный редактор игрока

`AdminPersonEditor` соединяет существующие `AdminPersonCard` и вынесенный без изменения формы `MarkModal`; действия доступа и сохранения метки общие для `MembersAdmin` и расписания. `ScheduleMemberProfile` загружается лениво по нажатию, получает снимок через существующий `data/people.listAdminPeople`, выбирает точный memberId, показывает загрузку/ошибку/повтор и игнорирует поздний ответ после закрытия. Ни приватные данные, ни редактор не загружаются в расписании до разрешённого нажатия. `V2Shell` передаёт существующее право admin.people; обычная карточка знает только callback и доступность. Серверные запросы/права прежние, миграция не нужна.

## Фон слотов и подписи N/E — 4 ноября 2026

`schedule/slotAppearance.ts` задаёт строгий формат общего оттенка `{enabled,strength}` и значения по умолчанию. `data/limitPalette.ts` читает палитру и `slot_tint` одним запросом, редактор сохраняет их одной `save_schedule_appearance`; обе исходные версии защищают от конфликтов. Старый RPC только цветов остаётся совместимым. Demo записывает пару одним значением `redparty.demo.slot-appearance.v1`, при его отсутствии читает старую палитру.

Провайдер устанавливает `--slot-tint-strength`, линия передаёт свой `--slot-limit-tone`; CSS окрашивает только пустые открытые `data-future` независимо от личного затемнения прошлого. `PairLabel` отделяет префикс вида от цифр. Императивная плашка и canvas JPEG повторяют это представление, используя те же переменные темы. Новых библиотек нет.

Личное отключение слоя нагрузки хранится через `v2/slotHighlightPrefs.ts` (ключ среды + участника). `V2Shell` передаёт ключ, `useSchedulePreferences` читает/записывает флаг и сбрасывает его вместе с видом, `V2Settings` показывает переключатель, `V2Schedule` исключает карту нагрузки из входа поля. Клубный провайдер и данные не изменяются. `V2Float` ограничивает высоту доступным пространством под текущей координатой окна; длинное содержимое прокручивается внутри.

## Подсказка времени слота

`OptField` создаёт один `.v2-opt-frame-host` непосредственно в `document.body`, удаляет его при размонтировании. Фиксированный CSS-слой z1100 не зависит от обрезки/слоёв дней и строк. `optField/dom.ts` использует общую плашку для наведения и `showPick`: подпись вида/лимита, диапазон, палитра через корневые CSS-переменные. `showPick` оставляет в строке только рамку выделения; прежняя подпись `::before` удалена. Положение рассчитывается по границам слота/диапазона и ограничивается экраном; scroll/resize скрывают устаревшую плашку. Очистка отменённого жеста работает и без предшествующего наведения (touch). Цвета/рамка/фон задаются CSS; таймеров и постоянного цикла отрисовки нет.

## Нагрузка и общий выбор пары

`schedule/hourLoad.ts` хранит типизированные ID оттенков, ключ `variant:limit`, строгую валидацию 24 часов. Объединение фоновых сегментов удалено при переходе к внешней тени. `data/hourLoad.ts` читает общую карту, пишет одну пару защищённой RPC, подписывается на изменения; Demo имеет отдельный ключ v2, старый localStorage читается только для явного импорта. `ClubHourLoadProvider` защищает повторное чтение от устаревших ответов и передаёт карту в сетку/редактор.

`HourLoadEditor` вынесен из V2Admin; хранит независимые черновики и исходные строки пар. `SchedulePairPicker` — единый компонент выбора N/E для нагрузки, ёмкости и DeadTimeEditor. Он передаёт вид и лимит одним callback, не занимается сохранением.

`OptBody` передаёт каждой существующей клетке `data-load-tone` и CSS-переменную по точным виду/лимиту/часу, исключая закрытые уровни. Внешний `box-shadow` на клетке заменяет прежние CSS-spans; дополнительных узлов нет. Глобальный градиент первого выбранного лимита удалён. Разделители и отступы синхронны у поля и левой колонки. Кэш подсказки `optField/dom.ts` учитывает полный текст пары/диапазона, поэтому переход на другой лимит в том же часу обновляет подпись.

## Общая палитра лимитов

`src/schedule/limitPalette.ts` содержит формат, стандартные цвета, валидацию, CSS-переменные и контраст. `src/data/limitPalette.ts` отдельно читает палитру из `schedule_settings`, сохраняет через защищённую RPC и подписывается на обновления; Demo использует свой localStorage. Старое чтение флагов расписания не зависит от новой колонки.

`ClubLimitPaletteProvider` в оболочке устанавливает общие CSS-переменные на корне документа, включая окна в порталах. `LimitPaletteEditor` — последний, изначально свёрнутый блок настроек расписания; он хранит изолированный черновик и исходную версию для проверки конкурирующих правок. React-компоненты не обращаются к Supabase напрямую. Основная сетка и календарь читают цвета через `--limit-*`; JPEG получает вычисленные переменные текущей темы, без отдельной палитры экспорта.

Канонический продукт — `apps/web`. Папка `sandbox/ui` остаётся лабораторией и не должна становиться вторым источником бизнес-логики.

## Границы модулей

- `App.tsx` передаёт существующий флаг `hydrated` в первоначальный `V2BootScreen`: сервер и первый клиентский кадр используют одинаковый RU, после подключения клиента применяется сохранённый язык. Это устраняет hydration mismatch при перезагрузке EN; последующие загрузочные экраны остаются на выбранном языке.

- `src/data` — ввод-вывод и преобразование DTO. Один пользовательский сценарий по возможности вызывает один RPC.
- `src/schedule/priorities.ts::priorityBreakdown` преобразует шесть месячных сумм в Nitro/Regular × два периода ×50/100: месячные турниры, суммарная дистанция, веса и очки. `calculatePriority` собирает из тех же слагаемых четыре чистых `distanceCells` и четыре взвешенных `pointCells`, а `total` суммирует только очки; `PriorityCalculation` только отображает последовательные блоки, включая ограничение выбранной ячейки.
- `PrioritySnapshotRows` в `PriorityCalculation.tsx` отображает четыре чистые дистанции и взвешенный итог сохранённой строки заявки. `LivePriorities` восстанавливает их существующей `rankPriorities` только из `detail.snapshot` и использует один результат для верхнего слепка и нижних подробностей; актуальный список дистанций сюда не подмешивается.
- `src/schedule/priorities.ts` — чистая формула50/100, шестимесячные периоды, чистое ранжирование по очкам и фильтрация после расстановки. Явный режим `legacy-vip-seats` нужен только для исторических снимков заявок. `src/data/priorities.ts` содержит защищённые RPC и отдельный Demo-контракт; `priorityRefresh.ts` уведомляет открытые вкладки после успешной записи дистанций. `V2Priorities` ведёт в `LivePriorities`, а `PriorityCalculation` одинаково раскрывает текущие и сохранённые расчёты. Предметная логика в React не дублируется; старый `prioritiesData.ts` больше не подключён.
- `src/schedule/roster.ts::orderRosterRows` задаёт очередь Core выбранного вида/группы → очки → ник/ID, исключённых оставляет без номера. Локально4 ноября2026 `src/v2/schedule/useRosterSource.ts` получает компактный рейтинг и прежний справочник через `data/roster.ts::createRosterLoader`; `load_month_roster` объединяет их в один условный ответ. `data/rosterRefresh.ts` объединяет события и сохраняет invalidation во время чтения. Поздние ответы другого периода/вида/группы не применяются; кэш принадлежит экрану/аккаунту. `V2Schedule` группирует часы только выбранной вкладки очереди; прямого доступа к БД нет.
- `src/schedule` — чистая предметная логика без React, DOM и Supabase; она покрывается unit-тестами.
- `src/v2/*Model.ts` — чистая логика конкретного экрана и форматирование представления.
- `src/v2/*.tsx` — компоненты, состояние экрана и события пользователя. Прямые запросы к таблицам здесь не размещаем.
- `src/components/ui/dialog.tsx` задаёт общий каркас диалога: отдельные шапка, прокручиваемое содержимое и footer. Мобильная плотность этого каркаса и исторических v2-модалок согласована общим media-контрактом в `src/v2/v2.css`, без второй мобильной реализации компонентов.
- `src/data/distanceBook.ts` собирает DTO контроля из `admin_distance_book`, объединяет активных участников с логическими `distance_entries`, считает нулевые состояния и формирует безопасный CSV. В Working создание и редактирование part из React идут только через транзакционные RPC; в Demo тот же контракт работает на отдельном снимке в памяти вкладки.
- Фильтры контроля применяет чистая `filterDistancePeople`: роль RedParty и активная анкета — независимые серверные признаки, наличие записей проверяется только по выбранным видам турниров. История может связаться с текущей играющей карточкой через `profile_member_id` из read-model, без изменения исторических фактов. `V2DistanceBook` защищает загрузку номером запроса и текущим месяцем/румом, скрывает прежний снимок и действия до готовности нового, не закрывает новую форму ответом от уже закрытой. Demo содержит текущие анкеты, историю RedParty без анкеты и внешнюю историю; ID срезов уникальны между месяцами и румами.
- `PersonBlock` контроля возвращает отдельный `tbody` участника с дочерними part, применяет крайние классы первой/последней строки и сохраняет плотность 26/24 px. Общий `PersonAvatar` имеет локальное состояние ошибки изображения; изменение URL пересоздаёт состояние, отсутствие/ошибка заменяются декоративными инициалами без изменения размеров. Фото и актуальное имя исторического участника приходят в DTO из защищённого read-model, React не запрашивает Supabase напрямую.
- `supabase/migrations` — транзакционные операции, права и серверные read-модели.
- `supabase/functions` — внешние интеграции; они не дублируют правила доступа из БД.

## Работа с БД

Для табличного списка заявок публичная `list_priority_requests` по-прежнему возвращает только безопасную сводку. `src/data/priorities.ts::loadPriorityRequestAuthors` читает авторов через существующую административную `get_priority_request` партиями до8 запросов; UI вызывает его только при открытом административном списке. Обычному пользователю этот путь не вызывается. Поколение эффекта отбрасывает результат после закрытия/смены списка; авторы и исходные комментарии не добавляются в публичный DTO.

1. Составная запись в несколько таблиц выполняется одной функцией PostgreSQL и одной транзакцией.
2. Экран получает согласованный срез нескольких таблиц одним read-model RPC.
3. Права проверяются внутри RPC и остаются продублированы RLS-политиками.
4. UI не выполняет циклы `insert/update/delete`; после записи допустим один повторный read.
5. Старые роли `member/admin` не используются для расписания. Источник истины — Discord-роли и `member_has_schedule_limit`.
6. Активный путь чтения — `src/data/scheduleSnapshot.ts`, без перехода на прямые запросы при отсутствии RPC. Старые helpers чтения в `slots.ts` не подключены к экрану; старую серверную RPC сохраняем для ранее опубликованного клиента. Все клиентские пути записи делегируют транзакционной `apply_schedule_edit`.

## Внешний API

`supabase/functions/external-api` — отдельная серверная точка машинных интеграций, локально реализованная3 ноября2026. `index.ts` запускает функцию; `app.ts` задаёт явные маршруты и HTTP-границы; `core` содержит общие ключи/ошибки/вызов RPC, `v1/schedule` — валидацию, DTO, календарное время и JSON. Будущие ресурсы получают собственный модуль и право доступа. React и клиентские функции `src/data` здесь не импортируются.

`external_api_schedule` доступна только внутренней service_role и работает как SECURITY INVOKER. Она проверяет SHA-256 индивидуального ключа, scope и атомарную минутную квоту через закрытую схему `external_api_private`, затем одним SQL-срезом читает существующие occupancy и текущие метаданные. Первый запрос материализует страницы по1000 меток в приватных `snapshots`/`snapshot_pages` одним `INSERT/SELECT`, фиксируя и состав, и метаданные. Следующие cursor-запросы читают только этот снимок с тем же клиентом после повторной авторизации; TTL15мин, очистка cron5мин. Возвращается скалярный JSON страницы, чтобы табличный max_rows не обрезал данные. Никакой долгой открытой транзакции между HTTP-запросами нет. Это отдельный контракт чтения для бота, а не второй механизм хранения/редактирования расписания; прежняя пользовательская RPC не ослаблена. Подробности и ограничения: [API README](../supabase/functions/external-api/README.md).

## Размер и разбиение

- Ориентир для компонента — до 400–500 строк.
- DOM-механика, форматирование и вычисления выносятся до добавления новой функции.
- Повторяемое представление выносится в компонент, предметное правило — в чистую функцию, составная запись — в RPC.

Расписание разделено по ответственности 4 октября 2026. `V2Schedule.tsx` собирает экран, связывает выбранные пары, статистику и окна; `OptField.tsx` собирает поле и его жизненный цикл. Обработчики вынесены с сохранением существующих алгоритмов, CSS-классов, адресов ячеек, RPC и локальных ключей хранения.

Следующие кандидаты отдельной работы: `MembersAdmin.tsx` и `V2Cabinet.tsx`. Дальнейшее уменьшение координатора `V2Schedule.tsx` допустимо по самостоятельным сценариям, но не ради формального количества строк. Не создаём универсальные компоненты без реального повторного использования.

## Модули экрана расписания

Модули находятся в [`src/v2/schedule`](../apps/web/src/v2/schedule). React-hooks управляют сценарием экрана, а запросы по-прежнему выполняют существующие функции `src/data`.

| Модуль | Ответственность |
|---|---|
| `useScheduleMonth.ts` | Жизненный цикл месяца Demo/Working, подписка до чтения, reconnect/focus и резервный опрос |
| `scheduleSync.ts` | Объединение уведомлений по дню/виду/лимиту, одно чтение за раз, очередь новых событий и повтор ошибок |
| `scheduleMonthState.ts` | Отдельный экземпляр на месяц: серверная основа, справочник, поколения чтения, последовательная очередь записи и слои optimistic-правок |
| `useScheduleMutations.ts` | Разница слотов, optimistic-запись и откат, проверка выбранной игровой пары, подтверждение чужих меток и уведомление |
| `useScheduleBrush.ts` | Собственный профиль и кисть другого игрока, эффективные права, справочник игроков, пресеты столов и их выбранное значение |
| `useScheduleRules.ts` | Клубные настройки, разрешённые лимиты фильтра и правила мёртвого времени с подписками |
| `useSchedulePreferences.ts` | Начальные локальные предпочтения, их состояние и сброс; чтение начального объекта один раз на монтирование |
| `useScheduleToolbar.ts` | Состояние меню, поиск, DOM-ссылки и закрытие меню при внешнем клике / Escape |
| `ScheduleToolbar.tsx` | Панель месяца, видов, лимитов, поиска, кисти и инструментов |
| `ScheduleRoster.tsx` | Таблица активных и исторических игроков месяца; открытие карточки передаётся координатору |
| `ScheduleViewSettings.tsx` | Связь существующего `V2Settings` с локальными предпочтениями и действиями окна |
| `constants.ts` | Стабильный порядок Nitro / Regular для полного снимка и календаря |

Состояние месяца принадлежит одному экземпляру `ScheduleMonthState`, созданному в `useScheduleMonth` для конкретных года и месяца; `useScheduleMutations` получает именно его. Поздняя запись может завершиться только в своём экземпляре. Чистая логика `src/schedule/gridEdits.ts` описывает и применяет изменения клеток, сохраняя остальную сетку. Нельзя заводить второй store или отдельные счётчики записи внутри окна. Кисть другого игрока не меняет собственную идентичность личного календаря.

## Стартовая навигация

`apps/web/src/v2/shellNavigation.ts` — чистая точка выбора стартового и fallback-раздела по доступу, роли, разрешениям и hash-ссылке. `V2Shell` применяет этот результат, но не дублирует матрицу разрешений в обработчиках. Для активного пользователя с правом расписания канонический старт и действие логотипа — `schedule`; портал-главная в рабочем маршруте не участвует.

## Локальные фильтры приоритетов

`apps/web/src/v2/priorityFilterPrefs.ts` проверяет формат и читает/пишет роли и два признака активности. `V2Shell` формирует ключ по ID участника и среде; `LivePriorities` восстанавливает выбор при открытии и сохраняет его при действиях пользователя. При смене аккаунта компонент пересоздаётся, настройки не смешиваются. Недоступное localStorage не мешает текущей фильтрации. Серверный состав и расчёт не зависят от этих предпочтений.

## Локальные предпочтения расписания

`apps/web/src/v2/prefs.ts` — единственная точка чтения и записи `v2-schedule-prefs`. Объект имеет версию, при чтении проходит нормализацию, а старые и повреждённые значения безопасно мигрируют к актуальному контракту.

| Поле | Назначение | Значение по умолчанию |
|---|---|---|
| `limits` | выбранные лимиты фильтра | `50` |
| `kinds` | один или два выбранных вида в стабильном порядке Nitro, Regular | `nitro` |
| `editPulse` | визуальный акцент режима правки | включён |
| `showExtraTz` | дополнительный пояс | включён |
| `busyHint` | подсветка пересечений | выключена |
| `dimPast` | приглушение прошлого | включено |
| `hidePastDays` | скрытие прошедших дней | выключено |
| `displayRange` | день / 3 дня / 7 дней / неделя / месяц для текущего месяца CET | `month` |
| `hideTables` | локально скрыть числа столов | выключено |
| `showTip` | карточка слота | включена |

`month` и `pin` пока сохраняются в типе только для миграционной совместимости; скрытый блок кабинета их больше не редактирует, а загрузка всегда нормализует значения к текущему месяцу. Общие клубные правила и данные профиля в этот объект не входят.

Чистая функция `schedule/displayRange.ts` рассчитывает числа видимых дней независимо от React. `OptField` фильтрует только представление и продолжает адресовать сетку по реальному индексу `day - 1`, поэтому скрытие строк не сдвигает данные и запись слотов.

## Состояние сеток нескольких видов

`src/data/scheduleSnapshot.ts` получает полный месяц Nitro и Regular одной RPC `load_schedule_snapshot`. Компактные слоты содержат `kind_id, day, half, level, member_id, tables`; каталог видов/лимитов и справочник владельцев передаются отдельно, без повторения имён в каждом слоте. `src/schedule/mergeScheduleSnapshot.ts` соединяет их в клиентское хранилище `variant:limit`. Полный месяц обоих видов нужен личному календарю и предупреждению о скрытых сменах; фильтр меняет представление, а не полноту снимка.

Скалярный JSON обходит табличный предел Data API в 1000 строк. Декодер проверяет период, количество, уникальность координат, ссылки на виды и владельцев; повреждённый ответ не превращается в частичный месяц. Начальная загрузка теперь содержит один пакет (прогресс 0/1); до готовности `ScheduleLoading` скрывает поле через `inert`, ошибка предлагает повтор. Успешный снимок того же месяца остаётся видимым при фоновых запросах.

`V2Schedule` хранит месяц в этом составном хранилище. Основная сетка строит группировку дата → вид → лимит → уровень прямо поверх составных ключей. Для вспомогательных окон `variantSchedule.ts` создаёт стабильную проекцию выбранных пар с ключом `variant:limit` и пользовательской подписью `N50`/`E50`; все агрегаторы получают одну и ту же проекцию. Запись основной сетки передаёт вид вместе с лимитом, поэтому изменение `regular:50` не затрагивает `nitro:50`.

Каждый месяц имеет собственную основу. Записи выполняются последовательно, видимый снимок состоит из подтверждённой основы и незавершённых правок клеток. Private Broadcast `schedule:changes` передаёт `slots {date, kind_id}` либо `directory`. `ScheduleSync` объединяет участки за 100 мс без бесконечного переноса таймера, ждёт окончания своих записей и делает одно чтение за раз. События во время запроса остаются в очереди. Ответ, начатый до локальной правки, отбрасывается и перечитывается. Пустой ответ участка очищает его, включая удаление последней метки; остальные дни и лимиты сохраняются.

Подписка начинается до первого чтения; через секунду без подключения запускается резервная начальная загрузка. Восстановление подписки, сети или возврат во вкладку запускают полный месяц для устранения пропущенных событий. Пока канал отключён, видимая вкладка опрашивает месяц раз в 10 секунд. Ошибка фонового чтения сохраняет данные и повторяется с задержкой 2–15 секунд. Изменение справочника перечитывает только владельцев месяца и обновляет их отображение во всех клетках, сохраняя число столов каждого слота.

Любой жест, включая постановку и снятие, использует `src/data/slots.ts → applyScheduleEdit → apply_schedule_edit`. Собственные удаления, чужие удаления с проверкой ожидаемых владельцев и постановки проходят в одной транзакции. Прежние helpers записи делегируют той же функции. Предварительный слой остаётся быстрым, но тост успеха появляется только после ответа транзакции; конфликт откатывает конкретную операцию, сохраняя соседние успешные операции очереди. Серверного кэша нет: RPC читает актуальные `occupancy` и профили в одном SQL-срезе.

`myShifts.ts` представляет предупреждения «Другие лимиты» матрицей пар `{ variant, limit }`. Занятость берётся из полного клиентского месяца с optimistic-правками; отдельного повторного запроса своих слотов больше нет. `OptField` исключает уже видимые пары и передаёт скрытую пару в DOM как `variant:limit` для полной подсказки.

Постатейная статистика хранит часы отдельно для каждой пары, а общий итог строится по множеству ключей `день:получас`. Поэтому одновременная занятость Nitro и Regular видна в детализации, но не удваивает фактическое время игрока. Личный календарь и JPEG показывают все пары на одной компактной временной дорожке дня; редкие пересечения накладываются.

### Панель внешнего API

Лениво загружаемый root-only `src/v2/api/ApiAdmin.tsx` содержит создание, карточки подключений и модальные инструкции. `src/data/externalApi.ts` отвечает за Web Crypto, RPC и эфемерный Demo; React не обращается к Supabase напрямую. Raw key остаётся только в состоянии окна выдачи и очищается при закрытии; сервер получает хеш. Live ошибки не заменяются Demo. Открытая root RPC работает без повышенных прав и делегирует закрытой функции с серверной проверкой роли. Внешний бот не использует административный маршрут.

«Онлайн» подключён к правой части шапки через OnlineMenu. Компонент отправляет сигнал присутствия через src/data/online.ts, а список запрашивает только при открытом диалоге. Сервер формирует краткую сводку из member_presence и журнала правок расписания.


Компактный HTTP-контракт v1 сериализуется явным списком полей поверх прежнего внутреннего снимка. Пример `apps/web/src/v2/api/scheduleExample.json` используется обеими инструкциями Root; API-тест сверяет его с сериализатором и OpenAPI. Сборка функции не импортирует UI или пример.
