# Архитектура кода

Канонический продукт — `apps/web`. Папка `sandbox/ui` остаётся лабораторией и не должна становиться вторым источником бизнес-логики.

## Границы модулей

- `src/data` — ввод-вывод и преобразование DTO. Один пользовательский сценарий по возможности вызывает один RPC.
- `src/schedule` — чистая предметная логика без React, DOM и Supabase; она покрывается unit-тестами.
- `src/v2/*Model.ts` — чистая логика конкретного экрана и форматирование представления.
- `src/v2/*.tsx` — компоненты, состояние экрана и события пользователя. Прямые запросы к таблицам здесь не размещаем.
- `src/data/distanceBook.ts` собирает DTO контроля из `admin_distance_book`, объединяет активных участников с логическими `distance_entries`, считает нулевые состояния и формирует безопасный CSV. В Working создание и редактирование part из React идут только через транзакционные RPC; в Demo тот же контракт работает на отдельном снимке в памяти вкладки.
- `supabase/migrations` — транзакционные операции, права и серверные read-модели.
- `supabase/functions` — внешние интеграции; они не дублируют правила доступа из БД.

## Работа с БД

1. Составная запись в несколько таблиц выполняется одной функцией PostgreSQL и одной транзакцией.
2. Экран получает согласованный срез нескольких таблиц одним read-model RPC.
3. Права проверяются внутри RPC и остаются продублированы RLS-политиками.
4. UI не выполняет циклы `insert/update/delete`; после записи допустим один повторный read.
5. Старые роли `member/admin` не используются для расписания. Источник истины — Discord-роли и `member_has_schedule_limit`.
6. Fallback на старую схему удаляется после раскатки миграции.

## Размер и разбиение

- Ориентир для компонента — до 400–500 строк.
- DOM-механика, форматирование и вычисления выносятся до добавления новой функции.
- Повторяемое представление выносится в компонент, предметное правило — в чистую функцию, составная запись — в RPC.

Следующие кандидаты разбиения: `V2Schedule.tsx`, `MembersAdmin.tsx`, `V2Cabinet.tsx` и визуальная часть `OptField.tsx`. Их делим по пользовательским блокам, не создавая универсальные компоненты без реального повторного использования.

## Стартовая навигация

`apps/web/src/v2/shellNavigation.ts` — чистая точка выбора стартового и fallback-раздела по доступу, роли, разрешениям и hash-ссылке. `V2Shell` применяет этот результат, но не дублирует матрицу разрешений в обработчиках. Для активного пользователя с правом расписания канонический старт и действие логотипа — `schedule`; портал-главная в рабочем маршруте не участвует.

## Локальные предпочтения расписания

`apps/web/src/v2/prefs.ts` — единственная точка чтения и записи `v2-schedule-prefs`. Объект имеет версию, при чтении проходит нормализацию, а старые и повреждённые значения безопасно мигрируют к актуальному контракту.

| Поле | Назначение | Значение по умолчанию |
|---|---|---|
| `limits` | выбранные лимиты фильтра | `50` |
| `kinds` | один или два выбранных вида в стабильном порядке Nitro, Regular | `nitro` |
| `editPulse` | визуальный акцент режима правки | включён |
| `showExtraTz` | дополнительный пояс | включён |
| `busyHint` | подсветка пересечений | выключена |
| `dimPast` | приглушение прошлого | включено |
| `hidePastDays` | скрытие прошедших дней | выключено |
| `hideTables` | локально скрыть числа столов | выключено |
| `showTip` | карточка слота | включена |

`month` и `pin` пока сохраняются в типе только для миграционной совместимости; скрытый блок кабинета их больше не редактирует, а загрузка всегда нормализует значения к текущему месяцу. Общие клубные правила и данные профиля в этот объект не входят.

## Состояние сеток нескольких видов

`src/data/slots.ts` загружает каждый выбранный вид отдельным вызовом существующего `load_month_schedule` и собирает клиентское хранилище с ключом `variant:limit`, например `nitro:50` и `regular:50`. Третий смешанный серверный вид не создаётся. Результат отдельно содержит успешно загруженные виды и ошибки по каждому виду, поэтому сбой Regular не интерпретируется как пустое успешное расписание и не затирает уже показанные данные Nitro.

`V2Schedule` хранит месяц в этом составном хранилище. Основная сетка строит группировку дата → вид → лимит → уровень прямо поверх составных ключей. Для вспомогательных окон `variantSchedule.ts` создаёт стабильную проекцию выбранных пар с ключом `variant:limit` и пользовательской подписью `N50`/`E50`; все агрегаторы получают одну и ту же проекцию. Запись основной сетки передаёт вид вместе с лимитом, поэтому изменение `regular:50` не затрагивает `nitro:50`.

Постатейная статистика хранит часы отдельно для каждой пары, а общий итог строится по множеству ключей `день:получас`. Поэтому одновременная занятость Nitro и Regular видна в детализации, но не удваивает фактическое время игрока. Личный календарь и JPEG раскладывают такие пары по независимым дорожкам.
