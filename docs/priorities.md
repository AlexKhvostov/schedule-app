# Приоритеты и матрица Core

Актуальные правила согласованы Алексеем4 ноября2026. Версия опубликована в main4 ноября2026; миграция20261104145020 применена к Working. Она заменяет прежний общий расчёт Nitro+Regular и добавляет сохранённые результаты. Предыдущие опубликованные версии и проверки описаны в `docs/work-log.md` и отчётах памяти. [План и проверки](../memory/tasks/2026-11-04-priority-matrix.md).

## Независимые срезы

По уточнению Алексея4 ноября2026 переключатели оформлены двумя отдельными подписанными кнопочными блоками: «Вид турниров» сверху, «Группа лимитов» снизу. В каждом выбирается ровно один вариант; активный выделен заливкой и рамкой. Одинаковое оформление применяется в Приоритетах и Игроках месяца, где недоступные значения остаются видимыми. Клавиатурное управление и сохранение выбора сохранены. Входит в разрешённый4 ноября выпуск матрицы приоритетов.

Два независимых выбора, по одному значению в каждом:

- вид турниров: Nitro / Regular;
- группа лимитов:50–100 /250.

В50–100 входят **строго50 и100**, только выбранного вида, только Winamax. Идея «100 и выше» отменена пользователем. В250 пока не рассчитываются дистанции и баллы: виден список, сначала положительный Core по возрастанию, остальные по нику. В интерфейсе нет фиктивных нулевых дистанций250; подробности объясняют отсутствие расчёта.

У каждого участника четыре независимых Core: Nitro50–100, Regular50–100, Nitro250, Regular250. Старые номера становятся Core50–100 без переноса/перенумерации. Номер положительного Core уникален внутри соответствующей пары вид × группа;0 означает отсутствие. Надписи одинаковы в RU/EN: `Core 1`, `Core 12`.

## Расчёт50–100

`очки месяца = турниры50 ×1 + турниры100 ×2`

| Начало действия | Старшие три месяца ×0,5 | Младшие три месяца ×1 |
|---|---|---|
| Февраль | Август–октябрь предыдущего года | Ноябрь–январь |
| Май | Ноябрь–январь | Февраль–апрель |
| Август | Февраль–апрель | Май–июль |
| Ноябрь | Май–июль | Август–октябрь |

Четыре колонки — чистые дистанции50/100 старшего и младшего периодов. Итог — взвешенные очки: старший50 ×0,5 + старший100 ×1 + младший50 ×1 + младший100 ×2. Очки показываются с одним десятичным знаком, половина очка сохраняется. Все части (`part`) суммируются. Другой вид и другие лимиты не участвуют.

Наведение, клик по ячейке, полный расчёт и исходные записи показывают **тот же выбранный вид и группу**. Подсказка и клик по любой дистанции периода показывают сразу50 и100 за его три месяца: два столбца, коэффициенты и общий итог периода. Подсказка заголовка периода объясняет формулу. Полный расчёт показывает месяцы, коэффициенты, сумму и исходные части. Старые снимки заявокv1/v2 продолжают показывать прежний общий расчёт обоих видов.

До8-го числа начала периода статус предварительный. Далее для основного статуса нужно20 логических записей последнего исходного месяца **выбранного вида**, со значениями50/100. Части считаются разными записями, два лимита одной части — одной записью. Несвязанные с карточкой записи тоже входят в этот контроль загрузки. У250 такого статуса нет.

## Сохранение и обновление

`priority_rating_cache` хранит готовые расчёты и исходные факты на период × вид × группу. Валидное чтение не сканирует дистанции и не пересчитывает баллы. Авторизация не хранится в общем кэше: `canManage` проверяется для каждого вызывающего.

Изменение, импорт или удаление дистанции помечает устаревшими только существующие результаты50–100 соответствующего вида, чьё шестимесячное окно затронуто. Следующее чтение один раз пересчитывает и сохраняет результат. Строковая блокировка не даёт двум чтениям одновременно пересобирать один срез. Новый квартал создаётся при первом чтении; cron не требуется.

Изменения карточек, привязки дистанций, ролей, лимитов и Core обновляют состав/метаданные; неизменённые исходные записи переиспользуют сохранённые месяцы и баллы. Служебные отметки времени синхронизации сами по себе не вызывают обновления. Дата Europe/Minsk и права актуальны на каждом чтении.

Кнопка «Обновить приоритет» доступна staff/admin/root и принудительно обновляет **текущий период, вид и группу**. Сервер отвергает ручной вызов обычного игрока. В интерфейсе показано время сохранения текущего результата. Открытый экран проверяет изменения каждые30 секунд, при фокусе и по сигналу записи дистанции. Обычная проверка получает сохранённый результат; фонового задания при закрытом приложении нет.

## Состав и порядок

Базовый список — все `members`, в том числе без выбранных лимитов, Winamax, игровых ролей и активной карточки. Discord без карточки members в список не добавляется. Отпуск не исключает участника.

Фильтры:

- роли Discord: любая из выбранных, пустой выбор — все; каталог содержит только действующие роли с правами приложения или разрешёнными лимитами;
- «Активны в расписании»: есть выбранные лимиты Winamax текущего **вида и группы**; календарные метки не проверяются;
- «Активная карточка»: отдельный фильтр профиля.

Роли проверяются по текущему Discord-снимку с fallback на identity; ушедший с сервера не имеет активных ролей. Фильтры, вид и группа сохраняются в браузере отдельно для аккаунта/среды. Недоступную сохранённую роль можно снять. Отчётный период при новом открытии текущий; синхронизации между устройствами нет.

В таблице50–100 порядок по очкам, затем нику/ID; Core показывается справочно и не меняет места. В250 порядок по Core, затем нику/ID. Галка «Показывать Core» меняет только отображение. Фильтры не перенумеровывают глобальные места. Исключённые идут в конце без места; существующее исключение по виду действует на обе группы. Сервер запрещает сочетание исключения и положительного Core этого вида в любой группе.

«Игроки месяца» использует Core и очки выбранной пары. Сначала положительные Core по возрастанию, затем очки и ник; для250 после Core только ник. Состав/часы по-прежнему определяются выбранными фильтрами расписания. Обе группы и оба вида всегда видны; недоступные текущим фильтрам значения disabled. Если фильтры включают100 и250, обе группы доступны. Снятие Regular оставляет его кнопку видимой, но недоступной. Исторические строки не получают текущий номер.

Оптимизация4 ноября2026 (опубликована вmain656806e): окно использует `load_month_roster`, проекцию существующего кэша с четырьмя полями человека — `memberId/core/score/excluded`. Справочник имён/меток приходит в том же запросе через прежний `schedule_player_directory`. У двух массивов независимые ревизии: `null` в ответе означает «использовать прежний массив с этой версией», `[]` означает пустой состав. Дата/статус/время расчёта приходят всегда. Изменение имени или метки обновляет справочник независимо от очков; права проверяются при каждом запросе. Окно не получает исходные дистанции и месячные расчёты. Сортировка, фильтры состава и период выбранного месяца сохранены.

Клиент хранит до8 результатов только в памяти текущего экрана/аккаунта, объединяет одновременные чтения и события за100мс. Сигнал изменения во время запроса вызывает одну последующую проверку. Опрос30секунд действует лишь при открытом окне и видимой вкладке; возврат вкладки обновляет данные. Закрытие окна сохраняет локальные версии до ухода со страницы для условного чтения при открытии. Ошибка показывает прежнее сообщение/повтор, а не пустую очередь. Подробности — в [отчёте](../memory/tasks/2026-11-04-compact-month-roster.md).

## Заявки и совместимость

«Сообщить о неточности» с восклицательным знаком позволяет выбрать1–50 участников и написать комментарий до2000 знаков. Это обращение на проверку, не изменение дистанций/Core.

Новый `submit_priority_slice_request` сверяет ревизию и точное равенство выбранных фактов с текущим срезом. Снимокv3 содержит группу, время сохранения, исходные записи, готовые расчёты, состав и Core. Заявка остаётся неизменной после правок. Публичный список показывает участников, вид/группу, даты, статус и ответ; автор и комментарий доступны только staff. Закрытие и удаление защищены сервером.

v1 сохраняет прежние точные Core-места (`legacy-vip-seats`), v2 — прежний общий рейтинг по дистанции. Их данные и алгоритм не переписываются. Старые RPC остаются совместимыми; вкладка «Приоритеты» использует `load_priority_slice` и снимкиv3; локально окно игроков использует его компактную проекцию через `load_month_roster`.

Период расположен сверху, сводка и служебное обновление отдельно от фильтров. По уточнению Алексея отступы и элементы компактны, на узком экране группы переносятся без смешения назначения.
