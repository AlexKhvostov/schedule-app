# Среды и текущее устройство приложения

Зафиксировано **25 сентября 2026**. Это основная сводка решений, принятых во время аудита, оптимизации и подготовки приложения к дальнейшей разработке.

## Три среды

| Среда | Статус сейчас | Данные | Вход | Для чего |
|---|---|---|---|---|
| **Demo** | Работает локально | Фейковые карточки в коде и хранилище браузера | Выбор тестового пользователя | Интерфейс, роли, расписание и автоматические UI-тесты без риска для базы |
| **Working / Development** | Работает | Текущий Supabase `wvfllegshaqonqqpbtle` | Настоящий Discord OAuth | Миграции, серверные права, Edge Functions и интеграционные проверки во время разработки |
| **Production** | Проекта ещё нет | Будущая чистая база | Настоящий Discord OAuth | Публичная работа с настоящими пользователями |

Переключатель сред показывается только в локальной development-сборке. В опубликованном приложении выбора Demo и Working быть не должно: оно подключается к одной среде, заданной при сборке.

### Demo

Demo — не отдельная база. Исходные карточки находятся в `apps/web/src/schedule/members.ts`, а изменения сохраняются только в `localStorage` браузера. Демо-расписание общее для всех тестовых пользователей в этом браузере: поставленная одним пользователем метка видна после выхода и входа под другим. В настройках расписания есть сброс всех локальных изменений к исходному демонстрационному плану. Выбранный пользователь и признак деморежима живут в `sessionStorage` вкладки. Supabase и Discord в этом режиме не вызываются.

Расписание создаётся детерминированно функцией `demoMonthPlan`: одинаковые исходные данные дают одинаковый результат. Это делает Demo подходящим для разработки интерфейса и повторяемых E2E-тестов.

Demo не доказывает правильность миграций, RLS (серверных правил доступа), Discord OAuth или Edge Functions. Эти части проверяются на Working.

### Working / Development

Текущий Supabase пока считается рабочей базой разработки, даже если в старых местах он назывался production. Живых пользовательских данных в нём ещё нет, поэтому редактирование не блокируется.

Здесь проверяем:

- настоящий вход через Discord;
- правила доступа базы;
- миграции и составные RPC-операции;
- общий слепок Discord;
- серверные функции и уведомления;
- интеграцию интерфейса с настоящей схемой данных.

### Production

Перед публичным запуском создаётся новый чистый Supabase-проект. В него применяются все миграции из репозитория и необходимые справочные данные, но не копируются накопившиеся тестовые записи Working.

После этого:

1. текущий проект окончательно становится Development/Staging;
2. новый проект становится Production;
3. у проектов отдельные URL, ключи, секреты и разрешённые адреса возврата Discord;
4. опубликованное приложение подключается только к Production;
5. мутационные тесты никогда не запускаются против Production.

## Вход и обновление Discord

Discord OAuth подтверждает личность. Роли и присутствие на сервере предоставляет бот через таблицы слепка.

Текущий алгоритм:

1. Без сохранённой сессии приложение сразу показывает вход и не делает сетевой запрос авторизации.
2. После нового возврата от Discord выполняется одна точечная проверка текущего человека через `discord-member-check`.
3. При восстановлении уже действующей сессии прямого обращения в Discord нет: приложение читает сохранённый слепок и профиль из Supabase.
4. Полный состав сервера обновляет `discord-guild` автоматически каждые 10 минут и вручную по команде администратора.
5. Полный успешный слепок блокирует активный профиль, если человек вышел или потерял обязательную роль RedParty. Неполный или ошибочный ответ Discord никого не блокирует.
6. Если точечная проверка нового входа временно не отвечает, используется последний слепок.

Это ограничивает задержку отзыва доступа примерно десятью минутами и не создаёт индивидуальный запрос в Discord при каждой перезагрузке страницы.

## Архитектура данных после оптимизации

- React-компоненты не собирают сложные данные множеством несвязанных запросов. Ввод-вывод находится в `src/data`.
- Админский список людей получает согласованный снимок через `admin_people_snapshot`.
- Справочник игроков расписания получает готовую серверную выборку через `schedule_player_directory`.
- Составные сохранения игровых профилей и платёжных методов выполняются атомарными RPC: либо сохраняется вся операция, либо ничего.
- Месяц расписания загружается одним `load_month_schedule`; постановка диапазона выполняется `apply_own_slots`.
- Права проверяются сервером, а не только скрытием кнопок в интерфейсе.
- Discord ID связывает внешний слепок с клубной карточкой, но не является внутренним ID участника.

Подробные границы модулей: [code-architecture.md](code-architecture.md). Таблицы и RPC: [database.md](database.md).

## Интерфейс и скорость запуска

- До появления приложения показывается отдельный экран проверки входа, а не пустой фон.
- Для вышедшего пользователя наличие сессии определяется локально, без ожидания сервера.
- Большие разделы загружаются только при открытии, поэтому стартовый пакет меньше.
- Фон строится средствами CSS и меняется вместе со светлой или тёмной темой; отдельная пятнистая картинка больше не используется.
- Локальные шрифты не требуют ожидания внешнего сервиса.

## Проверки

Перед завершением изменения выполняются:

- ESLint — проверка качества кода;
- TypeScript — проверка типов;
- unit-тесты чистой логики;
- production build — итоговая сборка;
- проверка размера стартового пакета;
- Playwright E2E — сценарии браузера, прежде всего на детерминированном Demo.

Реальные Discord и Supabase нельзя полноценно заменить Demo. Для них нужны отдельные smoke/integration-проверки на Working, а после запуска — на Staging.

## Правило развития

Новая функция сначала получает чистую предметную логику и автоматический тест. Экран вызывает слой `src/data`, а сложная или составная работа с базой выполняется одной серверной функцией. Если принятое здесь решение меняется, одновременно обновляются этот документ, [decisions.md](decisions.md) и затронутый тематический документ.
