# Dashboard: анализ и подготовка модуля

Проверено 5 ноября 2026 по локальному коду. Исследование и отдельная копия завершены. По последующему поручению Алексея **локально добавлен компактный React Dashboard с четырьмя экранами Points/Profile/Speed/Density на синтетических данных**; внешний HTTPS PHP с6ноября подключён к явно выбранному development-просмотру; production остаётся закрыт; [план и текущий этап](analytics-dashboard-plan.md). Рабочие серверы, данные и доступ не изменялись; push не выполнялся.

Копия: [modules/analytics](../modules/analytics/README.md). Состав и контрольные суммы: [import-manifest.json](../modules/analytics/import-manifest.json). Проверки и состояние задачи: [отчёт](../memory/tasks/2026-11-05-dashboard-analysis.md).

## Что есть в двух проектах

| Область | Расписание | Импортированная аналитика |
|---|---|---|
| Интерфейс | React 19, Next.js 15, TypeScript | Vue 3, Vite 6, JavaScript, Pinia, Vue Router, ApexCharts |
| Сервер | Supabase RPC/Edge Functions; оболочка Next.js на Vercel | PHP с PDO; исходный процесс размещения — Apache/Hostland |
| База | PostgreSQL в Supabase: участники, права, расписание, приоритеты | MySQL сборщика: `tournament_snapshots` и производные `analytics_*` |
| Вход | Discord OAuth через Supabase, затем проверка активного профиля клуба | Общего входа нет; у административных операций отдельный пароль/сессия |
| Навигация | Разделы по `#schedule`, `#priorities`, общая шапка | Собственные пути `/`, `/points`, `/profile`, `/player/:name`, `/speed`, `/heatmap`, `/admin`, `/yearly`, `/players` |
| Проверенная сборка | Действующая сборка проекта | Самостоятельная Vue-сборка, не часть `apps/web` |

Это независимые предметные области. Переносить MySQL-данные в Supabase или смешивать расчёты с расписанием не требуется. Авторизация может быть общей, а хранение данных — раздельным. Автоматически связывать игровые ники аналитики с участниками клуба тоже не требуется и без отдельного правила небезопасно.

Аналитика — не одна диаграмма: 8 самостоятельных экранов в 9 Vue-файлах (PlayerView только перенаправляет к профилю), фильтры, списки «свои/чужие», заметки игроков, административные пересчёты. В `app/src` около 9,7 тыс. строк JS/Vue/CSS; в API около 6,4 тыс. строк PHP/JS. Поэтому полное переписывание затронет заметный объём поведения и формул.

## Точки подключения в расписании

- [App.tsx](../apps/web/src/App.tsx) переключает вход, ворота заявки и авторизованную оболочку.
- [data/auth.ts](../apps/web/src/data/auth.ts): `signInDiscord`, `loadLiveEntry`, `loadLiveMemberForAuthUser` проверяют Supabase-пользователя, профиль и серверный контекст прав. Просто наличие OAuth-аккаунта не равнозначно допуску в клуб.
- [data/client.ts](../apps/web/src/data/client.ts) создаёт браузерный Supabase-клиент; серверной cookie-сессии для Dashboard пока нет.
- [V2Shell.tsx](../apps/web/src/v2/V2Shell.tsx): верхнее меню `pages` и показ разделов. [shellNavigation.ts](../apps/web/src/v2/shellNavigation.ts) разрешает прямые адреса с учётом доступа.
- [next.config.ts](../apps/web/next.config.ts) ограничивает внешние подключения и содержимое через CSP. Внешний iframe нельзя добавлять без проверки этой политики.

Будущая минимальная правка приложения: пункт `Dashboard` рядом с расписанием/приоритетами, разрешённый переход и отдельная лениво загружаемая оболочка, RU/EN-подписи. Предметные модули `src/schedule`, RPC расписания, его расчёты и база остаются прежними. Размер Vue JS после сборки — 326,42 kB gzip; его нельзя добавлять в начальную загрузку расписания.

Действующий реальный вход — только Discord. Типы Google/email в коде не подтверждают готовность этих способов входа. Новый способ входа — отдельная задача; для Dashboard достаточно проверенной сессии существующего приложения.

## Найденные риски

### Критично: закрыть только страницу недостаточно

[api/index.php](../modules/analytics/upstream/api/index.php) направляет обычные запросы в обработчики без общей проверки пользователя. [regs.php](../modules/analytics/upstream/api/routes/regs.php) и [notes.php](../modules/analytics/upstream/api/routes/notes.php) содержат запись и удаление, также без общего входа. Чтение отчётов/поиск/профили не защищены административным паролем. Админские обработчики проверяют собственную сессию; cron — отдельный секрет. Это **подтверждено по исходникам**, а фактические дополнительные ограничения на работающем Hostland в этом исследовании не проверялись.

Следствие: ссылка или iframe на старый публичный Dashboard не выполняет требование закрытого доступа. Защита должна действовать на HTML и API, включая прямой запрос к PHP и старый адрес. Если прежний сервис оставить публичным, данные по прежнему адресу останутся доступными независимо от новой кнопки.

### Критично: секреты и побочные записи

- В исходных `.env` есть рабочие настройки; в старом `ref/api/config/database.php` найден встроенный пароль MySQL. Эти файлы **не перенесены**. Проверка Git-истории исходного репозитория и факта прежней публикации пароля не выполнялась. Перед выпуском следует заменить такой пароль и убрать его из старого кода; при замене учесть сборщик и существующий Dashboard. Смена доступа сейчас не производилась.
- [bootstrap.php](../modules/analytics/upstream/api/bootstrap.php) в `db()` создаёт таблицы регов/заметок и пытается создать индексы в сырой таблице. Это вызывается даже при `/health`. Для безопасного читающего сервиса DDL нужно вынести в отдельный управляемый этап, а подключению отчётов дать только необходимые права.
- [rebuild-player-hour.cjs](../modules/analytics/upstream/scripts/rebuild-player-hour.cjs) использует `TRUNCATE` и пересчёт; deploy-скрипты копируют `.env` в пакет размещения. Они сохранены как исходники, не адаптированы и не запускались.

### Важно: детали эксплуатации

- `/health` раскрывает имя базы, хост, путь `.env`, а ошибки API возвращают текст исключения. В будущем публичные ответы должны быть обезличены, подробности — в закрытом журнале.
- `send_cors()` разрешает `*`; это не авторизация. При подключении надо определить разрешённый источник, методы и обработку cookie/CSRF, а не полагаться на CORS как на запрет чтения.
- `api/cache` хранит результаты и административное состояние, включая хеши сессий. Эти файлы не должны попадать в Git, публичную раздачу, общие CDN-кэши или сборку. Существующий `.htaccess` зависит от Apache и не заменяет конфигурацию другого хостинга.
- Метрика опциональна; при включении [metrika.js](../modules/analytics/upstream/app/src/utils/metrika.js) задаёт `webvisor: true` независимо от описанного в шаблоне флага. Для закрытых профилей/заметок включать её автоматически нельзя; в копии счётчик не настроен.
- Данные времени — UTC в `scraped_at`, дни/часы аналитики — `Europe/Madrid`, с историческим названием `scraped_date_milan`. Не подменять их локальной зоной участника или общей логикой расписания. Формулы MAX/carry по отдельному игроку/лимиту сохранять и проверять отдельно на подготовленных данных.
- SQL в модуле описывает производные таблицы; схема сырой таблицы, сборщик и часть служебных зависимостей находятся вне `analytics`. Копия интерфейса сама не запускает сбор.

## Выбранный способ интеграции — React + прежние PHP/MySQL

5 ноября 2026 Алексей выбрал **React для нового интерфейса**, сохранив существующие PHP-расчёты, MySQL и процесс сбора. Прежнее предложение встроить Vue заменено этим решением. Исходники Vue остаются референсом, в рабочий сайт не импортируются. [Подробный план по экранам, компонентам и UI/UX](analytics-dashboard-plan.md).

Оболочка приложения предоставляет только общую навигацию, вход, тему и язык. Самостоятельный модуль React содержит свои меню, фильтры, модели данных, показатели, графики и страницы-композиции. По последующему подтверждению Алексея запросы идут через отдельный клиентский слой данных непосредственно по HTTPS к защищённому PHP API, который обращается к прежней MySQL. Проверка доступа добавляется в PHP; отдельный Node/Next.js-посредник и прямой доступ приложения к MySQL не требуются. Сначала переиспользуются существующие операции, дальнейшие оптимизации — по измерениям. Не меняются предметная логика расписания и его Supabase-БД.

Общая авторизация API всё равно необходима: сохранение расчётов не означает сохранение публичного доступа. Подлинность токена проверяется сервером, затем проверяется допуск участника. Supabase `getUser(jwt)` позволяет проверить переданный токен; браузерный localStorage сам по себе недоступен серверу. См. [getUser](https://supabase.com/docs/reference/javascript/auth-getuser) и [session storage](https://supabase.com/docs/guides/auth/server-side/advanced-guide). Точный серверный контракт и матрица прав ещё не реализованы.

Часть вычислений находится в исходном Vue: показатели профиля и подготовка временных рядов. Их перенос в чистые TypeScript-функции должен сохранять формулы и проверяться на одинаковых данных. Новая бизнес-логика не должна возникать внутри компонентов графиков. Детали приёмки и найденные расхождения старых подписей/API перечислены в плане.

## Приёмка будущего подключения

Прямой адрес без сессии, фальшивый/просроченный токен, Demo и заблокированный участник не получают аналитику. Проверяются прямой PHP-адрес, JSON/API, заметки, админка, cron, кэш, выход и кнопка «назад». Авторизованный участник получает только свой разрешённый набор операций; прежний публичный обход закрыт. Сравниваются формулы и даты на согласованной тестовой выборке. Выполняются RU/EN, мобильная проверка и полный регресс расписания. Только после этого можно считать Dashboard готовым к выпуску.
