## Компактная месячная сетка и точечное обновление — 4 ноября 2026

После успешных проверок тестовой ветки Алексей прямо разрешил выпуск того же пакета в main/Production. Это заменяет ограничение предыдущего этапа «только preview» для данного пакета. Новых изменений правил или повторной миграции не требуется.

Алексей утвердил компактные слоты со справочником игроков, обновление только изменившегося дня и лимита, сохранение начальной загрузки полного месяца и отсутствие серверного кэша. Это заменяет промежуточную клиентскую пагинацию `load_month_schedule`, подготовленную ранее в тот же день для устранения обрезания после 1000 строк. Переносить метки повторно не требуется.

Рабочий выбор реализации: одна скалярная JSON-RPC возвращает согласованные `slots`, `members` и `kinds`; имена и оформление передаются один раз на владельца. Закрытый Supabase Broadcast передаёт координаты изменённых участков, включая удаления. Клиент объединяет события за 100 мс, выполняет одно чтение за раз и повторяет чтение, если во время него пришло новое событие. Полное согласование выполняется после reconnect/возврата во вкладку; при недоступном канале действует резервный опрос видимой вкладки раз в 10 секунд. Справочник обновляется отдельным событием без повторной выгрузки слотов. Запись остаётся транзакционной через `apply_schedule_edit`; права на чтение и получение событий проверяет сервер. До полного начального ответа поле закрыто индикатором, фоновые запросы его не скрывают. Миграция совместима со старым клиентом и должна выйти до нового клиента; 4 ноября Алексей сначала разрешил миграцию и preview, а после успешной проверки — main/Production. Оба этапа выполнены и проверены.

## Организация кода расписания

Зафиксировано 4 октября 2026: координаторы `V2Schedule` и `OptField` сохраняют прежние внешние контракты; самостоятельные сценарии экрана вынесены в `src/v2/schedule`, а отрисовка и DOM-механика поля — в `src/v2/optField`. Разделение уменьшает связанность при добавлении функций и сохраняет один источник состояния месяца, права, RPC, локальные предпочтения и существующий UX. Чистые предметные правила остаются в `src/schedule`, ввод-вывод — в `src/data`. Карта модулей: [code-architecture.md](code-architecture.md#модули-экрана-расписания).

Оптимизация способа realtime-доставки, удаление совместимых путей старой схемы и изменение серверных операций выполняются отдельными задачами с проверкой конкурентной работы. Структурный перенос файлов сам по себе не является основанием менять алгоритмы записи или заявлять прирост производительности.

12 октября Алексей разрешил исправить четыре замечания аудита. Для этих исправлений запись подтверждённого диапазона переведена на одну `apply_schedule_edit` с проверкой ожидаемых чужих владельцев; состояние и поздние ответы изолированы по месяцу, optimistic-слои относятся к отдельным клеткам, realtime учитывает владельца отдельно от автора операции. Это изменение поведения по итогам аудита, а не часть прежнего структурного переноса. Общая сохранённая сетка/кеш остаётся предложением для отдельной оценки нагрузки.

## Профиль и права

Слепок Discord и профиль клуба — разные вещи. Права стоят на **роли Discord**, не на старых подписях «участник / админ / staff».

| Решение | Зачем так |
|---|---|
| Слепок кормит живые поля профиля (ник, аватар, роли) и **не удаляет** профиль, когда человек вышел | Иначе выход стирает анкету |
| Профиль — участник сервиса. Статус: **активен** или **заблокирован** | Список людей фильтруется по этому статусу и по живым ролям Discord |
| Галочки доступа стоят на роли. Человек получает права всех своих ролей | Новая роль с галочками даёт их, как только роль есть у человека и слепок обновился |
| Обязательная роль клуба — **RedParty**. Нет её или человек вышел с сервера — активный профиль блокируется. Сам доступ **не возвращается** | Вышедший не остаётся внутри. Вернуть может только тот, у кого есть «Управление пользователями» |
| Ручная блокировка при выходе не затирается. Неполный синк никого не блокирует | Обрыв Discord не должен выключить клуб |
| **Root** не блокируется и видит все разделы. Экран root **не раздаёт** старые роли | Владелец не запирает сам себя. Права не из старого флага admin |
| Кабинет открывается только с правом **«Профиль»** | Меню и сервер смотрят одну галочку |
| Сетка: право **«Расписание»** и лимит роли (Nitro/Regular и бай-ин). **«Управление расписанием»** свои слоты не даёт | Вести поле и играть — разные галочки |
| Заявка на вход и на восстановление требует живую роль RedParty. Самосоздание профиля — только если клуб включил тумблер и роль RedParty есть | С улицы и без роли клуб не открывается |
| SQL `is_staff()` теперь значит право **«Управление пользователями»**, не старый флаг admin | Имя в базе старое, смысл новый |

## Люди и Discord

| Решение | Зачем так |
|---|---|
| Вход — **Discord OAuth** (`identify` + `email`). Роли читает бот и пишет в слепок | Личность с Discord. Права — галочки на ролях этого слепка |
| Бот — **снимок** сервера в `discord_members`, не живой Discord на каждом экране | Список людей можно обновить кнопкой. Сайт в Discord на клик не ходит |
| Карточку расписания **не создаём на каждого** с сервера. Админ открывает человека из снимка | Иначе 150 пустых карточек. Склейка потом по Discord ID |
| Кисть admin/root за другого — **не смена аккаунта**. Кабинет и «Мой календарь» остаются своими. В списке кисти — только игроки | Красим чужую метку, не логинимся чужим лицом |
| Discord ID и ID в клубе (`public_code`) **в кабинете не показываем**. Админ видит их в карточке человека — **те же блоки, что кабинет**, плюс выделенные служебные поля | Игроку эти номера ни к чему. Поддержка ищет по ним в админке |
| Админская карточка человека — **тот же кабинет**. Анкета, метка, рум, лимиты и **канал уведомлений** те же. Служебное (доступ, Discord ID, ID в клубе, VIP, дистанции) видно дополнительно и выделено | Иначе два разных макета. Админ меняет, куда бот пишет, не спрашивая человека |
| `distance_ext_id` пишет только тот, у кого есть «Управление пользователями» (SQL `is_staff()`), **в кабинете не показываем** | Это ключ к выгрузкам рук, не поле анкеты |

## Сетка и столы

Заменено решением 5 ноября 2026 о цветных плашках. История: 4 ноября 2026, явный выбор Алексея в чате: вернуть видимость закрытых получасов тонким приглушённым пунктиром без фона. Прежнее слияние с фоном дня было намеренным; оно заменено, чтобы можно было глазами проследить строку. Вариант заливки как у прошлого не выбран: пунктир различает закрытый и прошедший слот. Рабочая настройка реализации — CSS `1px dashed`, 18% foreground, без изменения размеров/доступности.

4 ноября 2026: Алексей сначала выбрал C со свечением, затем заменил свечение небольшим отличием фона расписания от дневных блоков, сохранив усиленную рамку и иерархию день → вид турнира → лимит. Последующим уточнением Алексей попросил уменьшить только толщину рамки дня. Актуальные размеры: рамка дня 1 px (вместо 2 px), между видами 1 px сплошная, между лимитами 1 px более бледная пунктирная; отступ доски уменьшен до 4 px, зазор между днями 8 px. Настоящий border заменяет внутреннюю тень, которую перекрывала закреплённая колонка даты; CSS-псевдоэлемент удерживает левый край при горизонтальной прокрутке. У дня нет тени или фильтра: поле отличается однотонной CSS-заливкой (7% foreground к card), без анимации.

4 ноября 2026, уточнение Алексея: в подсказках наведения и выделения диапазона для установки/удаления цвет лимита берётся из палитры клуба, Regular курсивом, Nitro прямой. Время остаётся нейтральным и обычным начертанием, чтобы цвет быстро обозначал выбранную пару. Фон подсказки слегка окрашен текущим цветом лимита: 12% цвета палитры и 88% фона всплывающих окон, через CSS color-mix. Настройка палитры и смена темы автоматически меняют оттенок; время остаётся нейтральным. Последующее поручение Алексея: рамка подсказки имеет полный цвет лимита, все три состояния показываются поверх блокировок и остальных объектов. Рабочий выбор реализации — одна общая плашка в body вне контекстов слоёв строк, без анимации и покадровых вычислений.

4 ноября 2026, принято Алексеем: пользователю нужен личный переключатель «Отключить подсветку слотов» в окне настроек расписания. Реализация скрывает цвет нагрузки, по умолчанию он виден; локальное запоминание отдельно по аккаунту и среде, сброс возвращает подсветку. Общая настройка клуба не изменяется.

4 ноября 2026, дополнительное указание Алексея: все блоки настроек расписания сворачиваются независимо. По умолчанию открыт только блок управления с переключателями; остальные закрыты, чтобы администратор раскрывал нужный раздел. Черновики сохраняются при сворачивании внутри страницы.

4 ноября 2026, принято Алексеем: нагрузка по часам выбирается отдельно по виду турнира и лимиту, подсветка не переносится на другие пары. Для нагрузки, ёмкости и мёртвого времени нужен единый левый выбор в два столбца Nitro/Regular с кнопками N/E и курсивом Regular. Группы лимитов разделяются пунктиром, виды — более заметной линией; подсказка наведения содержит обозначение пары перед временем. Рабочее решение реализации: общая клубная запись нагрузки вместо прежнего localStorage, атомарное сохранение одной пары с проверкой ожидаемого значения, явный импорт старых локальных цветов. Последующее уточнение Алексея: вместо фонового слоя нагрузка показана заметным внешним свечением по периметру каждой клетки; CSS-тень ограничена своей группой, чтобы мягкость не нарушала смысл цвета. [Подробности](schedule-ux.md#нагрузка-по-часам-и-выбор-пары).

4 ноября 2026, принято Алексеем: палитра лимитов общая для клуба и редактируется администратором с `schedule.manage`; отдельные значения для светлой и тёмной темы. По умолчанию 5 красный, 25 зелёный, 50 синий, 100 графит/серебристый, 250 розовый, 500 фиолетовый. Цифры Nitro и Regular одного номинала имеют общий цвет, Regular сохраняет курсив. Последующее уточнение Алексея от того же дня: только буква N всегда синяя, E жёлтая; цифры остаются цветом номинала. Так вид и лимит различаются независимо, без смешивания двух цветов в одном тексте. Палитра лимитов едина для сетки, календаря и JPEG. Уточнение Алексея от 5 ноября: буквенные подписи внутри цветных смен и образцов личного календаря/JPEG используют нейтральный текст текущей темы без обводки; синие N и жёлтые E в обозначениях основного расписания сохраняются. Редактор находится последним в настройках расписания и свёрнут по умолчанию, поскольку используется редко. Сохранение явное; параллельные правки защищены сравнением предыдущей палитры. Каталог лимитов и права игроков не меняются. [UX](schedule-ux.md#общая-палитра-клуба).

3 ноября 2026, принято Алексеем: в подписи линии вид и лимит имеют главный визуальный акцент, порядковый номер находится ниже и мельче. Размеры ячейки и строки сохраняются; номер не добавляется для единственной линии. Причина: быстрее различать виды и лимиты, сохраняя плотность сетки.

| Решение | Зачем так |
|---|---|
| Админская галка **«Постоянное редактирование на компьютере»** разрешает desktop-пользователям сразу менять сетку. Если она выключена, сначала нажимают карандаш. На touch-устройствах сетка всегда открывается в безопасном просмотре: пользователь увеличивает поле до рабочей клетки, явно нажимает «Редактировать», затем «Готово». **Двойной клик не используем** | Мышь и touch требуют разной защиты: на телефоне один палец не должен одновременно перемещать поле и случайно ставить метки |
| На телефоне используется тот же `OptField`, а не вторая сетка. Масштаб пропорционально меняет ширину и высоту клетки; кнопки переходят по ровным десяткам, pinch остаётся плавным. С 75% редактирование включается карандашом из однострочной служебной панели под сеткой и завершается галкой. Слева стоит инструкция, в центре — метка, подсветка и правка, справа — масштаб. Fit показывается процентом и оставляет запас против горизонтальной прокрутки | Одна предметная реализация не расходится по правам и жестам, верхние фильтры остаются компактными, а инструменты не перекрывают последний день и часы |
| Модальные, листовые и плавающие поверхности на экранах до 640 px следуют одному контракту: 4–6 px безопасного отступа, максимум по `100dvh`, компактные шапка/действия и прокручиваемое содержимое. Общий `Dialog` разделяет неподвижные шапку и footer с внутренней областью прокрутки; desktop остаётся прежним | Отдельные окна не должны заново решать высоту телефона и случайно обрезать заголовок или кнопки; единое правило уменьшает визуальный шум и предотвращает горизонтальную прокрутку |
| Левый клик + протяжка **в одной строке уровня**. Чужой лимит в этот получас — красная рамка и подсказка, ставить можно. Две свои метки на соседних уровнях одного лимита — можно | Один жест. Часы считаем по уникальному получасу |
| Обычное наведение в режиме просмотра и редактирования не рисует рамку выбора: ячейка получает мягкое светлое свечение в тёмной теме и тёмное полупрозрачное свечение в светлой, а её получас показывается в небольшой плашке по центру сверху. В объединённом блоке эффект лежит отдельным слоем над выбранным получасом и под текстом общей метки. Рамка и подпись полного интервала появляются только после фактической протяжки на несколько слотов | Точное время полезно и без намерения редактировать; контраст должен сохраняться в обеих темах, содержимое метки не должно исчезать, а рамка однозначно означает диапазон, который будет применён |
| Метка на поле **сразу**, запись в базу следом. Тост успеха только после успешного ответа базы; ошибка — тост и откат всех клеток конкретной операции. Все жесты идут через строгую `apply_schedule_edit`: просрочивание клетки за время ожидания отменяет весь диапазон; fallback на частичные записи нет. После завершения очереди выполняется согласование свежим снимком месяца с задержкой 250 мс; все realtime-события, включая собственные из других сессий, проходят тот же путь | Исправление P2 по поручению Алексея 12 октября: предварительная отрисовка не означает сохранение, успешным не считается частичный диапазон. Состояние изолировано по месяцу, устаревшие ответы чтения отбрасываются, незавершённые правки не затираются снимком |
| `members.tables` / `occupancy.tables` — кисть и снимок **только если** включена галка **«Работа со столами»**. Сейчас выкл: число в базе может лежать, на экране его нет | Не водим мёртвое поле, пока клуб столы не считает |
| Сервер хранит 1–5 упорядоченных уникальных кистей 1–30 в `member_table_presets`; `members.tables` остаётся совместимым активным значением, а `occupancy.tables` — неизменяемым снимком поставленного слота. Набор целиком заменяется одной RPC владельцем или пользователем с `admin.people` | Пять независимых прямых полей и пошаговые записи легко рассинхронизировать; нормализованный набор даёт порядок, уникальность, атомарность и безопасный переход со старой кисти |
| В занятом получасе двухбуквенная метка всегда приоритетна: без столов она центрируется, со столами остаётся по центру чуть выше, а число независимо стоит в правом нижнем углу и не участвует в горизонтальной раскладке. Размер обоих текстов уменьшается вместе с мобильной ячейкой; на обзорном масштабе, где текст физически не помещается, подписи скрываются целиком | Число столов не должно вытеснять личную метку, а текст не должен выходить за границы сжатой сетки |
| Админская галка **«Соединять рядом стоящие слоты одного игрока»** по умолчанию выключена. При включении соседние получасы объединяются только визуально при совпадении суток, вида, лимита, уровня, владельца, метки и числа столов. Реальные ячейки остаются под блоком и принимают hover, клик и протяжку | Красивый непрерывный блок не должен менять данные, расчёт часов или возможность снять отдельный получас |
| Рабочие часы остаются локальным фильтром представления, но скрытие собственного занятого получаса обязано давать заметное красно-цветное предупреждение на соответствующей перегородке или внешней границе видимого диапазона. Проверяется вошедший пользователь, а не временно выбранная админом кисть | Локальная настройка не должна незаметно скрывать уже взятое обязательство; при этом чужая занятость не создаёт ложную тревогу |
| Мёртвое время задаётся несколькими ежедневными полуоткрытыми интервалами `[начало, конец)` в CET/Europe/Madrid отдельно для пары Nitro/Regular + лимит. Переход через полночь и пересечения одной пары запрещены сервером; весь набор заменяется одной RPC | Правило клуба едино для всех, атомарная запись не оставляет частичное состояние, а получас на границе относится ровно к одному интервалу |
| Компактная подсказка слота разделена на три уровня: **чипы вида/лимита + дата**, выровненные строки **CET / часовой пояс пользователя** с табличными цифрами и отдельным бейджем длительности, затем идентичность игрока. В ней увеличенный Discord-аватар важнее уменьшенной копии метки, непустое имя из анкеты служит заголовком, а серверный Discord-ник и актуальный Winamax-ник собраны вторичным подписанным блоком; столы дублируются только если клуб их считает. У визуально объединённого блока время охватывает всю непрерывную смену по исходным 48 получасам: скрытие часов лишь разрезает её отрисовку, но не диапазон подсказки. Одиночный слот остаётся получасовым. Профиль дополняется из актуального справочника игроков, но визуальные свойства и столы остаются снимком слота. Без ID | Контекст турнира не конкурирует с временем, два часовых пояса читаются одинаково и не «прыгают»; аватар, имя, ники и метка имеют естественный порядок значимости; локальный фильтр не искажает реальную длину смены, а старые слоты получают узнаваемый профиль без изменения исторического значения кисти |

Рабочее имя агента `external-api` заменяет первоначально предложенное `schedule-api`, чтобы название не ограничивало API расписанием.

Вход людей в приложение остаётся через Discord; отдельный случай — машинный доступ бота по индивидуальному отзываемому ключу с правом `schedule:read`. Главный ключ Supabase боту не выдаётся. Это предотвращает расхождение сайта и интеграции. Позднее3 ноября Алексей утвердил страницы по1000 меток с единым снимком: первый запрос фиксирует данные, последующие используют cursor и тот же ключ. Прежний предел10000 меток заменён пагинацией; защитные пределы объёма и числа активных снимков описаны в контракте. Исходный контракт возвращал при неоднозначном DST локальные координаты и null вместо выдуманного UTC; компактное уточнение ниже сохраняет локальное время с предупреждающим time_resolution без UTC-полей. Причина: большой диапазон должен выгружаться полностью, без пропусков/повторов при параллельном редактировании. Подробности: [контракт API](../supabase/functions/external-api/README.md).
