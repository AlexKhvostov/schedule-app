# Сборные таблицы аналитики (пошаговый конвейер) + JSON-кэш

> Зафиксировано / уточнено 14.09.2026.  
> Правило очков: [`docs/DATA_POINTS_MAX.md`](../../README.md#внешние-зависимости-исходного-проекта).  
> Формула объёма: [`POINTS_DENSITY.md`](POINTS_DENSITY.md).

## Где это живёт

**Не новая база данных.**  
Это **обычные таблицы** в **той же MySQL**, куда уже пишется `tournament_snapshots`  
(Hostland / `MYSQL_DATABASE` из `.env`).

Префикс имён: `analytics_…`, чтобы отличать от сырого лога сборов.

---

## Сутки = граница всего

Лидерборд Expresso обнуляется в **00:00** дня Europe/Madrid (`scraped_date_milan`).
Момент снимка в БД — UTC (`scraped_at`). Подробнее: [`TIMEZONE.md`](./TIMEZONE.md).

| Правило | |
|---------|--|
| Carry (перенос max) | **Только внутри одного `day` и одного `tournament_limit`**. |
| Из вчера в сегодня | **Нельзя**. В 00:00 у всех условно 0; вчерашние очки не тащим. |
| Ключ среза | Всегда пара **`day` + `hour`**, никогда «скользящие 24ч через полночь». |

Если игрок вчера закончил со 500, а сегодня первый снимок в 12:00 на 80 — в срезе сегодня до 11:00 его **нет** (ещё не появлялся); с 12:00 в C входит **80**, не 500.

---

## Лимиты никогда не смешиваются

Очки на бай-инах **независимы** (50€ ≠ 100€). Carry/MAX только внутри `(игрок, tournament_limit)`.

**Решение по схеме сборных таблиц:** одна таблица + колонка **`tournament_limit`**  
(не отдельная физическая таблица на каждый лимит).

Почему колонка лучше отдельных таблиц `…_50`, `…_100`:
- лимитов мало (4–6+), индекс по `(day, hour, tournament_limit, segment)` дешёвый;
- не плодим DDL при новом бай-ине;
- UI «несколько лимитов» = **SUM строк** выбранных `tournament_limit` за тот же day/hour (после того как каждая строка посчитана честно).

Запрещено: одна строка «набор 50+100+250» с заранее смешанным C внутри сборщика шага 1.  
Смешение только на чтении как сумма готовых per-limit строк (или отдельный кэш JSON после суммы).

## Конвейер (целевой)

```
tournament_snapshots               (сырой лог сборов)
        ↓ шаг 1
analytics_player_hour              (игрок × день × час × лимит: max + diff_points/seconds + speed)
        ↓ шаг 2
analytics_hour_slice               (суммы поля: Σ max, volume, счётчики)
        ↓ шаг 3
analytics_hour_avg / day_summary…  (только из предыдущих ступеней)
        +
analytics_scrape_hour              (параллельно: day×hour ok/down — downtime сбора)
        +
JSON-кэш Points / Home             (из player_hour или hour_slice)
```

Сейчас в проде: шаг 1 (`analytics_player_hour`) и шаг 2 (`hour_slice` из player_hour) реализованы в админке.
Также: `analytics_scrape_hour` (часовой downtime) заполняется при сборке дня.

## Шаг 1 — `analytics_player_hour` (готово)

**Где:** Админка → «Почасовой max игрока». SQL: `api/sql/analytics_player_hour.sql`.

**Одна строка** = один игрок × один день ES × один час × **один** лимит.

Игрок на 50€ и 100€ в одном часу → **две строки**. Лимиты не смешиваются.

| Поле | Смысл |
|------|--------|
| `player_name` | ник |
| `day` | `scraped_date_milan` (сутки ES) |
| `hour` | 0–23 Europe/Madrid |
| `tournament_limit` | `16-25` / `50` / `100` / `250` |
| `max_points_carry` | **Накопленный максимум (carry):** наибольшие очки с 00:00 ES до конца часа H. Внутри дня не падает. Для срезов поля. |
| `min_points_hour` | Мин. очки среди **снимков только в часу H** (пара к `max_points_hour`) |
| `max_points_hour` | Макс. очки среди **снимков только в часу H** (без накопления с утра; может быть меньше `max_points_carry`) |
| `diff_points` | Разница **внутри часа** для скорости: `max_points_hour − min_points_hour`. Час 0 / первое появление: max − 0 |
| `diff_seconds` | Окно внутри часа: `|max_at − min_at|`. Час 0 / первое появление: `max_at − 00:00 ES` |
| `delta_hour` | Междучасовая разница для heatmap/плотности: `max_points_hour(H) − max_points_hour(H−1)`. Час 0: max − 0. Сумма за день ≈ dayMax |
| `speed` | `(diff_points / diff_seconds) × 3600` (очки/час внутри часа), NULL если интервал 0 |
| `rank_at_max` | место (`rank`) из снимка, на котором зафиксировали текущий `max_points_carry` |
| `has_snapshot` | 1 = в часу H был хотя бы один снимок на этом лимите |
| `min_at` / `max_at` | **UTC+0**: время min/max снимков в часу; `max_at` — момент пика часа (для скорости) |
| `computed_at` | UTC+0 пересчёта |

Скорость (хранится): `speed = diff_points / diff_seconds × 3600` (очки/час **внутри часа**).  
Heatmap / плотность / «+N» в отчётах берут `delta_hour` (между часами). Сырьё в первые 5 минут суток ES игнорируется (`PLAYER_HOUR_SKIP_FIRST_MINUTES`).  
На фронте `min_at`/`max_at` можно показывать в любом TZ — в БД всегда Greenwich.

Уникальный ключ: `(day, hour, tournament_limit, player_name)`.

### Дни без сырья и качество суток (`analytics_player_hour_day` + отчёт coverage)

| status | Смысл |
|--------|--------|
| `ok` | закрытые сутки, вечер после 22:00 есть, дыр нет, агрегат совпадает с сырьём, все лимиты из сырья на месте |
| `partial` (**неполно**) | нет данных после 22:00 ES, дыры по часам в snapshots, или в сырье есть часы/лимиты, которых нет в агрегате |
| `subset` (**лимиты**) | в сырье не все 4 бай-ина (остальные, видимо, выключены) — это не недосбор |
| `today` | текущие сутки ES ещё идут |
| `no_data` | в `tournament_snapshots` за сутки 0 строк |
| `empty` | сырьё есть, агрегат ещё не собран |

В админ-контроле: галочки лимитов + полоска часов 0–23 (зелёный = в агрегате, жёлтый = только в snapshots).

Автозаполнение: только `empty` + `partial`.

### Правила

1. Carry только внутри `(day, tournament_limit)` для этого ника. Вчера → сегодня нельзя.
2. До первого появления за день на лимите — **строк нет**.
3. Нет снимка в H, но игрок уже «в игре» сегодня на лимите → строка есть: `max_points_carry` = carry, `has_snapshot=0`, `rank_at_max` = то же место, что у снимка, где этот max был установлен (не ищем заново).
4. Если в H пришёл снимок с очками ≥ текущего max → обновляем `max_points_carry` и **перезаписываем** `rank_at_max` с этого снимка.
5. Если снимок с очками **ниже** текущего max (редко / шум) → max не понижаем; rank_at_max не трогаем (остаётся от пика).

`hour_slice.cumulative` = `SUM(max_points_carry)` по игрокам за тот же day/hour/limit.  
`hour_slice.volume` = прирост Σ max (с правилом дыры на уровне поля).

Джоб **hour_slice** при «Обновить» сначала пересобирает player_hour за окно, затем пишет slice.

## Часы сбора / downtime — `analytics_scrape_hour`

Отдельный слой «когда сервер не писал», не агрегат очков.

| Поле | Смысл |
|------|--------|
| `day` + `hour` | сутки и час ES |
| `snapshot_count` | строк в `tournament_snapshots` за час (наши лимиты) |
| `has_data` | был ли хоть один снимок |
| `status` | `ok` / `down` (час прошёл, сырья 0) / `pending` (будущий час сегодня) |

Заполняется при сборке `player_hour` и джобой «Часы сбора».  
Дневной `api/config/downtime.json` — длинные **ручные** интервалы (Yearly); эта таблица — авто по часам.

Админка: у каждой ready-таблицы вкладки **1. Статистика · 2. Контроль · 3. Обновление**.

## Бэклог скрапера (отдельная задача, не путать с агрегатами)

**Проблема:** дедуп `(player, limit, points, day)` не пишет повтор, если очки не выросли.  
Игрок доиграл до обеда → к вечеру в логе нет «финального» места дня.

**Идея (не реализовано):** в последние ~20 мин суток ES (2–3 сбора) **форсировать** запись текущего состояния лидерборда (очки + место), даже если points те же. Следующий такой же снимок можно снова скипнуть.

Зачем: сырьё для `rank` в конце дня / суточный max игрока / профиль.  
Делать **отдельным тикетом** после `analytics_player_hour`.

## Шаг 2 — `analytics_hour_slice` (подробно)

**Где смотреть / запускать:** пункт меню **Админка** в аналитике (`/admin`).

### Назначение

Сборная таблица **поля** (без ников). Одна строка = один час одного дня **одного** бай-ина.  
Позже источник = `SUM` из `analytics_player_hour`, не повторный проход по snapshots.

| Поле | Тип | Описание |
|------|-----|----------|
| `day` | DATE | День лидерборда (`scraped_date_milan`) |
| `hour` | TINYINT 0–23 | Час Europe/Madrid |
| `tournament_limit` | VARCHAR | Один лимит: `16-25`, `50`, `100`, `250` |
| `segment` | VARCHAR | Пока всегда `all` |
| `players_seen` | INT | Сколько ников уже встречались с 00:00 до конца H на этом лимите |
| `players_new` | INT | Впервые за день на этом лимите именно в часу H |
| `players_active_hour` | INT | У скольких был реальный снимок в H |
| `cumulative` | INT | C(H) = Σ max с carry |
| `volume` | INT | C(H)−C(H−1); если в H−1 не было записей → 0 |
| `has_records` | BOOL | Был ли снимок лимита в часу |
| `computed_at` | DATETIME UTC | Когда строка пересчитана |

Уникальный ключ: `(day, hour, tournament_limit, segment)`.

SQL: `api/sql/analytics_hour_slice.sql` (+ таблица логов `analytics_job_runs`).

### Админка

- Список таблиц, статус, последний запуск, число строк / диапазон дней.
- Кнопка **Обновить** → PHP job пересчитывает окно (по умолчанию 60 дней + сегодня) для лимитов 16-25/50/100/250.
- Клик по таблице / «Описание» → модалка: зачем, правила, поля, план обновления.
- Вход: пароль `ANALYTICS_ADMIN_PASSWORD` в `.env`. 3 ошибки → блок на 1 час (по IP, файл `api/cache/`).
- Сессия 12 ч в `sessionStorage` + заголовок `X-Admin-Session`.

## Шаг 3 — `analytics_hour_avg` (из slice, не из лога)

Средние **по числам из `analytics_hour_slice`** за окно (напр. 60 дней):

- `avg_volume` по часу (все дни / только этот weekday);  
- позже при необходимости: `avg_cumulative`, `avg_players_seen` — **новые колонки или строки**, база slice не ломается.

## JSON-кэш «сегодня»

Файл ≈ содержимое **шага 1 за сегодняшний `day`** (24 часа метрик выше).

- Если JSON есть и ему **≤ 15 мин** → отдать сразу.  
- Если старше / пусто → отдать старый при наличии **и** в фоне обновить; cold start — один раз посчитать.  
- Следующий запрос уже на более свежем файле.

Средние линии графика — из `analytics_hour_avg`, не обязаны жить в том же JSON.

## Порядок работ

1. ✅ Зафиксировать сутки-границу, «таблицы в той же БД», метрики slice (этот документ).  
2. DDL `analytics_hour_slice` + сборщик из `tournament_snapshots`.  
3. Backfill истории + «сегодня».  
4. `analytics_hour_avg` из slice.  
5. Home читает avg + сегодня (JSON/slice).  
6. JSON stale-while-revalidate.
