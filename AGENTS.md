# Инструкции для работы с репозиторием

Этот файл — обязательная стартовая точка для новых сессий Codex и других разработчиков.

## Перед изменениями

1. Прочитать `docs/current-state.md`.
2. Прочитать релевантный раздел `docs/decisions.md`.
3. Открыть тематический документ из `docs/README.md`.
4. Проверить `git status` и не перезаписывать чужие незавершённые изменения.
5. Сверить документацию с кодом и миграциями. При конфликте фактический код и применённая схема важнее старого описания; противоречивый документ нужно исправить в той же работе.

## Источники истины

Порядок доверия:

1. Код `apps/web`, миграции и Edge Functions в `supabase`.
2. `docs/current-state.md` — что работает сейчас.
3. `docs/decisions.md` — принятые продуктовые и архитектурные решения.
4. Тематические спецификации (`schedule-ux.md`, `auth.md`, `database.md` и другие).
5. Исторические документы `schedule-now.md`, `sandbox.md` и старые материалы в `references`.

Исторический документ нельзя использовать как задание на повторную реализацию без проверки текущего кода.

## Каноническая реализация

- Рабочее приложение: `apps/web` (Next.js + React).
- Предметная логика: `apps/web/src/schedule`.
- Доступ к данным: `apps/web/src/data`.
- Интерфейс: `apps/web/src/v2` и `apps/web/src/components`.
- Серверная схема и права: `supabase/migrations`.
- Внешние интеграции: `supabase/functions`.
- `sandbox/ui` — историческая лаборатория, не второй источник бизнес-логики.

## Среды

- Demo — локальные фейковые данные, Supabase не вызывается.
- Working/Development — текущий Supabase для разработки и интеграционных проверок.
- Production — отдельного чистого проекта пока нет.
- Push в `main` автоматически деплоит `apps/web` через Vercel.
- Миграции Supabase и Edge Functions автоматически не деплоятся.

Подробности: `docs/environments-and-architecture.md` и `docs/operations.md`.

## Обязательные правила изменений

- Не помещать прямые запросы к Supabase в React-компоненты; использовать `src/data`.
- Составные записи выполнять одной транзакционной RPC-функцией.
- Права проверять на сервере, а не только скрытием кнопок.
- Все пользовательские тексты добавлять одновременно в `locales/ru.json` и `locales/en.json`.
- Новую чистую логику покрывать unit-тестом; важный пользовательский сценарий — Playwright E2E.
- Не добавлять вторую реализацию уже существующей механики: сначала искать её через `rg` и читать `docs/work-log.md`.
- При принятии нового устойчивого решения обновлять `docs/decisions.md`, тематический документ и при необходимости `docs/current-state.md`.
- Не записывать секреты, токены и реальные приватные данные в git или документацию.

## Документация — часть результата

Диалог, который меняет проект, обязан поддерживать документацию в актуальном состоянии в рамках той же задачи. Изменение нельзя считать полностью завершённым, если код, база или процесс уже изменились, а документы всё ещё описывают прежнее состояние.

Перед завершением работы нужно просмотреть сделанные изменения и обновить только относящиеся к ним документы:

- принято или изменено устойчивое продуктовое либо архитектурное решение → `docs/decisions.md` с причиной решения;
- изменилось то, что фактически работает → `docs/current-state.md`;
- добавлена, удалена или существенно изменена технология, библиотека, внешний сервис либо способ их применения → `docs/stack.md` и при необходимости `docs/decisions.md`;
- изменились границы модулей, структура файлов или поток данных → `docs/code-architecture.md` и/или `docs/repo-structure.md`;
- изменились база, права, RPC или интеграции → соответствующий тематический документ;
- завершён крупный этап работы → краткая запись в `docs/work-log.md`;
- изменились деплой, проверки, переменные среды, backup или откат → `docs/operations.md`.

В документацию записываются итог и причина, а не полный ход рассуждений диалога. Идеи, которые ещё не приняты, нельзя выдавать за действующее решение. Если решение заменено, нужно исправить прежнюю запись или явно отметить её как заменённую, а не оставлять два противоречащих правила.

Если в работе не было изменений, влияющих на документацию, создавать формальную пустую запись не нужно. В итоговом ответе следует кратко указать, какие документы обновлены, либо явно сказать, что обновление документации не требовалось.

## Проверка перед завершением

Из `apps/web`:

```bash
npm run typecheck
npm run lint
npm test
npm run bundle:check
npm run build
npm run test:e2e
```

При изменении базы дополнительно выполнить локальную пересборку Supabase, SQL security contracts и database lint, как описано в `docs/operations.md`.

После технических проверок ещё раз сверить `git diff` с документацией по правилам выше и проверить локальные ссылки в изменённых Markdown-файлах.
